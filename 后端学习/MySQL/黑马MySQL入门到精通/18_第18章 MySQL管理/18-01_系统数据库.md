# 系统数据库

> 来源：P148《91. 进阶-MySQL管理-系统数据库介绍》 · 档位 B 部分重叠
> 与我已知的关系：SQL Server 有 `master`/`msdb`/`tempdb`，MySQL 是四个系统库，**其中两个是给你查性能的**

==一：意义与概念==

MySQL 自带四个系统库，各管一摊：

| 库 | 作用 | 你会不会用到 |
|---|---|---|
| `mysql` | 用户、权限、存储过程/事件定义、系统变量 | 查权限、改密码 |
| `information_schema` | **元数据视图**：有哪些库/表/列/索引/触发器 | ⭐ 常用 |
| `performance_schema` | **性能监控**：锁等待、慢 SQL、内存、线程 | ⭐ 排查问题必用 |
| `sys` | **基于 `performance_schema` 的视图封装**，更易读 | ⭐ 推荐优先用 |

### `information_schema`：元数据的标准入口

它是**视图**，不是真实表（每次查会实时读元数据）。常用的：

```sql
-- 有哪些库、各多大
SELECT table_schema, SUM(data_length+index_length)/1024/1024 AS mb
FROM information_schema.tables GROUP BY table_schema;

-- 某张表的列定义
SELECT column_name, column_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema='demo' AND table_name='emp';

-- 哪张表引擎不是 InnoDB（迁移前必查）
SELECT table_name, engine FROM information_schema.tables
WHERE table_schema='demo' AND engine <> 'InnoDB';

-- 哪些表没有主键
SELECT t.table_name FROM information_schema.tables t
LEFT JOIN information_schema.table_constraints c
  ON c.table_schema=t.table_schema AND c.table_name=t.table_name AND c.constraint_type='PRIMARY KEY'
WHERE t.table_schema='demo' AND c.table_name IS NULL;
```

最后那条**非常实用**：没有主键的表在 InnoDB 里用隐藏 `row_id`，你失去了对物理顺序的控制（11-04）。

### `performance_schema`：排查问题的核心

几个 8.0 版的常用表：

| 表 | 查什么 |
|---|---|
| `data_locks` | **当前所有锁**（行锁、表锁、间隙锁）|
| `data_lock_waits` | **谁在等谁的锁**（死锁/阻塞排查）|
| `events_statements_summary_by_digest` | 按"SQL 模板"聚合的执行统计（**找慢 SQL 的最佳入口**）|
| `metadata_locks` | MDL 锁（16-03 的 ALTER 卡死）|
| `threads` | 当前连接与线程状态 |

`events_statements_summary_by_digest` 值得单独说：它会**把参数不同的同一类 SQL 归并**（`SELECT * FROM t WHERE id = ?`），统计总耗时、执行次数、扫描行数。**这比慢查询日志更全面**，因为它不看单次阈值，看总量。

```sql
SELECT DIGEST_TEXT, COUNT_STAR, 
       ROUND(SUM_TIMER_WAIT/1e12, 2) AS 总秒数,
       ROUND(AVG_TIMER_WAIT/1e9, 2) AS 平均毫秒,
       SUM_ROWS_EXAMINED AS 扫描行数
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
```

这条 SQL 能直接告诉你"库里的性能被哪几条 SQL 吃掉了"。**建议存下来**。

### `sys`：把上面的东西变得能读

`sys` 库把 `performance_schema` 的原始数据算成了可读视图：

```sql
SELECT * FROM sys.innodb_lock_waits;      -- 谁阻塞了谁
SELECT * FROM sys.statements_with_full_table_scans LIMIT 10;  -- 全表扫描的 SQL
SELECT * FROM sys.schema_unused_indexes;  -- 从没被用过的索引（可以删！）
```

`sys.schema_unused_indexes` 是清理冗余索引的好工具——比手工对比快得多。

和 EF Core 的关系：这三张表能直接定位"EF Core 生成的 SQL 有没有问题"：

```sql
-- 找出所有全表扫描的语句（EF Core 的 LINQ 写错时就会出现在这里）
SELECT query, exec_count, total_latency
FROM sys.statements_with_full_table_scans
ORDER BY total_latency DESC LIMIT 5;
```

==二：使用格式==

```sql
SHOW DATABASES;
USE information_schema;
SELECT * FROM tables WHERE table_schema='demo';
```

==三：代码实践==

```sql
-- 一键体检：非 InnoDB 表 + 无主键表 + 未使用索引
SELECT '非InnoDB' AS 问题, table_name FROM information_schema.tables
WHERE table_schema='demo' AND engine<>'InnoDB'
UNION ALL
SELECT '未使用索引', object_name FROM sys.schema_unused_indexes
WHERE object_schema='demo';
```

==四：总结归纳==

- 三条：`information_schema` 查结构（引擎/主键/列定义）；`performance_schema` 查性能与锁；`sys` 是更好读的封装，优先用。
- 记忆锚：`information_schema` 是"户口本"，`performance_schema` 是"体检仪"，`sys` 是"体检报告"。

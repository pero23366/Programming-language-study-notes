# 事务四大特性 ACID

> 来源：P53《53. 基础-事务-四大特性ACID》 · 档位 A 几乎重叠
> 与我已知的关系：四个特性与 SQL Server 的定义一字不差，这里只补"各自靠什么实现"这一层

==一：意义与概念==

ACID 你在 C# 里 `TransactionScope` 那套已经理解过，这里不需要重新定义，只需要把"特性 → 实现机制"这条线接上去，因为第 17 章（InnoDB 原理）会从这条线继续往深处走：

| 特性 | 保证什么 | MySQL 靠什么实现 |
|---|---|---|
| **A** 原子性 Atomicity | 要么全成功要么全失败 | **undo log**（记录反向操作，回滚时逆着执行）|
| **C** 一致性 Consistency | 数据始终满足约束（如总额不变）| 是**结果**，由 A、I、D 共同保证 + 约束 |
| **I** 隔离性 Isolation | 并发事务互不干扰 | **锁** + **MVCC**（多版本并发控制）|
| **D** 持久性 Durability | 提交后断电也不丢 | **redo log**（先写日志再刷盘，WAL）|

两个值得记住的判断：

1. **一致性是目的，不是手段**。A、I、D 是手段，C 是它们共同达成的效果。所以"事务保证一致性"这句话本身是同义反复——真正要盯的是约束有没有写全（第 7 章）。
2. **redo log 和 undo log 是两套东西**：redo 管"已提交的别丢"（前滚），undo 管"没提交的撤回去"（回滚）。第 17 章会把这条彻底展开，现在只需要建立这个二分。

==四：总结归纳==

- 三条：A 靠 undo log、D 靠 redo log、I 靠锁 + MVCC；C 是前三者达成的结果。
- 记忆锚：undo 往回撤（未提交），redo 往前保（已提交）。
- 自测：断电后数据没丢，是 undo log 还是 redo log 的功劳？

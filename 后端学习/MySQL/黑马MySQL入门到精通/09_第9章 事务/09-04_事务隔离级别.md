# 事务隔离级别

> 来源：P55《55. 基础-事务-并发事务演示及隔离级别》 · 档位 B 部分重叠
> 与我已知的关系：四个级别同名同序，**但 MySQL 默认是 REPEATABLE READ，SQL Server 默认是 READ COMMITTED**

==一：意义与概念==

隔离级别是"性能与正确性的旋钮"：级别越高，并发问题越少，并发能力越差。

| 级别 | 脏读 | 不可重复读 | 幻读 | 谁的默认 |
|---|---|---|---|---|
| `READ UNCOMMITTED` 读未提交 | ✅ 会 | ✅ 会 | ✅ 会 | 没人用 |
| `READ COMMITTED` 读已提交 | ❌ | ✅ 会 | ✅ 会 | **SQL Server / Oracle 默认** |
| `REPEATABLE READ` 可重复读 | ❌ | ❌ | ⚠️ 基本解决 | **MySQL 默认** |
| `SERIALIZABLE` 串行化 | ❌ | ❌ | ❌ | 极少用 |

（✅ 会 = 该问题仍存在）

**这是本次课里对你影响最大的一条默认值差异。** 你在 SQL Server 里写的代码，默认处在 RC；换到 MySQL 默认 RR，行为会变：

1. **同一事务内反复读同一行，结果恒定**（读的是事务开始时的快照），不再受别人提交影响。
2. **幻读靠间隙锁压制**：`SELECT ... FOR UPDATE` 在 RR 下锁的不只是命中的行，还包括行之间的"间隙"，所以别人插不进来。代价是**锁范围变大、死锁概率变高**。
3. RC 下没有间隙锁（只有行锁），并发更高但会出现幻读。所以很多互联网公司**主动把 MySQL 改成 RC**，就是为了减少间隙锁带来的锁冲突。这是一个真实存在的工程取舍，不是"默认值最优"。

`SERIALIZABLE` 在 MySQL 里会把所有普通 `SELECT` 隐式变成 `SELECT ... FOR UPDATE`，等于全表读锁，并发直接崩，只在极少数对账场景用。

==二：使用格式==

```sql
-- 查看（8.0 的变量名是 transaction_isolation，5.7 是 tx_isolation）
SELECT @@transaction_isolation;

-- 设置：只影响当前会话
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 设置：影响之后新建的所有连接（重启失效）
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 只对下一个事务生效
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

| 作用域 | 命令 | 生效范围 |
|---|---|---|
| `SESSION` | `SET SESSION ...` | 当前连接 |
| `GLOBAL` | `SET GLOBAL ...` | 新连接（已有连接不变）|
| 单事务 | `SET TRANSACTION ...` | 下一个事务 |

==三：代码实践==

```sql
-- 复现"不可重复读"：把级别降到 RC
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT salary FROM emp WHERE id = 1;   -- 1000

-- 另一个会话：UPDATE emp SET salary=2000 WHERE id=1; COMMIT;

SELECT salary FROM emp WHERE id = 1;   -- 2000，同一事务内变了
COMMIT;

-- 换回 RR 再试一次，第二次读仍是 1000
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

==四：总结归纳==

- 三条：MySQL 默认 RR、SQL Server 默认 RC；RR 靠间隙锁压幻读，代价是锁范围大；RC 并发高但会幻读。
- 记忆锚：隔离级别是"看得见多少别人的改动"的开关，越往下看得越少但越安全。

# 并发事务问题

> 来源：P54《54. 基础-事务-并发事务问题》 · 档位 B 部分重叠
> 与我已知的关系：脏读/不可重复读/幻读三个定义一样，**但 MySQL 默认隔离级别是 RR，你在 SQL Server 上遇到的"不可重复读"默认不会发生**

==一：意义与概念==

两个事务同时读写同一批数据时，会出现三种"看到不该看的东西"的现象。定义与 T-SQL 教材一致，重点是它们的**区别在哪一步**：

| 问题 | 场景 | 本质 |
|---|---|---|
| **脏读** | A 改了没提交，B 读到了这个"脏"值；A 回滚，B 手里的数据从未存在过 | 读到了**未提交**的数据 |
| **不可重复读** | A 第一次读 `salary=1000`，B 改成 2000 并提交，A 再读变 2000 | 同一事务内**同一行两次读结果不同**（UPDATE 导致）|
| **幻读** | A 查"部门 1 有 3 人"，B 插入 1 人并提交，A 再查变 4 人 | 同一事务内**结果集行数变了**（INSERT/DELETE 导致）|

记法：**脏读是读未提交，不可重复读是行变了，幻读是行数变了。**

关键差异在默认隔离级别：

- **SQL Server / Oracle 默认 READ COMMITTED**：不会脏读，但**会出现不可重复读和幻读**。你在 .NET 里做"先查余额再扣款"的经典逻辑，如果不显式开事务或加锁，中途被别人改过是完全可能的。
- **MySQL 默认 REPEATABLE READ**：脏读和不可重复读都不会发生（同一事务内读到的永远是自己第一次读的那个快照），**幻读靠间隙锁（next-key lock）压制**。

所以从 SQL Server 迁到 MySQL 时，原本"必须加锁才安全"的代码可能变安全了，反过来也有另一种风险：**RR 下读到的是快照，看不到别人刚提交的数据**，做"检查库存→扣减"这种逻辑时，另一个事务刚加的库存你看不见，仍要显式 `SELECT ... FOR UPDATE` 加锁。

==二：使用格式==

这三种问题不能"手动触发"，只能通过隔离级别控制。相关语句在下一篇。

==三：代码实践==

```sql
-- 会话 A
START TRANSACTION;
SELECT COUNT(*) FROM emp WHERE dept_id = 1;   -- 3

-- 会话 B
INSERT INTO emp (name, dept_id) VALUES ('新人', 1);
COMMIT;

-- 会话 A 再查（RR 级别下仍是 3，因为读的是快照）
SELECT COUNT(*) FROM emp WHERE dept_id = 1;   -- 3
-- 但如果 A 执行 UPDATE ... WHERE dept_id=1，会看到 4 行（当前读）
```

这条注释里的"当前读 vs 快照读"是理解 RR 的关键：**普通 `SELECT` 读快照，`UPDATE` / `DELETE` / `SELECT ... FOR UPDATE` 读最新版本**。第 17 章 MVCC 会解释为什么同一个事务里两种读法结果不一样。

==四：总结归纳==

- 三条：脏读=读未提交、不可重复读=行变了、幻读=行数变了；MySQL 默认 RR 不会脏读也不会不可重复读；RR 下 `SELECT` 读快照但 `UPDATE` 读最新值。
- 记忆锚：脏读是"看了别人没写完的草稿"，不可重复读是"同一页读两遍内容变了"，幻读是"书里多了一页"。

# 触发器：概念与语法

> 来源：P116《59. 进阶-触发器-介绍》 · 档位 B 部分重叠
> 与我已知的关系：SQL Server 有触发器且支持 `INSTEAD OF`；**MySQL 只有行级 `BEFORE/AFTER`，没有语句级、没有 `INSTEAD OF`**

==一：意义与概念==

**触发器**：在表的 `INSERT`/`UPDATE`/`DELETE` 前后**自动执行**的一段逻辑。你不用调用，它自己跑。

和存储过程的区别：存储过程要 `CALL`，触发器靠"表的变更"触发。

MySQL 触发器的六个组合（3 事件 × 2 时机）：

```
BEFORE INSERT / AFTER INSERT
BEFORE UPDATE / AFTER UPDATE
BEFORE DELETE / AFTER DELETE
```

**只有行级触发器**（`FOR EACH ROW`），这是与 T-SQL 最大的差异：

| | MySQL | T-SQL |
|---|---|---|
| 语句级触发器 | ❌ 没有 | ✅ 有（一次语句触发一次）|
| 行级触发器 | ✅ 只能这个 | ✅（`FOR EACH ROW` 需要显式声明，或用 `inserted/deleted` 表）|
| `INSTEAD OF` | ❌ 不支持 | ✅ 支持（常用于可更新视图）|
| 取新旧值 | `OLD.列` / `NEW.列` | `deleted` / `inserted` 虚拟表 |

**没有 `INSTEAD OF`** 意味着：你不能用触发器"拦截"一次插入然后改写它——只能 `BEFORE INSERT` 里改 `NEW.列` 的值，这算替代方案但语义不同。

`OLD` 与 `NEW` 的可用性：

| 事件 | OLD | NEW |
|---|---|---|
| `INSERT` | ❌ 不可用 | ✅ 新值 |
| `UPDATE` | ✅ 旧值 | ✅ 新值 |
| `DELETE` | ✅ 旧值 | ❌ 不可用 |

在 `BEFORE` 触发器里**可以给 `NEW.列` 赋值**（相当于改写要写入的数据），这是 MySQL 触发器最有用的能力之一。

### 触发器的真实评价

课程会讲它"能保证数据完整性"。但工程现实是：**触发器是"隐式行为"，是维护性最差的设计之一**。

- 排查问题时，你不知道一条 `UPDATE` 背后还做了什么。
- 触发器里再触发触发器，链式反应难以追踪（MySQL 不允许同一表上的触发器递归，但跨表可以）。
- 备份/迁移/分库分表时触发器常被忽略，导致数据不一致。
- 阿里 Java 手册明确：**禁止使用触发器**。

**该学的理由**：存量系统里有大量触发器（尤其是"自动更新更新时间""写操作日志"），你得能读懂、能改、能删。

和 EF Core 的关系：EF Core **完全不知道触发器的存在**。`SaveChanges()` 之后实体的值可能已经被触发器改过，但 EF Core 的内存实体不会同步——这就是"实体和数据库数据不一致"的一个隐蔽来源。EF Core 7 起可以用 `.ToTable(tb => tb.HasTrigger("trg_name"))` 告诉 EF Core "这表有触发器"，让它在保存后重新读取值（`SaveChanges` 会追加一次查询）。

==二：使用格式==

```sql
CREATE TRIGGER 触发器名
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON 表名 FOR EACH ROW
BEGIN
  -- 逻辑
END;
```

==三：代码实践==

```sql
DELIMITER $$

-- BEFORE INSERT：自动补全字段
CREATE TRIGGER trg_emp_before_insert
BEFORE INSERT ON emp
FOR EACH ROW
BEGIN
  IF NEW.create_time IS NULL THEN
    SET NEW.create_time = NOW();          -- 改写要插入的值
  END IF;
END $$

DELIMITER ;
```

==四：总结归纳==

- 三条：只有 `BEFORE/AFTER` × 三种事件共六种，全是行级；没有 `INSTEAD OF`；`BEFORE` 里可改 `NEW.列`。
- 记忆锚：触发器是"表的条件反射"，条件反射太多，人就查不出病因了。
- 自测：① MySQL 有语句级触发器吗？② `DELETE` 触发器里能读 `NEW` 吗？

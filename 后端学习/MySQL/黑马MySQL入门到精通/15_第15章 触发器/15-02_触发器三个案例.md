# 触发器三个案例：INSERT、UPDATE、DELETE

> 来源：P117–P119《60–62. 进阶-触发器-案例1(insert类型) / 案例2(update类型) / 案例3(delete类型)》 · 档位 B 部分重叠
> 与我已知的关系：三个案例对应三种典型用途——补默认值、留审计痕迹、级联清理

==一：意义与概念==

三个案例分别代表触发器最合理的三种用法。判断标准：**这件事"必须和表操作原子绑定"吗？** 是，才用触发器。

| 场景 | 触发器类型 | 典型用途 |
|---|---|---|
| 自动补全字段（时间戳、业务编码）| `BEFORE INSERT` | 减少应用层遗漏 |
| 写审计日志 | `AFTER INSERT/UPDATE/DELETE` | 记录谁在什么时候改了什么 |
| 级联清理关联数据 | `AFTER DELETE` | 替代外键级联（或补充）|

### 案例一：INSERT —— 自动生成编号

```sql
CREATE TRIGGER trg_order_no
BEFORE INSERT ON `order`
FOR EACH ROW
BEGIN
  IF NEW.order_no IS NULL OR NEW.order_no = '' THEN
    SET NEW.order_no = CONCAT('ORD', DATE_FORMAT(NOW(),'%Y%m%d'), LPAD(NEW.id, 6, '0'));
  END IF;
END;
```

注意这里有个坑：`BEFORE INSERT` 时自增 `id` **还没生成**（值是 0），所以拼不出带 id 的编号。正确做法是 `AFTER INSERT` 里 `UPDATE` 回填，或者干脆用 UUID/雪花在应用层生成。**这个细节课程演示里容易忽略，实际做的时候会卡住。**

### 案例二：UPDATE —— 审计日志

```sql
CREATE TRIGGER trg_emp_audit
AFTER UPDATE ON emp
FOR EACH ROW
BEGIN
  INSERT INTO emp_audit (emp_id, old_salary, new_salary, changed_at)
  VALUES (OLD.id, OLD.salary, NEW.salary, NOW());
END;
```

这是触发器**最站得住的用途**：审计必须"不漏、不依赖应用代码"。应用层写日志，一旦有人绕过应用直接改库就漏了。

但要付代价：每次 `UPDATE` 多一次 `INSERT`，批量更新 100 万行 = 多 100 万次写入。所以审计表要单独放、定期归档。

### 案例三：DELETE —— 清理关联数据

```sql
CREATE TRIGGER trg_dept_delete
AFTER DELETE ON dept
FOR EACH ROW
BEGIN
  DELETE FROM emp WHERE dept_id = OLD.id;   -- 手动实现级联
END;
```

这个案例**通常是反面教材**：如果本来就有外键 `ON DELETE CASCADE`，触发器是重复劳动；如果没有外键（逻辑外键方案），那这里删子表可能删掉不该删的数据。

**更好的做法**：删除用"软删除"（`is_deleted` 标记），而不是物理删除 + 触发器清理。

### 一条必须记住的限制

**触发器里不能对"正在被触发的表"做 `INSERT/UPDATE/DELETE`**：

```sql
-- 报错 1442: Can't update table 'emp' in stored function/trigger
CREATE TRIGGER trg_x AFTER INSERT ON emp FOR EACH ROW
BEGIN UPDATE emp SET ...; END;
```

这是防递归的保护。要改本表数据只能用 `BEFORE` 触发器改 `NEW.列`。

和 EF Core 的关系：三个案例里，**只有"审计日志"值得在 EF Core 项目里用触发器**。另两个都能在应用层做得更清楚：

```csharp
// 时间戳：EF Core 的 SaveChanges 拦截器 / 值生成器
modelBuilder.Entity<Order>().Property(o => o.CreatedAt).HasDefaultValueSql("CURRENT_TIMESTAMP");
```

==二：使用格式==

```sql
CREATE TRIGGER 名 {BEFORE|AFTER} {INSERT|UPDATE|DELETE} ON 表 FOR EACH ROW BEGIN ... END;
DROP TRIGGER [IF EXISTS] 名;
SHOW TRIGGERS;
SELECT * FROM information_schema.triggers WHERE trigger_schema = 'demo';
```

==三：代码实践==

```sql
-- 完整的审计表 + 触发器
CREATE TABLE emp_audit (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  emp_id INT, old_salary DECIMAL(10,2), new_salary DECIMAL(10,2),
  changed_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

DELIMITER $$
CREATE TRIGGER trg_emp_audit AFTER UPDATE ON emp FOR EACH ROW
BEGIN
  IF OLD.salary <> NEW.salary THEN        -- 只记薪资变化，避免噪音
    INSERT INTO emp_audit (emp_id, old_salary, new_salary)
    VALUES (OLD.id, OLD.salary, NEW.salary);
  END IF;
END $$
DELIMITER ;

UPDATE emp SET salary = 9999 WHERE id = 1;
SELECT * FROM emp_audit;   -- 多了一条记录
```

==四：总结归纳==

- 三条：审计日志是触发器最合理的用途；触发器不能操作本表；`BEFORE INSERT` 时自增 id 还没生成。
- 记忆锚：触发器只做"必须原子绑定、不能漏"的事，其余一律放应用层。
- 自测：① 为什么 `AFTER DELETE` 触发器里删子表可能是坏设计？② 触发器能 `UPDATE` 自己所在的表吗？

# 主键优化

> 来源：P90《33. 进阶-SQL优化-主键优化》 · 档位 C 全新
> 与我已知的关系：EF Core 里"用 `Guid.NewGuid()` 当主键"这个再自然不过的写法，在 InnoDB 里是要付代价的

==一：意义与概念==

主键在 InnoDB 里不是"一个约束"，是**整张表的物理组织方式**（11-04 的聚簇索引）。所以主键的设计直接决定写入性能。

### 三条硬结论

**1. 主键尽量短**

二级索引的叶子存"索引列 + 主键"。主键从 `INT`(4B) 变成 `CHAR(36)`(UUID 文本)，**每个二级索引都多 32 字节/行**。一张 1000 万行、5 个二级索引的表，多占约 1.5GB。

同时对聚簇索引本身：key 越短，每页能放的目录项越多，树越矮。

**2. 主键尽量顺序插入（单调递增）**

B+ 树叶子页按主键排序。**递增主键**永远追加在最右页，满了就新开一页——顺序写。
**随机主键**（UUID、雪花 ID 里带随机位的）会落在中间任意页，该页满了就**页分裂**：拆成两页各占 50%，并搬运一半数据。

后果：表文件碎片化、写入变慢、缓存命中率下降。这就是为什么 MySQL 官方推荐自增主键。

**3. 尽量降低主键长度带来的"页分裂"与"随机 IO"**

具体机制（课程会画图）：一个 16KB 页存满后插入中间值 → 申请新页 → 把原页一半数据挪过去 → 调整链表指针。这个过程是**同步的、要写 redo log 的**，非常贵。

### 那 UUID 怎么办？

如果你的分布式系统必须用 UUID，三种缓解方案：

| 方案 | 做法 | 效果 |
|---|---|---|
| 用有序 UUID | `UUID_TO_BIN(UUID(), 1)`（时间高位前置）| 近似递增，页分裂大幅减少 |
| 用 `BINARY(16)` | 存成 16 字节而非 36 字符 | 省空间（索引小一半）|
| 业务自增 + 分片 | 雪花 ID（时间戳 + 机器号 + 序列）| 全局唯一且趋势递增 |

`UUID_TO_BIN(uuid, 1)` 的 `1` 表示"把时间部分换到高位"，这是 MySQL 8.0 提供的、专为"UUID 当主键"设计的函数。**这个细节在 EF Core 项目里很有用**：可以用值转换器 `HasConversion` 把 `Guid` 存成 `BINARY(16)`。

和 EF Core 的关系（这是本篇最实用的一段）：

```csharp
// 默认：Guid 主键会存成 char(36)，随机分布 → 页分裂
public Guid Id { get; set; } = Guid.NewGuid();

// 优化 1：值转换器，存 BINARY(16)
modelBuilder.Entity<Order>()
    .Property(o => o.Id)
    .HasConversion(
        v => v.ToByteArray(),
        v => new Guid(v))
    .HasColumnType("binary(16)");

// 优化 2：改用自增主键（单库单表最省心）
public long Id { get; set; }   // EF Core 自动识别为自增
```

另外提醒：**EF Core 里 `int` 自增主键 + 高并发插入**是没问题的，自增锁在 8.0 已改为"轻量互斥"（`innodb_autoinc_lock_mode=2`），不会成为瓶颈。

==二：使用格式==

```sql
CREATE TABLE t (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,   -- 推荐：短 + 递增
  ...
);

-- UUID 方案的写法
CREATE TABLE t (
  id BINARY(16) PRIMARY KEY,                        -- 16 字节
  ...
);
INSERT INTO t (id) VALUES (UUID_TO_BIN(UUID(), 1)); -- 时间高位前置
```

==三：代码实践==

```sql
-- 观察页分裂的迹象（表文件远大于数据量）
SELECT table_name,
       ROUND(data_length/1024/1024, 2) AS data_mb,
       ROUND(index_length/1024/1024, 1) AS index_mb
FROM information_schema.tables
WHERE table_schema='demo';
```

==四：总结归纳==

- 三条：主键要短（二级索引都带它）；主键要递增（避免页分裂）；必须用 UUID 就用 `UUID_TO_BIN(uuid,1)` + `binary(16)`。
- 记忆锚：自增主键是"往书末页持续追加"，UUID 是"随机插到书中间"——后者每次都要重排。
- 自测：① 页分裂为什么拖慢写入？② 主键长度为什么会放大所有二级索引？

# 插入数据优化

> 来源：P89《32. 进阶-SQL优化-插入数据》 · 档位 C 全新
> 与我已知的关系：EF Core 的 `AddRange` + `SaveChanges` 背后就是这里的批量插入问题——**默认行为可能是一条一条发**

==一：意义与概念==

痛点：导入 100 万行数据，一条一条 `INSERT` 跑了 40 分钟。因为每条 `INSERT` 都是一个独立事务 = 一次磁盘刷 + 一次日志写。

三个层次的优化，效果依次递增：

### 1. 批量插入（一条 SQL 多个 VALUES）

```sql
-- 差：100 万次网络往返 + 100 万次事务
INSERT INTO t VALUES (1,'a');
INSERT INTO t VALUES (2,'b');

-- 好：一条语句插多行
INSERT INTO t VALUES (1,'a'), (2,'b'), (3,'c');
```

**但别无限加**：一条 SQL 太长会撞 `max_allowed_packet`（默认 64MB），而且解析开销大。经验值 **500~1000 行一批**。

### 2. 手动事务（把多条插入包成一个事务）

```sql
START TRANSACTION;
INSERT INTO t VALUES (1,'a');
INSERT INTO t VALUES (2,'b');
...
COMMIT;
```

为什么快：InnoDB 默认 `autocommit=1`，每条 `INSERT` 都 `COMMIT` 一次 = 一次 redo log 刷盘（`innodb_flush_log_at_trx_commit=1` 时）。包成一个事务，只有最后一次刷盘。

**这是三条里最容易拿到最大收益的一条**：100 万行 → 从 100 万次提交变成 1 次。

### 3. 顺序插入（按主键顺序）

```sql
-- 主键递增，插入只追加到 B+ 树最右页
INSERT INTO t VALUES (1,'a'),(2,'b'),(3,'c');

-- 主键乱序（如 UUID），每次插入都可能落在中间页 → 页分裂
```

页分裂的代价：B+ 树一个页满了要拆成两页，并把一半数据搬过去。乱序插入会让分裂频繁发生，表文件膨胀、写入变慢。**这就是"主键要单调递增"的物理原因**（12-02 展开）。

### 额外的两个开关（大批量导入时才用）

```sql
SET UNIQUE_CHECKS = 0;        -- 关闭唯一性校验（导入完记得改回 1）
SET FOREIGN_KEY_CHECKS = 0;   -- 关闭外键校验
-- 导入完
SET UNIQUE_CHECKS = 1;
SET FOREIGN_KEY_CHECKS = 1;
```

**风险**：关掉校验期间插入的脏数据不会被发现。只在"数据源可信 + 导入后要人工核对"时用。

和 EF Core 的关系（这一段很实用）：

```csharp
// EF Core 默认：每条 INSERT 一条 SQL（7.0 之前），或按批合并（7.0+ 有优化但不保证）
db.AddRange(list);
db.SaveChanges();

// 明确控制批大小
db.AddRange(list);
db.ChangeTracker.AutoDetectChangesEnabled = false;   // 大集合时省 CPU
db.SaveChanges();

// 最快的方案：绕过 ORM，用批量库或原生 SQL
// EFCore.BulkExtensions / Pomelo 的 ExecuteSqlRaw 拼多值 INSERT
```

EF Core 7 起对 `SaveChanges` 做了批处理优化（`MaxBatchSize` 可配），但**批量导入仍然建议 `AutoDetectChangesEnabled = false` + 分批 `SaveChanges`**，否则变更追踪本身会吃掉大量 CPU。

==二：使用格式==

```sql
INSERT INTO t (a, b) VALUES (1,'x'), (2,'y'), ...;   -- 一批 500~1000 行
START TRANSACTION; ... COMMIT;                        -- 包事务
SET UNIQUE_CHECKS=0; SET FOREIGN_KEY_CHECKS=0;        -- 大批量导入时临时关
```

==三：代码实践==

```sql
-- 反例：1000 条独立插入
INSERT INTO log (msg) VALUES ('m1');
INSERT INTO log (msg) VALUES ('m2');
-- ... 每句一次提交

-- 正例
START TRANSACTION;
INSERT INTO log (msg) VALUES ('m1'),('m2'),...,('m1000');
COMMIT;
```

==四：总结归纳==

- 三条：多值批量插入（500~1000 行/批）；用事务包住所有插入（减少提交次数，收益最大）；按主键顺序插入（避免页分裂）。
- 记忆锚：插入慢的三个原因——往返太多、提交太多、页分裂——对应三个开关。
- 自测：① 为什么"包一个事务"能让插入快很多？② 主键用 UUID 为什么拖慢插入？

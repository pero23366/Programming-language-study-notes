# 单列与联合索引、索引设计原则

> 来源：P86–P87《29–30. 进阶-索引-使用规则-单列&联合索引 / 设计原则》 · 档位 C 全新
> 与我已知的关系：这一篇是给你一套"建索引的决策流程"，而不是零散技巧——你以后在 EF Core 里配 `HasIndex` 就靠它

==一：意义与概念==

先回答一个具体问题：`WHERE name = ? AND age = ?`，该建两个单列索引还是一个联合索引 `(name, age)`？

**答案：联合索引更好。** 三个理由：

1. **一个联合索引能当多个索引用**（最左前缀）：`(name, age)` 能服务 `name`、`name+age` 两种查询。
2. **回表次数更少**：两列都在索引里，一次定位就筛掉大部分行。
3. **省空间**：两个单列索引 = 两棵树；一个联合索引 = 一棵树。

代价是**列顺序很重要**：`(name, age)` 服务不了 `age` 单查。所以顺序要按"谁更常用、谁选择性更高"排。

### 索引设计原则（八条，按重要性排）

| # | 原则 | 原因 |
|---|---|---|
| 1 | **高频查询、大表的 WHERE / ORDER BY / GROUP BY 列才建** | 小表全表扫比走索引快，索引是负担 |
| 2 | **选择性高的列优先**（区分度大）| 基数低（性别、状态）走索引不如全表扫 |
| 3 | **联合索引把等值列放前、范围列放后** | 范围条件会截断后续列（11-08）|
| 4 | **尽量做覆盖索引**，避免 `SELECT *` | 免回表（11-11）|
| 5 | **长字符串用前缀索引** | 控制索引体积（11-12）|
| 6 | **主键要短、要单调递增** | 主键短 → 所有二级索引都小；递增 → 插入只追加，不页分裂（12-02）|
| 7 | **控制索引数量**（一般单表 ≤ 5~6 个）| 每个索引都拖慢写入；太多会让优化器选错 |
| 8 | **避免冗余索引**：`(a)` 和 `(a, b)` 并存时，`(a)` 是冗余的 | `(a,b)` 已能服务 `a` |

第 8 条值得单独说：很多人给 `user_id` 建了索引，又给 `(user_id, created_at)` 建一个，其实前者纯属浪费——后者能服务前者。**判断冗余的方法：把索引按列顺序写成字符串，如果 A 是 B 的前缀，A 就是冗余的。**

和 EF Core 的关系，对应到 `OnModelCreating` 里的决策流程：

```csharp
// 1. 这个查询高频吗？表大吗？→ 是，才加索引
// 2. 等值列在前，范围/排序列在后
modelBuilder.Entity<Order>()
    .HasIndex(o => new { o.UserId, o.Status, o.CreatedAt })
    .HasDatabaseName("idx_order_user_status_time");

// 3. 冗余检查：如果已有 (UserId, Status, CreatedAt)，就不要再建 (UserId)
```

EF Core 的 `.HasIndex()` 不会帮你判断"该不该建"。它只负责生成 DDL。**索引设计是数据库层面的决策，ORM 只是执行者** —— 这是本篇最该带走的一句话。

=== 关于"单列 vs 联合"的一个反例

```sql
-- 建了两个单列索引
CREATE INDEX idx_name ON emp(name);
CREATE INDEX idx_age  ON emp(age);

-- 这条查询：优化器只能选一个索引（name 或 age），另一个条件在回表后过滤
SELECT * FROM emp WHERE name = '张三' AND age = 25;
-- 走 idx_name，找到张三的所有行（可能 100 行），回表 100 次，再筛 age=25
```

如果换成 `(name, age)` 联合索引：索引内就同时按两列定位，回表可能只有 1 次。**这就是"联合索引优于多个单列索引"的量化解释。**

但反过来，如果两个查询分别是 `WHERE name=?` 和 `WHERE age=?`，且都高频，那建 `(name, age)` 就只能服务前者。这时要么建两个单列索引，要么建 `(name, age)` + `(age)`。**没有万能解，取决于查询模式** —— 所以第一步永远是"列出高频查询"。

==二：使用格式==

```sql
SHOW INDEX FROM 表名;     -- 看现有索引：列顺序、Cardinality（基数）
```

`Cardinality` 是索引列的不重复值估算数。**基数 / 总行数 = 选择性**，越接近 1 越好。它是估算值（`ANALYZE TABLE` 可刷新），但足以判断"这列值不值得建索引"。

==三：代码实践==

```sql
-- 冗余索引检查：手写对比
SHOW INDEX FROM `order`;
-- 若有 idx_a(user_id) 和 idx_b(user_id, created_at) → idx_a 冗余，删掉
DROP INDEX idx_a ON `order`;

-- 设计一个订单列表页的索引
-- 查询：WHERE user_id=? AND status=? ORDER BY created_at DESC LIMIT 20
CREATE INDEX idx_order_list ON `order` (user_id, status, created_at);
-- 等值列在前（user_id, status），排序列在后（created_at）
-- 这条查询：索引定位 + 索引内已按 created_at 有序 → 无 filesort、无回表（若只取这三列）
```

==四：总结归纳==

- 三条：优先联合索引（一个顶多个、少回表）；等值列在前范围列在后；主键短且递增，索引数量控制在 5~6 个内。
- 记忆锚：索引设计不是"给字段加索引"，是"为查询模式定制数据结构"——先列查询，再定索引。
- 自测：① 已有 `(a,b)`，还需要 `(a)` 吗？② 为什么 `WHERE user_id=? AND status=?` 用两个单列索引不如一个联合索引？

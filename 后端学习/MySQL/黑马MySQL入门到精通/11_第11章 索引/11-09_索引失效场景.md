# 索引失效场景

> 来源：P81–P82《24–25. 进阶-索引-使用规则-索引失效情况一 / 二》 · 档位 C 全新
> 与我已知的关系：EF Core 里"写得很自然的 LINQ"最可能触发的就是这几条——尤其是 `ToLower()` 和 `Contains()`

==一：意义与概念==

"索引失效"不是索引坏了，是**优化器认为用索引不划算，或者根本用不了**。八种情况，按真实踩坑频率排序：

### 1. 在索引列上做函数/运算（最常见的坑）

```sql
-- 失效：索引存的是 name 原值，LOWER(name) 是计算后的值，没有索引
SELECT * FROM emp WHERE LOWER(name) = 'zhangsan';
-- 改写：把函数移到值上（保持列"裸着"）
SELECT * FROM emp WHERE name = 'zhangsan';   -- 或者用不区分大小写的排序规则

-- 失效：列参与运算
SELECT * FROM emp WHERE id + 1 = 100;
-- 改写
SELECT * FROM emp WHERE id = 99;
```

EF Core 对应：`.Where(x => x.Name.ToLower() == "abc")` 会生成 `LOWER(Name)='abc'`，直接废掉索引。更隐蔽的是 `.Where(x => x.CreatedAt.Date == today)` → `DATE(CreatedAt)=...`，同样废掉。

### 2. 字符串不加引号（类型隐式转换）

```sql
-- phone 是 varchar，索引失效（MySQL 会把字符串列转成数字比较）
SELECT * FROM emp WHERE phone = 13800138000;
-- 正确
SELECT * FROM emp WHERE phone = '13800138000';
```

为什么：`varchar` 与数字比较时，MySQL 把**列**转成数字（而不是把常量转成字符串），列一变，索引就废了。传参时类型没对上，是 .NET 侧最常见的诱因（`MySqlParameter` 类型设错）。

### 3. 模糊查询以 `%` 开头

```sql
LIKE '张%'    -- ✅ 能走索引（前缀确定）
LIKE '%张'    -- ❌ 全表扫
LIKE '%张%'   -- ❌ 全表扫
```

EF Core 对应：`.Where(x => x.Name.Contains("张"))` 生成 `LIKE '%张%'`，索引必废；`.StartsWith("张")` 生成 `LIKE '张%'`，索引有效。**这是 EF Core 里性能差别最大的两个写法，长得几乎一样。**

### 4. `OR` 连接的列有一边没索引

```sql
-- id 有索引，name 没索引 → 整体全表扫
SELECT * FROM emp WHERE id = 1 OR name = '张三';
```

原理：`OR` 要求两边都能走索引，否则只能全表扫一遍再筛。修法：给 `name` 也建索引，或拆成 `UNION`。

### 5. 联合索引不满足最左前缀

见 11-08。`WHERE b=1` 在 `(a,b)` 索引上必失效。

### 6. 范围条件截断后续列

`WHERE a=1 AND b>10 AND c=2` 在 `(a,b,c)` 上只用得上 `a,b`。

### 7. 数据分布导致优化器主动放弃索引（最反直觉）

```sql
-- status 只有 0/1 两个值，各占 50%
SELECT * FROM emp WHERE status = 1;
```

即使 `status` 有索引，优化器算完会认为"回表 50 万次比全表扫还慢"，于是 `type=ALL`。**这不是失效，是成本决策。**

判断依据是 `filtered` 和 `rows`：如果索引列的基数（`SHOW INDEX` 里的 `Cardinality`）很低，索引价值就低。所以"给性别、状态位建单列索引"往往没用——**要么放进联合索引做覆盖，要么不建**。

### 8. `IS NULL` / `IS NOT NULL` 与 `!=`

- `IS NULL` 在索引列上**可以**走索引（InnoDB 索引存 NULL）。
- `!=` / `NOT IN` / `NOT LIKE` 通常导致范围扫描或全表扫，因为"不等于"要检查的行太多。

和 EF Core 的关系总结成一句：**LINQ 里任何"对列做变换"的写法都会废掉索引**——`ToLower()`、`.Date`、`.ToString()`、`.Contains()`、`+` 运算。这些在 C# 里读起来最自然，在 SQL 里最贵。

==二：使用格式==

没有语法，只有检查清单。排查顺序：

1. `EXPLAIN` 看 `type` 是否 `ALL`、`key` 是否 `NULL`
2. 看 `filtered`（低 = 选择性差）
3. 检查 WHERE 里有没有函数、隐式转换、前置 `%`、`OR`

==三：代码实践==

```sql
CREATE INDEX idx_name ON emp(name);
CREATE INDEX idx_phone ON emp(phone);

-- 逐条验证
EXPLAIN SELECT * FROM emp WHERE LOWER(name)='a';        -- type=ALL
EXPLAIN SELECT * FROM emp WHERE name='a';               -- type=ref
EXPLAIN SELECT * FROM emp WHERE phone=13800138000;      -- type=ALL（隐式转换）
EXPLAIN SELECT * FROM emp WHERE phone='13800138000';    -- type=ref
EXPLAIN SELECT * FROM emp WHERE name LIKE '%a%';        -- type=ALL
EXPLAIN SELECT * FROM emp WHERE name LIKE 'a%';         -- type=range
```

==四：总结归纳==

- 三条：**列上做任何变换就失效**（函数/运算/隐式转换）；前置 `%` 与 `OR` 半边无索引也失效；低基数列优化器会主动放弃索引。
- 记忆锚：索引只认识"列的原始值"——你把列包进任何函数，它就不认识了。

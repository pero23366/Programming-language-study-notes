# 索引分类与聚簇索引

> 来源：P72–P73《15–16. 进阶-索引-分类 / 思考题》 · 档位 C 全新
> 与我已知的关系：这是全章的地基。EF Core 里 `HasKey()` 选的主键，实际决定了**整张表数据的物理排列顺序**

==一：意义与概念==

两个维度分类，别混：

**按逻辑功能分**（你平时说的"建个索引"）：

| 类型 | 说明 | 一个表能有几个 |
|---|---|---|
| 主键索引 | `PRIMARY KEY` | 1 个 |
| 唯一索引 | `UNIQUE`，允许多个 NULL | 多个 |
| 常规索引 | 普通 `INDEX` | 多个 |
| 全文索引 | `FULLTEXT`，倒排结构，分词 | 多个 |

**按物理存储分**（InnoDB 特有，这才是重点）：

| 类型 | 叶子节点存什么 | 数量 |
|---|---|---|
| **聚簇索引**（Clustered）| **整行数据** | **只能有 1 个** |
| **二级索引**（Secondary）| 索引列的值 + **主键值** | 多个 |

### 聚簇索引：InnoDB 的数据就是主键索引

这句话是本篇的核心：

> **InnoDB 的表，本身就是一棵以主键为 key 的 B+ 树，叶子节点直接存放整行记录。**
> 所以"主键索引"不是一个额外的结构，它就是表本身。

推论：

- 按主键查 = 沿着树走到叶子，**直接拿到整行**，1 次定位。
- 如果没有主键，InnoDB 会选：**第一个不含 NULL 的唯一索引** 当聚簇索引；如果连这个都没有，就**自动生成一个隐藏的 6 字节 `row_id`** 当聚簇索引（你查不到它）。
- 这就是"每张表必须有主键"的真正原因——不是规范要求，是**没有主键就得靠隐式 row_id，你失去了对数据物理顺序的控制**。

### 二级索引：叶子只存主键，查数据要"回表"

给 `name` 建索引后，这棵树的叶子长这样：

```
叶子项: ('张三', 1)  ('李四', 2)  ('王五', 3)
          值    主键
```

所以 `SELECT * FROM t WHERE name='张三'` 要两步：

1. 在 `name` 的二级索引树里找到 `'张三'`，拿到主键 `1`；
2. 拿主键 `1` 回到聚簇索引树里找整行 —— **这一步叫"回表"**。

```
二级索引树                 聚簇索引树（就是表）
  name → id                   id → 整行
  '张三' → 1  ────回表───→   1 → (1,'张三',25,...)
```

**回表是随机 IO**：`id=1, 5, 100, 3000...` 这些主键在聚簇索引里跳来跳去，每次都是一次新的磁盘寻道。所以：

- 查 1 行：2 次 IO（可接受）
- 查 10 万行：10 万次回表（灾难）

这直接导出第 11-11 篇的"覆盖索引"——**如果查询要的列全在二级索引里，就不用回表**。

和 EF Core 的关系，三条实用结论：

1. `.Find(id)` 走聚簇索引，最快；`.FirstOrDefault(x => x.Email == email)` 若 `Email` 有唯一索引，走二级索引 + 1 次回表。
2. **主键类型决定树的扇出**：`Guid` 主键 16 字节且无序 → 插入时页分裂频繁、树更高。这是"别用 Guid 当聚簇主键"的原因（EF Core 里常见 `Guid.NewGuid()` 主键，性能上不划算）。
3. **二级索引自动带上主键**：所以二级索引占的空间 = 索引列 + 主键大小。主键越长，所有二级索引都跟着变大。这是"主键要短"的第二条理由。

常见误解：以为"给主键再加一个索引能更快"。主键已经是聚簇索引，再建一个普通索引只会多一棵冗余的树。

==二：使用格式==

```sql
-- 无主键表：InnoDB 会自动造 row_id，你看不到
CREATE TABLE no_pk (a INT, b INT);

-- 显式指定聚簇索引（唯一且非空，但不用 PRIMARY KEY 写法）
-- 不推荐，正常就用 PRIMARY KEY
```

==四：总结归纳==

- 三条：聚簇索引 = 表本身（叶子存整行，全表仅 1 个）；二级索引叶子存"列值 + 主键"，查数据要回表；没有主键会用隐藏 `row_id`。
- 记忆锚：聚簇索引是"正文按主键排好序的书"，二级索引是"按人名编的索引页，每条只写页码（主键）"。

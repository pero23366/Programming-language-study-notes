# Hash 索引与引擎选型

> 来源：P70–P71《13–14. 进阶-索引-结构-hash / 思考题》 · 档位 C 全新
> 与我已知的关系：这就是 `Dictionary<K,V>` 的磁盘版本——O(1) 等值查找，但完全不支持范围

==一：意义与概念==

Hash 索引用哈希表：对索引列算 hash 值，直接定位桶。**等值查询 O(1)**，一次 IO 就够。

但它的限制几乎让它没法用在业务表上：

| 能力 | Hash 索引 | B+ 树 |
|---|---|---|
| `=` / `IN` 等值查 | ✅ O(1)，极快 | ✅ O(log n) |
| 范围查 `>` `<` `BETWEEN` | ❌ 完全不支持 | ✅ |
| `ORDER BY` 利用索引排序 | ❌ | ✅ |
| 最左前缀（联合索引） | ❌ 必须用全部列 | ✅ |
| 模糊查 `LIKE 'x%'` | ❌ | ✅ |
| 哈希冲突 | 有，冲突多则退化 | 无 |

**关键事实**：InnoDB **不支持用户手动建 Hash 索引**（`USING HASH` 会被忽略或报错）。InnoDB 只在内部用"自适应哈希索引"（AHI）——它自己观察哪些索引被频繁等值查询，自动在内存里建 hash 加速，你管不着也不用管。

真正用 Hash 索引的是 **Memory 引擎**（默认就是 Hash），所以 Memory 表只适合"按 key 精确取"的场景。

### 课程里的思考题（三个常被问的问题）

1. **为什么 InnoDB 选择 B+ 树而不是 Hash？** 因为业务查询 90% 带范围或排序（时间区间、分页、`ORDER BY id`），Hash 一个都做不了。
2. **为什么不用二叉树/红黑树？** 树太高，磁盘 IO 太多。
3. **为什么不用 B 树？** 非叶子节点存数据导致扇出小、树高、范围查要中序遍历。

和 EF Core 的关系：你不用操心 Hash。但要记住一个推论——**如果你在 EF Core 里写 `.Where(x => x.Status == 1)`，而这个列基数极低（只有几个值），B+ 树索引反而不划算**：优化器算完发现"走索引要回表 100 万次，不如直接全表扫"，于是放弃索引。这不是索引失效的 bug，是成本决策。第 11-09 篇会讲这个"数据分布影响索引选择"。

==二：使用格式==

```sql
-- InnoDB：写了 USING HASH 也不会真的建 Hash 索引
CREATE INDEX idx ON t(col) USING HASH;   -- 实际仍是 B+ 树（8.0 会忽略）

-- Memory 表：默认 Hash
CREATE TABLE cache (k VARCHAR(32) PRIMARY KEY, v VARCHAR(64)) ENGINE=MEMORY;
```

==四：总结归纳==

- 三条：Hash 只支持等值查；InnoDB 不支持手动 Hash 索引，只有内部 AHI；Memory 引擎默认 Hash。
- 记忆锚：Hash 是 `Dictionary`——按键取极快，但你不能"取出所有 key 大于 10 的项"。
- 自测：① 为什么 InnoDB 不用 Hash 索引？② Memory 表上 `WHERE k > 'a'` 能走索引吗？

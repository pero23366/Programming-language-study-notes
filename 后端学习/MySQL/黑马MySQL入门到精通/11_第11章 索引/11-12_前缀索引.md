# 前缀索引

> 来源：P85《28. 进阶-索引-使用规则-前缀索引》 · 档位 C 全新
> 与我已知的关系：这是"长字符串不敢建索引"的解药，EF Core 里没有直接对应能力，必须写原生 SQL 或迁移脚本

==一：意义与概念==

痛点：`VARCHAR(255)` 的 URL、邮箱、文章标题建索引，索引树会非常大——每页能放的 key 少、树高、占磁盘、写入慢。

**前缀索引**：只索引**前 n 个字符**，不索引整列。

```sql
CREATE INDEX idx_url ON article(url(20));   -- 只索引 url 的前 20 个字符
```

省了多少：`url(20)` 相比 `url` 全长，索引项从平均 100 字节降到 20 字节，索引体积缩到 1/5，树高可能降一层。

**代价：区分度下降**。"前 20 个字符相同"的行会挤在同一个索引项后面，`WHERE url = '完整URL'` 时先按前缀定位，再回表逐行比对完整值。所以：

- 前 n 个字符重复度高 → 索引基本没用，可能退化成大量回表
- 前 n 个字符几乎唯一 → 效果接近全列索引

### 怎么选 n：用"前缀选择性"算

```sql
SELECT
  COUNT(DISTINCT LEFT(url, 10)) / COUNT(*) AS sel_10,
  COUNT(DISTINCT LEFT(url, 20)) / COUNT(*) AS sel_20,
  COUNT(DISTINCT LEFT(url, 30)) / COUNT(*) AS sel_30,
  COUNT(DISTINCT url) / COUNT(*)          AS sel_full
FROM article;
```

`sel_n` 越接近 `sel_full` 越好。经验阈值：**`sel_n ≥ 0.9 × sel_full` 就可以用这个 n**。课程演示里通常会看到"前缀 10 字符的选择性已经到 0.9x"这种结论。

三条限制（必须知道）：

1. **不能用于 `ORDER BY` 和 `GROUP BY`**：索引里只有前缀，无法按整值排序/分组。
2. **不能做覆盖索引**：索引里没有完整值，要完整值只能回表。
3. **`LIKE '%x'` 依然无效**：前缀索引只优化"值的左边"，不优化"模式的左边"。

和 EF Core 的关系：EF Core 的 `HasIndex` **不支持指定前缀长度**（没有 `HasPrefixLength` 这样的 API）。要建前缀索引只能：

- 在迁移里写 `migrationBuilder.Sql("CREATE INDEX idx_url ON article(url(20));")`
- 或者手工建，然后把该索引标记为 `HasAnnotation` 排除迁移管理

这也是一个很实际的信号：**ORM 抽象不了的数据库能力，往往正是性能关键点**。知道它有、知道何时该用，比"ORM 里能不能写"重要。

另外：如果这一列**必须唯一**，前缀索引不能建唯一索引（`UNIQUE` 会把前缀当唯一键，误判冲突）。这时要么用全列唯一索引，要么在应用层保证。

==二：使用格式==

```sql
CREATE INDEX idx_col ON 表名 (列名(n));     -- n 是字符数，不是字节
ALTER TABLE 表名 ADD INDEX idx_col (列名(n));
```

对 `TEXT` 类型**必须**指定前缀长度（否则报错 `BLOB/TEXT column used in key specification without a key length`）。

==三：代码实践==

```sql
-- 1. 先算选择性，选 n
SELECT COUNT(DISTINCT LEFT(email, 6)) / COUNT(*) AS sel_6,
       COUNT(DISTINCT LEFT(email, 12)) / COUNT(*) AS sel_12,
       COUNT(DISTINCT email) / COUNT(*) AS sel_full
FROM users;
-- 假设结果：0.72 / 0.98 / 0.99  → 选 12

-- 2. 建前缀索引
CREATE INDEX idx_email ON users(email(12));

-- 3. 验证：type=ref，Extra 为空（要回表比对完整值）
EXPLAIN SELECT * FROM users WHERE email = 'a@example.com';
```

反例：

```sql
CREATE INDEX idx_email ON users(email(3));   -- 前 3 字符几乎全是 'abc'/'xyz'，选择性极低
-- 大量行共享同一前缀，回表次数暴涨，比全表扫还慢
```

==四：总结归纳==

- 三条：`列名(n)` 只索引前 n 个字符，省空间但降低区分度；用 `COUNT(DISTINCT LEFT(...))/COUNT(*)` 选 n，接近全列选择性即可；前缀索引不能覆盖、不能排序、不能唯一。
- 记忆锚：前缀索引是"只记门牌号前几位"——找得快，但同一栋楼的还得挨个敲门。

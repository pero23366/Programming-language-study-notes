# 最左前缀法则

> 来源：P79–P80《22–23. 进阶-索引-使用规则-验证索引效率 / 最左前缀法则》 · 档位 C 全新
> 与我已知的关系：这是联合索引唯一必须理解的规则，也是 EF Core 里 `HasIndex(o => new { A, B, C })` 到底能撑住哪些查询的答案

==一：意义与概念==

痛点：你给 `(a, b, c)` 建了联合索引，结果 `WHERE b = 1` 没走索引。为什么？因为 B+ 树只按 `a` 排序，`b` 只在 `a` 相同的块内有序——**不知道 `a`，就找不到 `b` 从哪开始**。

**法则**：联合索引 `(a, b, c)` 的 B+ 树按 **a → b → c** 的优先级排序。查询条件必须**从最左列开始、连续命中**，才能用上索引。中间跳过任何一列，后面的列都用不上。

举个具体例子。索引按 `(a, b, c)` 排序后，数据顺序是这样：

```
(a=1,b=1,c=1) (a=1,b=1,c=2) (a=1,b=2,c=1) (a=1,b=2,c=2)
(a=2,b=1,c=1) (a=2,b=1,c=2) ...
```

看出来了：

- 给 `a=1`，能定位到连续一块 ✅
- 给 `a=1 AND b=2`，能定位到更小一块 ✅
- 只给 `b=2`，`b=2` 的行散落在整个索引里 ❌
- 给 `a=1 AND c=2`，`b` 跳过了 → 只能用 `a` 定位，`c` 用不上 ❌

命中矩阵（索引 `(a, b, c)`）：

| WHERE 条件 | 能用上几列 | 说明 |
|---|---|---|
| `a` | 1 | ✅ |
| `a, b` | 2 | ✅ |
| `a, b, c` | 3 | ✅ 全命中 |
| `a, c` | 1 | `b` 断了，`c` 用不上 |
| `b` | 0 | ❌ 全表扫 |
| `b, c` | 0 | ❌ |
| `c` | 0 | ❌ |
| `a` + `ORDER BY b` | 1（但排序免费）| ✅ 因为 `a` 相同块内 `b` 有序 |
| `a` + `ORDER BY c` | 1（排序要 filesort）| `b` 无序，`c` 也乱 |

**关键延伸（课程没讲但极重要）**：`WHERE` 里条件的**书写顺序不影响**，MySQL 优化器会自动重排成索引顺序。所以 `WHERE b=2 AND a=1` 和 `WHERE a=1 AND b=2` 等价，都能用上两列。真正决定命中数的是**"跳过了哪一列"**，不是"写在前还是后"。

还有一条常被误解的：**范围条件会截断后面的列**。`WHERE a=1 AND b>10 AND c=2` 里，`b` 用了范围，`c` 就用不上了（因为 `b>10` 范围内 `c` 不保证有序）。所以联合索引里**范围列要放最后**——这是设计原则的核心一条。

和 EF Core 的关系：`.HasIndex(o => new { o.UserId, o.Status, o.CreatedAt })` 这个索引能撑住：
- `.Where(o => o.UserId == 1)` ✅
- `.Where(o => o.UserId == 1 && o.Status == 2)` ✅
- `.Where(o => o.UserId == 1 && o.Status == 2).OrderBy(o => o.CreatedAt)` ✅（排序免了）

撑不住：
- `.Where(o => o.Status == 2)` ❌
- `.Where(o => o.UserId == 1).OrderBy(o => o.Status)` ⚠️ 能查，但要额外排序

=== 验证索引效率（P79 的做法）

用 `EXPLAIN` 对比加索引前后的 `type` 和 `rows`，或者用 `SHOW PROFILES` 看实际耗时。最直观的是 `key_len`：

`varchar(20) NOT NULL` 在 utf8mb4 下 = 20×4 + 2（长度字节）= 82；允许 NULL 再 +1 = 83。

所以 `key_len=83` 表示"只用了 1 列"，`166` 表示"用了 2 列"。**`key_len` 是判断联合索引命中了几列的唯一可靠手段**。

==二：使用格式==

```sql
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;   -- 看 key_len 判断命中列数
```

==三：代码实践==

```sql
CREATE INDEX idx_abc ON t(a, b, c);

EXPLAIN SELECT * FROM t WHERE a=1 AND b=2 AND c=3;   -- key_len = 3 列之和
EXPLAIN SELECT * FROM t WHERE a=1 AND c=3;           -- key_len = 1 列（b 断了）
EXPLAIN SELECT * FROM t WHERE b=2;                   -- type=ALL, key=NULL
```

==四：总结归纳==

- 三条：联合索引按列顺序排序，必须从左连续命中；条件书写顺序不影响，跳列才影响；范围列会截断后续列，应放最后。
- 记忆锚：联合索引像"字典按拼音+部首排序"——只给部首查不到，必须先知道拼音。
- 自测：① 索引 `(a,b,c)`，`WHERE a=1 AND c=3` 用了几列？② `WHERE a=1 AND b>5 AND c=3` 中 `c` 为什么用不上？

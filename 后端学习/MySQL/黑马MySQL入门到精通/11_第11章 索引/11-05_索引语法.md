# 索引语法

> 来源：P74《17. 进阶-索引-语法》 · 档位 B 部分重叠
> 与我已知的关系：`CREATE INDEX` 与 SQL Server 语法几乎一致，**但 MySQL 没有 `INCLUDE` 覆盖列，且索引名是表级唯一的**

==一：意义与概念==

建、查、删三类操作，骨架与 T-SQL 相同。三处差异：

1. **没有 `INCLUDE` 子句**：SQL Server 支持 `CREATE INDEX ... INCLUDE (col)` 把额外列挂在叶子节点上实现"覆盖索引"。MySQL 只能**把列加进联合索引**（`(a, b)` 里 b 天然在叶子节点上），所以联合索引承担了覆盖索引的职责。
2. **索引名在表内唯一**：不同表可以有同名索引（和 T-SQL 一样），但同一表内不能重名。
3. **`USING BTREE / HASH` 写在最后**：InnoDB 只认 BTREE，写 HASH 会被忽略。

建索引的两种时机：

- **建表时**：`CREATE TABLE` 里写 `INDEX` / `UNIQUE` / `FULLTEXT`。
- **建表后**：`CREATE INDEX` 或 `ALTER TABLE ... ADD INDEX`。

**生产注意**：大表加索引会重建索引树并**锁表**（8.0 的 Online DDL 支持 `ALGORITHM=INPLACE, LOCK=NONE`，多数加索引场景可以不锁写）。千万行的表直接 `CREATE INDEX` 可能卡住业务，要用在线工具。

和 EF Core 的关系：`modelBuilder.Entity<Order>().HasIndex(o => new { o.UserId, o.CreatedAt })` 生成的就是 `CREATE INDEX ... (UserId, CreatedAt)`。**注意 EF Core 默认索引名是 `IX_表名_列名`**，如果手工建过索引又跑迁移，可能撞名冲突。生产上建议显式 `.HasDatabaseName("idx_order_user_created")`。

==二：使用格式==

```sql
-- 建表时
CREATE TABLE t (
  id INT PRIMARY KEY,
  name VARCHAR(20),
  email VARCHAR(50),
  content TEXT,
  INDEX idx_name (name),
  UNIQUE INDEX uk_email (email),
  FULLTEXT INDEX ft_content (content)
);

-- 建表后
CREATE [UNIQUE|FULLTEXT] INDEX 索引名 ON 表名 (列1 [ASC|DESC], 列2 ...);
ALTER TABLE 表名 ADD [UNIQUE|FULLTEXT] INDEX 索引名 (列...);

-- 查看与删除
SHOW INDEX FROM 表名;
DROP INDEX 索引名 ON 表名;
```

| 参数 | 说明 |
|---|---|
| `UNIQUE` | 值唯一，允许多个 NULL |
| `FULLTEXT` | 全文索引，需分词，只对 char/varchar/text |
| `(a, b)` | 联合索引，**顺序有意义**（最左前缀）|
| `ASC/DESC` | 8.0 才真正支持降序索引；8.0 之前写 DESC 被忽略 |

==三：代码实践==

```sql
-- 联合索引：注意列顺序，它决定能命中哪些查询
CREATE INDEX idx_user_status_time ON `order` (user_id, status, created_at);

-- 能用上（命中前两列/前三列）
-- WHERE user_id=1
-- WHERE user_id=1 AND status=2
-- WHERE user_id=1 AND status=2 AND created_at>'2026-01-01'

-- 用不上（跳过了最左列 user_id）
-- WHERE status=2
-- WHERE created_at>'2026-01-01'
```

==四：总结归纳==

- 三条：没有 `INCLUDE`，覆盖靠联合索引；索引名表内唯一；大表加索引注意锁表。
- 记忆锚：MySQL 的联合索引 = SQL Server 的联合索引 + `INCLUDE` 的合体。

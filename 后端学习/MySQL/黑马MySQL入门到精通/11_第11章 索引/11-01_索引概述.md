# 索引概述

> 来源：P66《09. 进阶-索引-概述》 · 档位 B 部分重叠
> 与我已知的关系：`HasIndex()` 你在 EF Core 里写过，但那时你只知道"加了会快"——这一章要把它拆到底

==一：意义与概念==

痛点：1000 万行的表，`WHERE id = 5000000` 如果要一行行比，得扫 500 万次。索引就是给这张表建一本"目录"，让你直接翻到那一页。

**定义**：索引是**有序的、独立存储的数据结构**，保存"某个列的值 → 该行物理位置"的映射。MySQL 的索引由引擎实现，InnoDB 用 B+ 树。

索引不是免费的，官方说法是"索引是帮助 MySQL 高效获取数据的数据结构"，但实际是**空间 + 写入性能换查询性能**：

| 代价 | 具体表现 |
|---|---|
| 占磁盘 | 每个二级索引都是一棵独立的 B+ 树，存一份列值 + 主键 |
| 拖慢写入 | 每 `INSERT` 一行，所有索引树都要插入并可能分裂页 |
| 拖慢更新 | 更新被索引的列 = 删旧索引项 + 插新索引项 |
| 优化器负担 | 索引太多，优化器可能选错（选错比没有更慢） |

所以"给每个查询列都加索引"是错的。正确做法是**按查询模式建索引**，这也是第 11-13 篇（设计原则）和 12 章（SQL 优化）要解决的问题。

与你 EF Core 经验的连接：`.HasIndex(e => e.Email).IsUnique()` 这类配置最终落成的就是 MySQL 的 B+ 树索引。EF Core 里的 `Where()` 会不会走索引，**不取决于 LINQ 写得多优雅，而取决于生成的 SQL 的 WHERE 条件是否命中了索引的最左前缀**。这是本章最有实用价值的一句话。

常见误解：以为"主键索引"和"普通索引"是两种东西。InnoDB 里主键索引是**聚簇索引**（叶子节点直接存整行数据），普通索引是**二级索引**（叶子存主键值），两者查一次数据要走的路不同——见 11-04。

==二：使用格式==

```sql
CREATE INDEX idx_name ON t(col);          -- 普通索引
CREATE UNIQUE INDEX uk_name ON t(col);    -- 唯一索引
CREATE INDEX idx_multi ON t(a, b);        -- 联合索引
SHOW INDEX FROM t;                        -- 查看
DROP INDEX idx_name ON t;
```

==四：总结归纳==

- 三条：索引是"列值 → 行位置"的有序结构；换来查询快、付出空间与写入代价；索引有效性取决于 WHERE 是否命中**最左前缀**。
- 记忆锚：索引是书的目录——目录本身也要占页数，而且每次改内容都得改目录。
- 自测：① 一张表加 8 个索引，`INSERT` 会变慢几倍？为什么？② 主键索引和普通索引的叶子节点分别存什么？

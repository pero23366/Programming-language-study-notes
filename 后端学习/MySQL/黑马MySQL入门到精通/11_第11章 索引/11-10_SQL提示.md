# SQL 提示（USE / FORCE / IGNORE INDEX）

> 来源：P83《26. 进阶-索引-使用规则-SQL提示》 · 档位 B 部分重叠
> 与我已知的关系：SQL Server 的 `WITH (INDEX(...))` 是同一类东西，但 MySQL 用独立子句写在表名后面

==一：意义与概念==

优化器偶尔会选错索引：明明有更好的索引却用了差的，或者该走索引却全表扫。SQL 提示（hint）就是**人工干预优化器的选择**。

三种，语义不同：

| 提示 | 含义 | 强度 |
|---|---|---|
| `USE INDEX(idx)` | **建议**用这个索引，优化器可以不听 | 弱 |
| `FORCE INDEX(idx)` | **强制**用这个索引（全表扫都比它快时也可能听）| 中 |
| `IGNORE INDEX(idx)` | **禁用**这个索引 | 中 |

**重要认知：hint 是最后手段，不是常规手段。** 一旦用了，索引改名/删除后 SQL 直接报错，而且数据分布变化后 hint 可能变成新的问题。正确顺序是：先改 SQL 写法（消除函数、调整条件）→ 再考虑改索引设计 → 最后才用 hint。

真实场景（hint 确实有用的时候）：

- 同一个字段有多个索引（一个单列、一个联合），优化器选了单列导致回表过多 → `FORCE INDEX(联合索引)`。
- 分页 `ORDER BY id LIMIT 100000, 10`，优化器选了错误的索引导致 filesort → `FORCE INDEX(PRIMARY)`。
- 测试环境要复现"线上走了某个索引"的行为。

和 EF Core 的关系：EF Core 的 LINQ **不直接支持 hint**。要写只能：

1. `${}` 拼接进 `FromSqlRaw`（有注入风险，必须参数化）
2. 用拦截器（`DbCommandInterceptor`）改写 SQL 文本
3. 改索引设计，让优化器自己选对（推荐）

这也说明一个事实：**用 ORM 时，索引设计比 hint 重要得多**——因为 hint 在 ORM 里很难优雅地表达。

==二：使用格式==

```sql
SELECT * FROM 表名 USE INDEX (索引名) WHERE ...;
SELECT * FROM 表名 FORCE INDEX (索引名) WHERE ...;
SELECT * FROM 表名 IGNORE INDEX (索引名) WHERE ...;

-- 针对 JOIN 中的某张表
SELECT * FROM t1 FORCE INDEX (idx_a) JOIN t2 ON ...;
```

==三：代码实践==

```sql
SHOW INDEX FROM emp;      -- 假设有 idx_name、idx_age、idx_name_age

-- 优化器可能只用 idx_name，回表很多
EXPLAIN SELECT * FROM emp WHERE name = '张三' ORDER BY age;

-- 强制用联合索引，name+age 都在索引里，减少回表
EXPLAIN SELECT * FROM emp FORCE INDEX (idx_name_age) WHERE name = '张三' ORDER BY age;

-- 禁用某个索引（常用于验证"是不是它拖慢了"）
EXPLAIN SELECT * FROM emp IGNORE INDEX (idx_name) WHERE name = '张三';
```

对照 T-SQL：

```sql
-- SQL Server 的写法，对比记忆
SELECT * FROM emp WITH (INDEX(idx_name)) WHERE name = '张三';
```

==四：总结归纳==

- 三条：`USE` 是建议、`FORCE` 是强制、`IGNORE` 是禁用；hint 是最后手段，改了索引要回来维护；ORM 里难表达，优先改索引设计。
- 记忆锚：hint 是"手动挡"，平时不该用，只有自动挡换错挡时才切。

# 索引结构：B 树与 B+ 树

> 来源：P67–P69, P71《10–12. 进阶-索引-结构-介绍 / Btree / B+tree / 思考题》 · 档位 C 全新
> 与我已知的关系：你熟悉的 `List` / `Dictionary` 是内存结构，这里要建立"磁盘上的树"这个新直觉——**每次节点访问是一次磁盘 IO**

==一：意义与概念==

先给核心问题：内存里查 1000 万个 `int` 用二分很快，但磁盘不行——**磁盘每次随机读要几毫秒，比内存慢 10 万倍**。所以索引结构的设计目标只有一个：**尽可能少的磁盘 IO 次数**。

### 二叉树为什么不行

普通二叉搜索树，1000 万个节点高度约 24 层 = 24 次磁盘 IO。太深。而且插入有序数据会退化成链表（高度 1000 万）。

### B 树（多路平衡查找树）

关键改动：**一个节点存多个 key、有多个子节点**（多路），并且所有叶子在同一层（平衡）。这样高度可以从 24 降到 3 左右。

一个 5 阶 B 树的节点长这样：

```
[ 17 | 35 ]                    ← 一个节点有 2 个 key、3 个子指针
  /    |    \
 <17  17~35  >35
```

B 树的特点：**每个节点既存 key 也存数据（value）**。

### B+ 树（MySQL 的选择）

B+ 树做了三个改动：

1. **非叶子节点只存 key，不存数据** → 一个 16KB 的页能塞更多 key → 树更矮（通常 2~4 层）
2. **所有数据都在叶子节点**，非叶子节点只是"指路牌"
3. **叶子节点之间用双向链表连接** → 范围查询极快

```
         [ 30 | 60 ]              ← 非叶子：只有 key，纯索引
        /     |     \
   [5,15]  [30,45]  [60,75]       ← 叶子：存数据（或主键），且横向串成链表
     ↔        ↔        ↔
```

**为什么是 B+ 树而不是 B 树**，四条理由，逐条对应 MySQL 的需求：

| 需求 | B+ 树的优势 |
|---|---|
| 单点查询要快 | 非叶子只存 key → 扇出更大 → 树高更低 → IO 更少 |
| 范围查询（`BETWEEN`、`>`、`ORDER BY`）| 叶子有链表，找到起点后顺序扫描，不用回上层 |
| 全表扫描（`COUNT(*)`）| 只遍历叶子层链表，不用遍历整棵树 |
| 排序输出 | 叶子本身有序，天然免排序 |

**树高与数据量的关系**（这张表要记住，面试常问）：

假设一个页 16KB，主键 `bigint`（8 字节）+ 指针（6 字节）= 14 字节，一个非叶子页可放约 **1170 个 key**；叶子页假设一行 1KB，可放约 **16 行**。

- 高度 1（只有根，即叶子）：16 行
- 高度 2：1170 × 16 ≈ **1.8 万行**
- 高度 3：1170 × 1170 × 16 ≈ **2100 万行**
- 高度 4：约 **240 亿行**

所以**2000 万行的表，查一行只要 3 次磁盘 IO**。这就是 B+ 树的威力，也是"主键要短"的原因——主键越长，每页能放的 key 越少，树越高。

和 EF Core 的关系：EF Core 的 `Find(id)` 走主键，永远是 3 次 IO 左右；`.Where(x => x.Name == "张三")` 如果 `Name` 没索引，就是**全表扫描**（几百万次 IO）。这两者在 C# 代码里长得差不多，性能差三个数量级。所以"给查询字段加索引"这件事，EF Core 帮不了你，得你自己看 `EXPLAIN`。

常见误解：以为"B+ 树比 B 树新所以更好"。B 树在"单点查询且数据就在非叶子节点"时可能更快（少一层），但 MySQL 的场景（范围查、排序、全表扫）全都偏向 B+ 树。

==二：使用格式==

这一节是结构原理，没有 SQL 语法。要"看"结构：

```sql
SHOW INDEX FROM t;                  -- 看索引的列顺序、基数
EXPLAIN SELECT ... ;                -- 看优化器是否用了索引
```

==四：总结归纳==

- 三条：B+ 树非叶子只存 key → 树矮；叶子存数据且带链表 → 范围查/排序快；2000 万行只需 3 次 IO。
- 记忆锚：B+ 树是"一本每页都写了页码索引的书"——目录很薄（只有 key），正文（数据）都在最后，而且正文按顺序装订。

# 视图介绍与基本语法

> 来源：P97《40. 进阶-视图-介绍及基本语法》 · 档位 B 部分重叠
> 与我已知的关系：SQL Server 也有视图，概念一致；**差别在 MySQL 的视图不支持参数、性能和"是否合并"有关**

==一：意义与概念==

痛点：一张报表 SQL 有 40 行、连 6 张表，十个地方要用。复制十份 → 改一次要改十处。

**视图**：一条 SELECT 存起来的"命名查询"，用起来像表。

```sql
CREATE VIEW v_emp_dept AS
SELECT e.id, e.name, d.name AS dept_name
FROM emp e LEFT JOIN dept d ON e.dept_id = d.id;

-- 之后像表一样用
SELECT * FROM v_emp_dept WHERE dept_name = '销售部';
```

**关键认知：视图不存数据**（普通视图）。它只是一段 SQL，每次查询时展开执行。所以"视图能提速"是错的——**视图只省了书写，不省执行**。

对比 T-SQL 的差异，三条：

| 维度 | MySQL | T-SQL |
|---|---|---|
| 参数化 | ❌ 视图不能带参数 | ❌ 也不能（要参数得用表值函数）|
| 物化视图 | ❌ 不支持（8.0 也没有）| ✅ 有索引视图 |
| 算法 | 可选 `MERGE` / `TEMPTABLE` | 优化器自己决定 |

`ALGORITHM` 是 MySQL 特有：

| 算法 | 行为 | 何时用 |
|---|---|---|
| `MERGE`（默认）| 把视图的 SQL **合并**进外层查询，等价于直接写 JOIN | 简单视图，性能最好 |
| `TEMPTABLE` | 先把视图结果放进临时表，再查临时表 | 视图含 `GROUP BY`/`DISTINCT`/`UNION`/聚合时自动使用 |

`TEMPTABLE` 的代价：每次查视图都建临时表，数据量大时很慢。所以**视图里放聚合函数要小心**。

### 视图的真实用途（不是"简化查询"这么简单）

1. **权限隔离**：只给用户视图权限，不给他基表权限 → 他看不到敏感列（如 `salary`）。
2. **屏蔽表结构变更**：底层表改名/拆表，改视图即可，应用代码不动。
3. **统一口径**：多个系统共用同一份"有效订单"定义，避免各处 SQL 不一致。

和 EF Core 的关系：EF Core **可以映射视图**：

```csharp
modelBuilder.Entity<EmpDeptView>().HasNoKey().ToView("v_emp_dept");
```

`HasNoKey()` 是必须的（视图没有主键）。但注意：**映射成 `HasNoKey` 的实体不能 `SaveChanges`**，是只读的。要做可写视图得满足 13-04 的条件。

==二：使用格式==

```sql
CREATE [OR REPLACE] [ALGORITHM = {MERGE|TEMPTABLE|UNDEFINED}]
VIEW 视图名 [(列别名...)] AS SELECT ...;

ALTER VIEW 视图名 AS SELECT ...;     -- 修改
DROP VIEW [IF EXISTS] 视图名;
SHOW CREATE VIEW 视图名;
```

==三：代码实践==

```sql
-- 创建时重命名列（视图列名默认取 SELECT 的别名）
CREATE OR REPLACE VIEW v_dept_stat (部门, 人数, 平均薪资) AS
SELECT d.name, COUNT(*), AVG(e.salary)
FROM dept d LEFT JOIN emp e ON d.id = e.dept_id
GROUP BY d.name;

SELECT * FROM v_dept_stat WHERE 人数 > 3;
```

==四：总结归纳==

- 三条：视图是"存起来的 SELECT"，不存数据、不提速；`MERGE` 合并执行、`TEMPTABLE` 建临时表；视图的真正价值是权限隔离与口径统一。
- 记忆锚：视图是"给一段 SQL 起了个名字"，不是"缓存了一份结果"。

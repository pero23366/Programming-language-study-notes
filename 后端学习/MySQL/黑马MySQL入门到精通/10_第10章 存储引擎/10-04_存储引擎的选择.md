# 存储引擎的选择

> 来源：P63《06. 进阶-存储引擎-选择》 · 档位 B 部分重叠
> 与我已知的关系：结论对你几乎没有决策成本——默认用 InnoDB 就对了，这一篇的价值是给"为什么"一个答案

==一：意义与概念==

选型原则一句话：**没有特殊理由就 InnoDB，有特殊理由再单独论证。**

| 场景 | 选择 | 理由 |
|---|---|---|
| 绝大多数业务表 | **InnoDB** | 事务、行锁、外键、崩溃恢复 |
| 只读的日志归档、统计报表 | InnoDB 也行 | MyISAM 的 `COUNT(*)` 优势抵不过维护成本 |
| 会话级临时中间表 | **Memory** | 数据可重建、追求极致速度 |
| 需要全文检索且不想上 ES | InnoDB 的全文索引 | MyISAM 全文索引已无优势 |
| 历史遗留 MyISAM 表 | 逐步迁到 InnoDB | 见下 |

**迁移老表的注意点**：`ALTER TABLE t ENGINE=InnoDB` 会重建整张表——**锁表、耗磁盘、可能耗时几小时**。生产上要走在线 DDL 工具（pt-online-schema-change / gh-ost），或者在从库上改完再切。这一步在课程里不会讲，但你真动手前必须知道。

另外：MyISAM 表如果**曾经被非正常关闭**，`ALTER` 前要 `REPAIR TABLE`，否则会把损坏带进新表。

和 EF Core 的关系：EF Core 的迁移只负责结构，不负责"引擎选型"。`EnsureCreated()` 建出来的表用服务器默认引擎，所以**开发环境跟生产环境引擎不一致**的情况是真实存在的（比如生产 my.cnf 里改过 `default_storage_engine`）。上线前查一次 `information_schema.tables` 的 `engine` 字段，比事后查事务不生效省事得多。

==二：使用格式==

```sql
ALTER TABLE t ENGINE=InnoDB;                      -- 重建表，锁表，慎用
ALTER TABLE t ENGINE=InnoDB, ALGORITHM=INPLACE, LOCK=NONE;  -- 8.0 支持在线时优先用
```

==三：代码实践==

```sql
-- 批量生成转换语句（审查后再执行，不要直接跑）
SELECT CONCAT('ALTER TABLE ', table_name, ' ENGINE=InnoDB;') AS stmt
FROM information_schema.tables
WHERE table_schema = 'demo' AND engine = 'MyISAM';
```

==四：总结归纳==

- 三条：默认 InnoDB；Memory 只用于可重建的小中间表；MyISAM 转 InnoDB 是重建表，生产要走在线工具。
- 记忆锚：选引擎不是"挑最好的"，是"确认没有例外"。
- 自测：① `ALTER TABLE ... ENGINE=InnoDB` 为什么要谨慎？② 开发库和生产库引擎可能不一致吗？怎么查？

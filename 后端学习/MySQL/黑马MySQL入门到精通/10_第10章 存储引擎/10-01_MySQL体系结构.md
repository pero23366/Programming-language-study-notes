# MySQL 体系结构

> 来源：P59《02. 进阶-存储引擎-MySQL体系结构》 · 档位 C 全新
> 与我已知的关系：SQL Server 是"一个引擎到底"，MySQL 把引擎做成了可插拔的一层——这一层就是你以后换 InnoDB/MyISAM 的开关

==一：意义与概念==

先给痛点：同样一句 `SELECT`，为什么在 MySQL 里换个"引擎"性能能差十倍？因为 MySQL 的架构不是一个整体，而是**四层各管一段**，最下面那层是可以替换的。

```
┌─────────────────────────────────────┐
│ 连接层                               │  客户端连接、认证、线程池
├─────────────────────────────────────┤
│ 服务层（Server Layer）               │  解析器、优化器、执行器、内置函数
├─────────────────────────────────────┤
│ 引擎层（Pluggable Storage Engine）    │  InnoDB / MyISAM / Memory ...（可插拔）
├─────────────────────────────────────┤
│ 存储层                               │  文件系统、redo/undo、表空间
└─────────────────────────────────────┘
```

四层各干什么：

| 层 | 职责 | 关键点 |
|---|---|---|
| 连接层 | 管理 TCP 连接、认证、权限校验、线程复用 | 连接数是资源，不是越多越好 |
| 服务层 | 词法语法解析、生成执行计划、调用引擎 | **跨引擎通用**：优化器在这一层 |
| 引擎层 | 真正读写数据、管理索引、事务、锁 | 可替换，决定表的能力边界 |
| 存储层 | 把数据落到磁盘文件 | 表空间（ibd）、日志文件 |

**为什么要这样分层**：服务层只负责"想清楚怎么取"，引擎层负责"真的去取"。所以你在服务层写的东西（SQL 语法、优化器规则）对所有引擎都一样，而"支不支持事务""支不支持行锁""索引怎么存"完全是引擎自己的事。

和 EF Core 的关系：`DbContext` 在你眼里是"一个数据库"，但底下至少有四层在转。EF Core 生成的 SQL 进的是**服务层的解析器**，优化器决定走不走索引，最后由**引擎**执行。所以 EF Core 的查询性能问题，90% 不是 EF Core 生成的 SQL 语法问题，而是**优化器选了不走索引**——这解释了为什么第 11 章的 `EXPLAIN` 比读 EF Core 文档更管用。

常见误解：以为"MySQL 数据库"是一整块。其实 `SHOW ENGINES` 能看到多个引擎共存，**同一库里不同表可以用不同引擎**（虽然不推荐）。

==二：使用格式==

```sql
SHOW ENGINES;                        -- 看支持哪些引擎与默认引擎
SELECT @@default_storage_engine;     -- 当前默认引擎（8.0 是 InnoDB）
```

==四：总结归纳==

- 三层要紧：连接层（资源）→ 服务层（优化器，跨引擎）→ 引擎层（可插拔，决定能力）。
- 记忆锚：MySQL 像一台可换发动机的车，服务层是变速箱（通用），引擎层是发动机（可换）。
- 自测：① `EXPLAIN` 的结果由哪一层产生？② 同一库的两张表能用不同引擎吗？

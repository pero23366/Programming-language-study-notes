# DCL 权限控制

> 来源：P25《25. 基础-SQL-DCL-权限控制》 · 档位 B 部分重叠
> 与我已知的关系：`GRANT` / `REVOKE` 同名，但 MySQL 的权限**挂在 `'user'@'host'` 上**，且粒度能细到列

==一：意义与概念==

给账号发权限、收权限。语法骨架与 T-SQL 相似（`GRANT ... ON ... TO ...`），差异有四层：

1. **授权对象是二元组**：`TO 'app'@'%'`，不是 `TO app`。漏写 `@host` 会报语法错或授错账号。
2. **作用域用点号分级**：`*.*`（全局）、`demo.*`（整个库）、`demo.emp`（单表）。T-SQL 靠 `USE 库` 切上下文再授，MySQL 一次写清。
3. **粒度能到列**：`GRANT SELECT(id,name) ON demo.emp TO ...`。T-SQL 也能，但用得少。
4. **没有"角色"这套默认体系**：T-SQL 有 `db_datareader` / `db_datawriter` 等固定角色，MySQL 8.0 才引入 `CREATE ROLE`，课程里没讲，日常基本靠直接授权限。

最常用的权限清单（记这些就够）：

| 权限 | 允许做什么 |
|---|---|
| `ALL [PRIVILEGES]` | 该作用域下全部（不含 `GRANT OPTION`）|
| `SELECT` / `INSERT` / `UPDATE` / `DELETE` | 增删改查数据 |
| `CREATE` / `DROP` / `ALTER` | 建/删/改表结构 |
| `CREATE USER` | 建账号 |
| `GRANT OPTION` | 允许该账号把权限再转授给别人 |

`FLUSH PRIVILEGES` 只在**直接改 `mysql` 库的系统表**后才需要，用 `GRANT` / `REVOKE` 语句时不必要——很多人习惯性加，是无害但多余的。

==二：使用格式==

```sql
GRANT 权限1, 权限2 ON 作用域 TO '用户'@'主机' [WITH GRANT OPTION];
REVOKE 权限1, 权限2 ON 作用域 FROM '用户'@'主机';
SHOW GRANTS FOR '用户'@'主机';      -- 查这个账号到底有什么
```

==三：代码实践==

```sql
-- 应用账号：只能读写 demo 库，不能改结构
GRANT SELECT, INSERT, UPDATE, DELETE ON demo.* TO 'app'@'%';

-- 只读报表账号：只给 emp 表的两列
GRANT SELECT(id, name, salary) ON demo.emp TO 'report'@'%';

-- 验证
SHOW GRANTS FOR 'app'@'%';

-- 收回 DELETE
REVOKE DELETE ON demo.* FROM 'app'@'%';
```

反例：给应用账号 `ALL ON *.*`。等于把 root 权限散出去，一次 SQL 注入就能 `DROP DATABASE`。生产上应用账号**永远只给最小集**，且不给 `DROP` / `ALTER`。

> 💡 延伸：EF Core 用 `EnsureCreated()` 或 `Migrate()` 时需要有 `CREATE` / `ALTER` / `INDEX` 权限，所以开发库给宽一点、生产库只跑迁移脚本后再收回，是常见做法。

==四：总结归纳==

- 三条：授权对象必须写 `'user'@'host'`；作用域用 `库.表` 点号分级；生产账号只给最小权限。
- 记忆锚：T-SQL 是"先切库再发钥匙"，MySQL 是"一句话说清哪把钥匙开哪个门"。
- 自测：① `GRANT SELECT ON demo.* TO 'app'`（漏了 `@host`）会怎样？② 用 `GRANT` 授权后还需要 `FLUSH PRIVILEGES` 吗？

# 锁概述与分类

> 来源：P121《64. 进阶-锁-介绍》 · 档位 C 全新
> 与我已知的关系：C# 用 `lock` 保护内存对象，数据库的锁要保护**磁盘上的行**且要跨进程——粒度、范围、死锁问题都复杂得多

==一：意义与概念==

锁解决一个问题：**多个事务同时改同一份数据，谁先谁后、谁等谁**。

MySQL 的锁按两个维度分类：

### 维度一：锁的粒度

| 粒度 | 锁定范围 | 加锁开销 | 并发度 | 引擎 |
|---|---|---|---|---|
| **全局锁** | 整个实例 | 低 | 极低（全库只读）| 服务层 |
| **表级锁** | 整张表 | 低 | 低 | MyISAM 主力，InnoDB 也有 |
| **行级锁** | 命中的索引项 | 高 | 高 | **仅 InnoDB** |

规律：**粒度越细，并发越高，但加锁开销越大**。InnoDB 选行锁是因为要支撑高并发 OLTP。

### 维度二：锁的模式

| 模式 | 含义 | 谁加 |
|---|---|---|
| **共享锁 S**（读锁）| 可读不可写，多个 S 兼容 | `SELECT ... LOCK IN SHARE MODE`（8.0 改为 `FOR SHARE`）|
| **排他锁 X**（写锁）| 独占，与任何锁都不兼容 | `INSERT`/`UPDATE`/`DELETE` 自动加；`SELECT ... FOR UPDATE` 手动加 |

兼容矩阵（记住这个 2×2）：

| | S | X |
|---|---|---|
| **S** | ✅ 兼容 | ❌ 冲突 |
| **X** | ❌ 冲突 | ❌ 冲突 |

**读操作默认不加锁**——这是 InnoDB 用 MVCC 实现的"快照读"。只有显式 `FOR UPDATE`/`FOR SHARE` 才是"当前读 + 加锁"。这一点是 MySQL 与 SQL Server 的一个大差异（SQL Server 默认 RC 下读也会加 S 锁并立即释放）。

### 一条容易被忽略的事实

**InnoDB 的锁是加在索引上的，不是加在行上**（12-07 已提）。所以：

```sql
-- id 是主键 → 锁 1 行
UPDATE emp SET salary=1 WHERE id=5;
-- name 无索引 → 扫过的所有行都锁
UPDATE emp SET salary=1 WHERE name='张三';
```

同一句 `UPDATE`，有无索引决定了"锁 1 行"还是"锁 100 万行"。**这是本章最实用的一句话。**

和 EF Core 的关系：EF Core 的 `SaveChanges()` 在事务里执行 `UPDATE ... WHERE Id=?`，天然锁一行。但如果你写"先查后改"：

```csharp
var stock = db.Stocks.Find(1);      // 快照读，不加锁
stock.Count -= 1;                    // 内存里减
db.SaveChanges();                    // UPDATE ... WHERE Id=1  ← 这时才加锁
```

**中间这段时间别人也能读到旧值、也能减**，于是超卖。修法是悲观锁（`SELECT ... FOR UPDATE`）或乐观锁（版本号）。这个 bug 在"秒杀"场景里非常经典，本质就是"快照读不加锁"。

==二：使用格式==

```sql
-- 共享锁
SELECT * FROM t WHERE id=1 FOR SHARE;            -- 8.0
SELECT * FROM t WHERE id=1 LOCK IN SHARE MODE;   -- 5.7 写法

-- 排他锁
SELECT * FROM t WHERE id=1 FOR UPDATE;

-- 查看当前锁
SELECT * FROM performance_schema.data_locks;      -- 8.0
SELECT * FROM performance_schema.data_lock_waits; -- 谁在等谁
```

==四：总结归纳==

- 三条：粒度分为全局/表/行，行锁只有 InnoDB 有；S 与 S 兼容，X 与谁都冲突；锁加在索引上，没索引就锁全表。
- 记忆锚：锁是"排队牌"，粒度是"多大范围排队"，模式是"允不允许别人一起进"。

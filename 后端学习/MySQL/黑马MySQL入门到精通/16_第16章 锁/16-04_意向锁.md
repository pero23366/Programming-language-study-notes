# 意向锁

> 来源：P126–P127《69–70. 进阶-锁-表级锁-意向锁 / 意向锁-测试》 · 档位 C 全新
> 与我已知的关系：意向锁是 InnoDB 内部的"信号灯"，你永远不会手动加它，但不懂它就解释不了"为什么行锁会跟表锁打架"

==一：意义与概念==

先给问题：InnoDB 支持行锁，也支持表锁。假设事务 A 锁了表里第 5 行（行锁），事务 B 想 `LOCK TABLES t WRITE`（表锁）。B 怎么知道"表里已经有行被锁了"？

笨办法：B 遍历整张表，逐行检查有没有行锁——100 万行就是 100 万次检查。太慢。

**意向锁（Intention Lock）就是解法**：当事务给某行加锁时，**先在表级别打一个标记**，表示"我在这张表里有行锁"。B 只看这个标记就知道"表里有行被锁"，不用遍历。

### 三种意向锁

| 锁 | 全称 | 含义 |
|---|---|---|
| **IS** | Intention Shared | 表里**有行**被加了共享锁 |
| **IX** | Intention Exclusive | 表里**有行**被加了排他锁 |
| **AI** | AUTO-INC（8.0 额外）| 自增列分配锁 |

**规律：加行级 S 锁前先加 IS，加行级 X 锁前先加 IX。** 这是自动的，你不写。

### 兼容矩阵（关键）

| | IS | IX | S（表）| X（表）|
|---|---|---|---|---|
| **IS** | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ |
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |

两条结论直接读出来：

1. **IS 和 IX 互相兼容** → 不同事务可以同时锁不同的行（这就是行锁能并发的根本原因）。
2. **IX 与表级 S 冲突** → 有人锁了行，你就不能加表级读锁。这正是"意向锁要解决的问题"。

### 为什么不用"遍历"也能判断

因为意向锁是**表级的一个标志位**，检查它 O(1)。所以：

- 事务 B 想加表锁 S：看到表上有 IX → 直接失败/等待，不用看行。
- 事务 B 想加表锁 X：看到表上有 IS 或 IX → 拒绝。

**意向锁不阻塞任何行级操作**，只用于"表锁申请时的快速判断"。这句话要记住，避免误以为"意向锁会拖慢并发"。

和 EF Core 的关系：完全透明，ORM 层看不到。但有一个可观察的推论：**`LOCK TABLES` 在有活动行锁时会失败或等待**，所以"用 `LOCK TABLES` 做备份"这种做法在有并发写入时并不可靠。

==二：使用格式==

意向锁不能手动加。只能观察：

```sql
SELECT * FROM performance_schema.data_locks
WHERE lock_type = 'TABLE';     -- 能看到 IS/IX 记录
```

==三：代码实践==

```sql
-- 会话 A：锁一行 → InnoDB 自动加 IX（表级）+ X（行级）
START TRANSACTION;
UPDATE emp SET salary = 1 WHERE id = 5;

-- 会话 B：尝试加表级读锁 → 被 IX 挡住
LOCK TABLES emp READ;
-- 等待...（因为 IX 与 S 冲突）

-- 查看锁情况
SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks WHERE OBJECT_NAME = 'emp';
-- 能看到：TABLE / IX 一行；RECORD / X 一行
```

==四：总结归纳==

- 三条：意向锁是表级标记，表示"表里有行锁"；IS/IX 互相兼容，所以行锁能并发；IX 与表 S 冲突，这是表锁申请时的快速判断依据。
- 记忆锚：意向锁是"门上的挂牌"——"屋里有客"，想包场的人看牌子就知道，不用挨个房间看。
- 自测：① 意向锁会阻塞行级操作吗？② 为什么 IS 和 IX 必须互相兼容？

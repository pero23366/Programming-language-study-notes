# 表级锁：表锁与元数据锁

> 来源：P124–P125《67–68. 进阶-锁-表级锁-表锁 / 元数据锁》 · 档位 C 全新
> 与我已知的关系：MDL 是 MySQL 独有的一套"结构变更保护"，**它是线上加字段把业务卡死的真正原因**

==一：意义与概念==

表级锁两类：

### 1. 表锁（`LOCK TABLES`，显式）

```sql
LOCK TABLES t READ;    -- 本会话可读，别人只能读
LOCK TABLES t WRITE;   -- 本会话可读写，别人什么都做不了
UNLOCK TABLES;
```

特点：

- **粒度是整表**，粒度粗、并发差。
- **MyISAM 的主力锁**（它没有行锁）。
- InnoDB 也能用，但**没必要**——用了 `LOCK TABLES` 反而会绕开事务，行为和预期不一致。

**实际很少用**。它主要出现在"批量导入前锁表"的老脚本里。

### 2. 元数据锁 MDL（`Metadata Lock`，隐式、自动）

这个才是重点。**你从来没写过它，但它一直在工作**：

> 任何对表的访问（`SELECT`/`INSERT`/`UPDATE`/`DELETE`/DDL）都会自动加 MDL。
> - 增删改查 → 加 **MDL 读锁**（共享，互相兼容）
> - 改表结构（`ALTER`）→ 加 **MDL 写锁**（排他，与读锁冲突）

**关键机制：MDL 读锁在事务结束时才释放**（不是语句结束）。

于是有了线上最经典的故障：

```
时间线：
T1 会话A：START TRANSACTION; SELECT * FROM t;   ← 加了 MDL 读锁，事务没提交
T2 会话B：ALTER TABLE t ADD COLUMN x INT;        ← 要 MDL 写锁，被 T1 阻塞
T3 会话C：SELECT * FROM t;                       ← 新查询要 MDL 读锁
                                                  但 MDL 申请是队列，B 在前面等着
                                                  → C 也被阻塞！
T4 会话D、E、F... 全部 SELECT 被阻塞 → 业务雪崩
```

**一句话总结：一个没提交的长事务 + 一次 `ALTER`，就能把整张表的读请求全部堵死。**

排查命令：

```sql
SELECT * FROM performance_schema.metadata_locks;
-- 或 5.7
SELECT * FROM information_schema.innodb_trx;
SHOW PROCESSLIST;   -- 看 State 里有没有 "Waiting for table metadata lock"
```

**预防三板斧**：

1. `ALTER` 前查 `information_schema.innodb_trx` 有没有长事务。
2. `ALTER` 加超时：`SET SESSION lock_wait_timeout = 5;`，超时就失败，不会拖死全表。
3. 大表 DDL 走 `ALGORITHM=INPLACE` 或在线工具（gh-ost/pt-osc）。

和 EF Core 的关系：**这直接对应"EF Core 长事务"的风险**：

```csharp
using var tx = db.Database.BeginTransaction();   // 开事务
var list = db.Orders.ToList();                    // 加 MDL 读锁
// ... 中间做了很慢的业务处理、调了外部 API、用户还没点确认
tx.Commit();                                      // 才释放
```

这段时间里运维一执行 `ALTER TABLE orders ...`，整个 `orders` 表的读都会排队。**事务要短**这条老生常谈，在 MySQL 里有一个非常具体的后果。

==二：使用格式==

```sql
-- 表锁
LOCK TABLES 表名 READ|WRITE;
UNLOCK TABLES;

-- MDL 是隐式的，只能查不能加
SELECT * FROM performance_schema.metadata_locks;
SHOW PROCESSLIST;
```

==三：代码实践==

```sql
-- 复现 MDL 阻塞（两个会话）
-- 会话 A
START TRANSACTION;
SELECT * FROM emp LIMIT 1;        -- 加 MDL 读锁，事务挂起

-- 会话 B
ALTER TABLE emp ADD COLUMN c INT; -- 阻塞，State: Waiting for table metadata lock

-- 会话 C
SELECT * FROM emp;                -- 也被阻塞（排队在 B 后面）

-- 会话 B 加超时避免拖死全表
SET SESSION lock_wait_timeout = 5;
ALTER TABLE emp ADD COLUMN c INT; -- 5 秒后放弃，不拖累别人
```

==四：总结归纳==

- 三条：表锁是显式粗粒度锁，InnoDB 少用；MDL 自动加，增删改查加读锁、DDL 加写锁；**MDL 读锁在事务结束才释放**，长事务 + ALTER = 全表卡死。
- 记忆锚：MDL 是"装修许可证"——有人在屋里（事务没结束），你就不能改户型，而且后面想进屋的人也得排队。

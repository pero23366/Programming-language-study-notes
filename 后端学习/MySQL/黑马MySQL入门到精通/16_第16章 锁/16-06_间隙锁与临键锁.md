# 间隙锁与临键锁

> 来源：P130–P131《73–74. 进阶-锁-行级锁-间隙锁&临键锁1 / 2》 · 档位 C 全新
> 与我已知的关系：这是"RR 级别为什么能防幻读"的答案，也是 MySQL 死锁频发的头号原因

==一：意义与概念==

先回到 09-03 的幻读：事务 A 查"部门 1 有 3 人"，事务 B 插了 1 人并提交，A 再查变 4 人。

**行锁防不住幻读**——行锁只能锁"已存在的行"，而幻读是"**凭空多出来的行**"。所以需要锁"行与行之间的空间"。

### 三种锁的图示

假设表里有 `id = 5, 10, 15` 三条记录（主键索引）：

```
 ( -∞ , 5 )   ( 5 , 10 )   ( 10 , 15 )   ( 15 , +∞ )
     间隙1        间隙2         间隙3         间隙4
   ——5——       ——10——       ——15——
```

| 锁类型 | 锁的范围 | 举例 |
|---|---|---|
| 记录锁 | 单条记录 | 锁住 `id=5` 这一行 |
| **间隙锁 Gap** | 两条记录之间（**不含**记录） | `(5, 10)` 这个空隙 |
| **临键锁 Next-Key** | 记录 + 它前面的间隙 | `(5, 10]`，即"间隙2 + id=10 这行" |

**临键锁 = 记录锁 + 间隙锁**，是两者的组合。RR 级别下 InnoDB 默认加的是**临键锁**。

### 什么时候加什么（RR 级别）

| 条件 | 加的锁 |
|---|---|
| 唯一索引等值命中且存在 | **记录锁**（退化为单行锁）|
| 唯一索引等值查不到 | **间隙锁**（锁住那个空隙，防止别人插）|
| 非唯一索引等值 | 临键锁 + 间隙锁（可能锁多条）|
| 范围查询 | **临键锁**（锁住整个范围 + 边界间隙）|
| 无索引 | 锁全表所有记录 + 所有间隙 |

关键推论：

**1. 间隙锁之间不互斥**。两个事务可以同时持有同一间隙的间隙锁，间隙锁只阻止"往间隙里插入"。

**2. 间隙锁只在 RR 及以上级别存在**。RC 级别没有间隙锁（只有记录锁），所以 RC 并发更高，但会出现幻读。**这就是很多公司把 MySQL 改成 RC 的原因**——不是不在乎幻读，而是间隙锁导致的锁等待/死锁代价更大。

**3. 间隙锁是插入意向锁的对手**。`INSERT` 会加"插入意向锁"（一种特殊的间隙锁），它与间隙锁冲突——所以"有人锁了间隙，你就插不进去"。

### 死锁的高发场景

间隙锁让死锁概率显著上升，典型模式：

```sql
-- 会话 A
START TRANSACTION;
SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE;   -- 锁 (5,10] 临键锁
-- 会话 B
START TRANSACTION;
SELECT * FROM t WHERE id BETWEEN 8 AND 15 FOR UPDATE;   -- 锁 (8,15]
-- 两个都成功（间隙锁不互斥）
-- 然后 A 插入 id=8 → 等 B；B 插入 id=9 → 等 A → 死锁
```

**修法**：范围查询尽量小、事务尽量短、避免"先 `FOR UPDATE` 再 `INSERT` 同一范围"。

和 EF Core 的关系：EF Core 不会主动加间隙锁（它不加 `FOR UPDATE`），但**你的 `UPDATE` 语句在 RR 下会带临键锁**。所以：

- 批量更新一个范围（`WHERE created_at < '2020-01-01'`）会锁住整个区间的间隙，期间别人插不进来。
- 分库分表做数据迁移时，这种"范围更新"是常见阻塞源。

**实践结论**：如果业务不能容忍间隙锁带来的锁等待，可以把会话隔离级别设为 RC（`SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED`），但要接受幻读——通常用"唯一索引 + 幂等"来兜住。

==二：使用格式==

间隙锁不能手动加，只能通过条件触发：

```sql
-- 触发临键锁：范围条件 + FOR UPDATE
SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE;

-- 触发间隙锁：唯一索引等值查不到
SELECT * FROM t WHERE id = 7 FOR UPDATE;   -- 7 不存在 → 锁 (5,10) 间隙

-- 查看
SELECT * FROM performance_schema.data_locks WHERE LOCK_MODE LIKE '%GAP%';
```

==三：代码实践==

```sql
-- 验证间隙锁阻止插入
-- 会话 A
START TRANSACTION;
SELECT * FROM t WHERE id BETWEEN 5 AND 10 FOR UPDATE;

-- 会话 B（会被阻塞）
INSERT INTO t VALUES (7);     -- 7 在 (5,10) 间隙内 → 等待

-- 会话 A 提交后，B 才能插入
COMMIT;
```

==四：总结归纳==

- 三条：间隙锁锁"行之间的空隙"，防幻读；临键锁 = 记录锁 + 间隙锁，RR 下默认；间隙锁不互斥但会阻塞插入，是死锁高发源。
- 记忆锚：行锁锁"站着的人"，间隙锁锁"两个位置之间的空位"——防止有人挤进来。

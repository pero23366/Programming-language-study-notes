# 行级锁：行锁

> 来源：P128–P129《71–72. 进阶-锁-行级锁-介绍 / 行锁》 · 档位 C 全新
> 与我已知的关系：C# 的 `lock(obj)` 锁一个对象，InnoDB 的行锁锁一个**索引项**——理解这一点，才能理解死锁和锁等待

==一：意义与概念==

**行锁**：锁住命中的索引记录，其他事务不能改这些行。InnoDB 独有，是它能做高并发 OLTP 的根本。

### 三种行级锁（InnoDB）

| 锁 | 锁什么 | 何时加 |
|---|---|---|
| **记录锁 Record Lock** | 单条索引记录 | `UPDATE ... WHERE id=5` |
| **间隙锁 Gap Lock** | 两条记录**之间**的间隙（不含记录本身）| RR 级别下，范围条件 |
| **临键锁 Next-Key Lock** | 记录 + 前面的间隙 | RR 级别默认，是记录锁与间隙锁的组合 |

本篇讲记录锁，间隙锁与临键锁在 16-06。

### 最核心的一句话：行锁加在索引上

```sql
-- id 是主键 → 锁 id=5 这一条记录
UPDATE emp SET salary=1 WHERE id=5;

-- name 有普通索引 → 锁 name='张三' 对应的索引项（可能多行，如果有重名）
UPDATE emp SET salary=1 WHERE name='张三';

-- name 无索引 → 扫全表，扫过的每一行都加锁 = 事实上的表锁
UPDATE emp SET salary=1 WHERE name='张三';
```

这就是为什么 12-07 说"`UPDATE` 的条件列必须有索引"。**没有索引不是"慢一点"，是"锁全表"。**

### 行锁的两个重要行为

**1. 行锁在事务结束时释放，不是语句结束**

```sql
START TRANSACTION;
UPDATE emp SET salary=1 WHERE id=5;   -- 锁住 id=5
-- 此时别的事务改 id=5 会等待，直到你 COMMIT/ROLLBACK
COMMIT;                               -- 释放
```

**2. 快照读不加锁，当前读才加锁**

| 语句 | 类型 | 加锁 |
|---|---|---|
| `SELECT * FROM t WHERE id=5` | 快照读（MVCC）| ❌ 不加锁 |
| `SELECT ... FOR UPDATE` | 当前读 | ✅ 加 X 锁 |
| `SELECT ... FOR SHARE` | 当前读 | ✅ 加 S 锁 |
| `UPDATE` / `DELETE` | 当前读 | ✅ 加 X 锁 |

这也解释了"为什么并发扣库存会超卖"：普通 `SELECT` 读的是快照，不加锁，两个事务都读到库存 1，都扣，结果 -1。

### 死锁：行锁的必然后果

两个事务互相等对方持有的锁 → 死锁。InnoDB 会**自动检测并回滚其中一个**（代价小的那个），报：

```
ERROR 1213: Deadlock found when trying to get lock; try restarting transaction
```

避免死锁的三条实践：

1. **按固定顺序访问资源**（比如总是先锁 id 小的行）。
2. **事务要短**，减少持锁时间。
3. **`UPDATE` 的 `WHERE` 尽量用主键/唯一索引**，减少锁范围。

和 EF Core 的关系（很实用）：

```csharp
// 悲观锁：EF Core 7+ 有原生支持
var stock = db.Stocks.FromSql($"SELECT * FROM stock WHERE id=1 FOR UPDATE").First();
stock.Count -= 1;
db.SaveChanges();

// 乐观锁：版本号（EF Core 的并发令牌）
public byte[] Version { get; set; }
modelBuilder.Entity<Stock>().Property(s => s.Version).IsRowVersion();
// SaveChanges 时自动加 WHERE Version=旧值，影响行数为 0 则抛 DbUpdateConcurrencyException
```

**这两种是解决超卖的标准方案**，一个靠数据库锁，一个靠应用层检测。理解行锁，才知道该选哪个。

==二：使用格式==

```sql
-- 手动加行锁
SELECT * FROM t WHERE id=1 FOR UPDATE;        -- X 锁
SELECT * FROM t WHERE id=1 FOR SHARE;         -- S 锁

-- 查看行锁
SELECT * FROM performance_schema.data_locks WHERE LOCK_TYPE='RECORD';
```

==三：代码实践==

```sql
-- 会话 A
START TRANSACTION;
UPDATE emp SET salary = 9999 WHERE id = 5;    -- 锁 id=5

-- 会话 B（会等待）
UPDATE emp SET salary = 8888 WHERE id = 5;    -- 阻塞
-- 查看：SELECT * FROM sys.innodb_lock_waits;

-- 会话 A 提交后，B 立即执行
COMMIT;
```

==四：总结归纳==

- 三条：行锁加在索引上，无索引 = 锁全表；行锁在**事务结束**才释放；普通 `SELECT` 是快照读不加锁，`FOR UPDATE` 才加。
- 记忆锚：行锁是"在索引树上插一面旗"，没有索引就没有插旗的位置，只能把整张桌子围起来。

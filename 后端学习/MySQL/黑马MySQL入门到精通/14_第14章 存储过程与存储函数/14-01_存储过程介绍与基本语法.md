# 存储过程：介绍与基本语法

> 来源：P102–P103《45–46. 进阶-存储过程-介绍 / 基本语法》 · 档位 B 部分重叠
> 与我已知的关系：T-SQL 也有存储过程，概念不陌生；**但 MySQL 的 `DELIMITER` 和 `BEGIN...END` 配合方式完全不同**

==一：意义与概念==

**存储过程**：一组预编译好的 SQL 语句，存在数据库里，用名字调用。

```sql
CALL p_get_dept_emp(1);
```

它解决的问题：把"多条 SQL 组成的业务步骤"封在数据库侧，减少应用与数据库的往返。

**必须讲的行业现实**：互联网公司**普遍不用存储过程**。理由：业务逻辑散在数据库里难维护、难测试、难做版本管理、难迁移（换库要重写）、扩容时数据库是瓶颈。**"逻辑留在应用层"是现代主流**。

那为什么还要学：

1. 大量存量系统（金融、ERP、政务）里有海量存储过程，你得能读能改。
2. 它是理解"游标/handler/变量"的载体，而这些概念在触发器里也用。
3. 数据迁移、批量修复数据时，存储过程确实比写 C# 脚本方便。

### 与 T-SQL 的三个硬差异

| 维度 | MySQL | T-SQL |
|---|---|---|
| 语句结束符 | 过程体内用 `;`，必须先用 **`DELIMITER $$`** 换掉默认的 `;` | 用 `GO` 分隔批次，不需要改分隔符 |
| 语句块 | `BEGIN ... END` | `BEGIN ... END`（但常省略）|
| 调用 | `CALL 过程名(...)` | `EXEC 过程名 ...` 或直接 `过程名` |

`DELIMITER` 是初学者最大的坎：MySQL 客户端看到 `;` 就认为"语句结束"，而存储过程体里到处是 `;`。所以要临时把"结束标志"换成 `$$`，写完再换回 `;`。**这纯粹是客户端行为，不是 SQL 语法**——用 DataGrip 时它通常自动处理。

和 EF Core 的关系：`db.Database.ExecuteSqlRaw("CALL p_xxx({0})", id)` 可以调存储过程，但**返回值/结果集处理很别扭**（`OUT` 参数在 EF Core 里拿不到，要用 `DbCommand` 手写）。这也侧面说明：ORM 时代的存储过程基本是"只读遗留代码"的角色。

==二：使用格式==

```sql
DELIMITER $$                       -- 换结束符（客户端命令）

CREATE PROCEDURE 过程名([参数列表])
BEGIN
  -- 多条 SQL，每条以 ; 结尾
END $$

DELIMITER ;                        -- 换回来

CALL 过程名(参数);

DROP PROCEDURE [IF EXISTS] 过程名;
SHOW PROCEDURE STATUS WHERE Db = 'demo';
```

==三：代码实践==

```sql
DELIMITER $$

CREATE PROCEDURE p_emp_count(IN p_dept_id INT, OUT p_count INT)
BEGIN
  SELECT COUNT(*) INTO p_count FROM emp WHERE dept_id = p_dept_id;
END $$

DELIMITER ;

CALL p_emp_count(1, @cnt);
SELECT @cnt;
```

==四：总结归纳==

- 三条：`DELIMITER` 是客户端换结束符，不是 SQL；`BEGIN...END` 里每条语句仍以 `;` 结尾；现代项目优先把逻辑放应用层。
- 记忆锚：存储过程是"数据库里的函数"，`DELIMITER` 是"先告诉客户端别急着截断"。
- 自测：① 不写 `DELIMITER` 直接建带 `BEGIN...END` 的过程会怎样？② 为什么互联网公司少用存储过程？

# DDL 数据库操作

> 来源：P6《06. 基础-SQL-DDL-数据库操作》 · 档位 B 部分重叠
> 与我已知的关系：`CREATE DATABASE` 与 T-SQL 同名同用法，**但 MySQL 多了一层字符集，且它是库级默认值**

==一：意义与概念==

建库、删库、切库、看库——四条语句，骨架你在 T-SQL 里都写过。真正要理解的是 MySQL 独有的那个概念：**字符集（charset）与排序规则（collation）挂在库上，会往下继承**。

- T-SQL 的 Collation 是**实例级 + 列级**的东西，跟"能不能存中文"关系不大（它改用 `nvarchar` 解决）。
- MySQL **没有 `nvarchar`**，能不能存中文、能不能存 emoji，全靠字符集。库上定了 `utf8mb4`，库里新建的表、表里的列默认都继承它。

为什么必须是 `utf8mb4` 而不是 `utf8`：MySQL 的 `utf8` 是个**残缺实现，最多 3 字节**，存不下 4 字节的 emoji 和部分生僻字。`utf8mb4` 才是真正的 UTF-8。这是 MySQL 最著名的历史包袱，别用 `utf8`。

常见误解：以为排序规则只影响 `ORDER BY`。它还影响 `=` 比较——`utf8mb4_general_ci` 的 `ci` 是 case-insensitive，`WHERE name='Tom'` 能匹配到 `tom`。要区分大小写得用 `_bin` 或 `_as_cs` 结尾的。

==二：使用格式==

```sql
CREATE DATABASE [IF NOT EXISTS] 库名
  [DEFAULT CHARACTER SET utf8mb4]
  [DEFAULT COLLATE utf8mb4_general_ci];

DROP DATABASE [IF EXISTS] 库名;   -- 库里的表一起没，不可恢复
USE 库名;                          -- 相当于 C# 换连接串里的 Database
SELECT DATABASE();                 -- 看当前在哪个库
SHOW DATABASES;                    -- 列出所有库
```

| 子句 | 必填 | 作用 | 默认值 |
|---|---|---|---|
| `IF NOT EXISTS` | 否 | 库已存在时不报错 | 无（存在则报错）|
| `CHARACTER SET` | 建议填 | 库的默认字符集 | 8.0 为 `utf8mb4` |
| `COLLATE` | 否 | 比较/排序规则 | 跟随字符集 |

==三：代码实践==

```sql
-- 建库：显式写死字符集，别依赖默认值（5.7 默认是 latin1）
CREATE DATABASE IF NOT EXISTS demo
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

USE demo;
SELECT DATABASE();          -- 返回 demo

-- 查看这个库到底用了什么字符集
SHOW CREATE DATABASE demo;
```

反例：

```sql
CREATE DATABASE demo2;      -- 5.7 上这行建出 latin1 的库
```

症状是插入中文报 `Incorrect string value: '\xE4\xB8\xAD'`，或者中文变 `???`。**不是连接串问题，是库字符集问题。** 修复：`ALTER DATABASE demo2 CHARACTER SET utf8mb4;`（只影响之后新建的表，老表要单独改）。

==四：总结归纳==

- 三条：建库必写 `utf8mb4`；`utf8` 是残缺版别用；排序规则的 `ci` 影响等值比较。
- 记忆锚：T-SQL 用 `nvarchar` 一列一列解决中文，MySQL 用字符集一层一层继承解决。
- 自测：① 库建好后改字符集，已有的表会跟着变吗？② `WHERE name='tom'` 能查出 `Tom`，是字符集还是排序规则决定的？

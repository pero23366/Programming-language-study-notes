# 数据类型

> 来源：P8《08. 基础-SQL-DDL-数据类型及案例》 · 档位 B 部分重叠
> 与我已知的关系：C# 的类型能对上大半，但**没有 nvarchar、没有 bit、没有 datetime2**，这是移植 EF Core 项目时最容易踩的一段

==一：意义与概念==

建表定列类型，本质是回答三个问题：占多大空间、能存什么范围、比较时按什么规则。MySQL 的类型体系比 C# 少，所以映射关系不是一一对应——**有几个 C# 常用类型在 MySQL 里压根不存在**。

最要紧的一条：MySQL 的 `VARCHAR(n)` 里 **n 是字符数，不是字节数**（5.0.3 之后）。所以 `VARCHAR(10)` 能存 10 个汉字，不用像 `nvarchar(10)` 那样操心字节。这意味着 **MySQL 没有 `varchar` / `nvarchar` 之分**——统一用 `varchar`，中文靠 `utf8mb4` 解决。

数值类型：

| 类型 | 字节 | 范围 / 用途 | C# 对应 |
|---|---|---|---|
| `TINYINT` | 1 | -128~127，常用 `TINYINT(1)` 当布尔 | `bool` / `byte` |
| `SMALLINT` | 2 | ±3.2 万 | `short` |
| `MEDIUMINT` | 3 | ±838 万（MySQL 独有）| 无 |
| `INT` | 4 | ±21 亿 | `int` |
| `BIGINT` | 8 | ±922 京 | `long` |
| `FLOAT` / `DOUBLE` | 4 / 8 | 浮点，有精度误差 | `float` / `double` |
| `DECIMAL(p,s)` | 变长 | 定点，**金额必须用它** | `decimal` |

字符串与日期：

| 类型 | 说明 | C# 对应 |
|---|---|---|
| `CHAR(n)` | 定长，不足补空格，适合定长编码 | `string`（定长场景）|
| `VARCHAR(n)` | 变长，n 是字符数 | `string` |
| `TEXT` / `LONGTEXT` | 大文本，不能设默认值 | `string` |
| `DATE` | 只有日期 `2026-11-09` | `DateOnly` |
| `TIME` | 只有时间 | `TimeOnly` |
| `DATETIME` | 8 字节，`1000-01-01`~`9999-12-31`，**不随时区变** | `DateTime` |
| `TIMESTAMP` | 4 字节，`1970-01-01`~`2038-01-19`，**按 UTC 存、按会话时区显示** | `DateTimeOffset`（近似）|
| `DATETIME(6)` | 带微秒，精度到 6 位 | `DateTime`（Ticks）|

**C# 到 MySQL 的移植对照**（写 EF Core 配 MySQL 时直接查这张）：

| 你在 SQL Server 里用 | MySQL 改用 | 注意 |
|---|---|---|
| `NVARCHAR(n)` | `VARCHAR(n)` | n 直接写字符数 |
| `NVARCHAR(MAX)` | `LONGTEXT` | 不能设默认值、不能直接建索引 |
| `BIT` | `TINYINT(1)` | MySQL 的 `BOOLEAN` 就是它的别名 |
| `MONEY` | `DECIMAL(19,4)` | 别用 `DOUBLE` 存钱 |
| `DATETIME2(7)` | `DATETIME(6)` | 最多 6 位小数 |
| `UNIQUEIDENTIFIER` | `CHAR(36)` 或 `BINARY(16)` | MySQL 没有原生 GUID 类型 |
| `VARBINARY(MAX)` | `LONGBLOB` | |

两个真实坑：

- **`TINYINT(1)` 的 `(1)` 不是长度限制**，只是"显示宽度"，8.0.17 起已废弃。`TINYINT(1)` 和 `TINYINT(4)` 存的数值范围一模一样。很多人以为写了 `(1)` 只能存 0/1，其实存得下 127。
- **`TIMESTAMP` 有 2038 问题**，且会自动把写入时间转成 UTC。同一行数据在时区不同的两个客户端里读出来不一样。要做"创建时间、更新时间"用 `DATETIME` 更稳；要跨时区绝对时间才用 `TIMESTAMP`。

==二：使用格式==

```sql
-- 常用自动时间列写法
create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

| 选项 | 作用 | 限制 |
|---|---|---|
| `DEFAULT CURRENT_TIMESTAMP` | 插入时不给值就取当前时间 | 只能是 `DATETIME` / `TIMESTAMP` |
| `ON UPDATE CURRENT_TIMESTAMP` | 该行**任一列**被更新时自动刷新 | 同上 |
| `UNSIGNED` | 去掉负数区间，正数范围翻倍 | 与 C# 的无符号类型对应，慎用于会做减法的列 |
| `ZEROFILL` | 不足位补 0（已废弃）| 8.0.17 起不推荐 |

==三：代码实践==

```sql
CREATE TABLE emp (
  id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
  name        VARCHAR(20)  NOT NULL COMMENT '姓名',
  gender      TINYINT(1)   DEFAULT 1  COMMENT '1男 2女',   -- 不是 bool 专用，只是习惯
  age         TINYINT UNSIGNED COMMENT '年龄',
  salary      DECIMAL(10,2) COMMENT '薪资，别用 double',
  id_card     CHAR(18)     COMMENT '定长用 char',
  entry_date  DATE,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

反例：

```sql
salary DOUBLE          -- 0.1+0.2 存进去可能变成 0.30000000000000004，对账差一分钱
salary DECIMAL(10,2)   -- 正确：定点数，精确到分
```

==四：总结归纳==

- 三条：`VARCHAR(n)` 的 n 是字符数（所以不需要 nvarchar）；金额只用 `DECIMAL`；`TIMESTAMP` 有时区和 2038 限制，默认用 `DATETIME`。
- 记忆锚：MySQL 的类型是"C# 的精简版"——`string` 只剩一个 varchar，`bool` 借 `tinyint(1)`，`Guid` 借 `char(36)`。

# 约束概述与分类

> 来源：P32《32. 基础-约束-概述》 · 档位 A 几乎重叠
> 与我已知的关系：六种约束与 T-SQL 一一对应，概念零成本

==一：意义与概念==

约束是**数据库层的最后一道校验**：应用层可以忘写 if，数据库不许脏数据进表。

| 约束 | 作用 | T-SQL 对应 |
|---|---|---|
| `NOT NULL` | 该列不许为 NULL | 同 |
| `UNIQUE` | 该列值唯一（可多个 NULL）| 同 |
| `PRIMARY KEY` | 唯一 + 非空，一表一个 | 同 |
| `DEFAULT` | 不给值时填默认 | 同 |
| `CHECK` | 值必须满足条件 | 同（MySQL 8.0.16 前不生效，见下篇）|
| `FOREIGN KEY` | 值必须在父表存在 | 同 |

区别只在**生效强度**与**默认行为**，不在概念。所以这篇只需要记住一句话：分类照 T-SQL 记，写之前确认 CHECK 和 UNIQUE 的边界（下两篇）。

与 EF Core 的对应关系也直白：`[Required]` → `NOT NULL`、`HasIndex().IsUnique()` → `UNIQUE`、`HasKey()` → `PRIMARY KEY`、`HasDefaultValue()` → `DEFAULT`、导航属性 + `HasForeignKey()` → `FOREIGN KEY`。**但 EF Core 的 Fluent API 只是生成 DDL 的模板**，最终约束活在数据库里，绕过 EF 直连数据库照样受约束。

==四：总结归纳==

- 三条：六种约束与 T-SQL 同名同义；约束是应用层校验之外的兜底；EF Core 的配置最终都落成这些约束。
- 记忆锚：`[Required]` / `[MaxLength]` 那些特性，编译到数据库里就是 `NOT NULL` / `VARCHAR(n)`。
- 自测：一个表能有几个 `PRIMARY KEY`？几个 `UNIQUE`？

# 外键的删除与更新行为

> 来源：P35《35. 基础-约束-外键删除更新行为》 · 档位 B 部分重叠
> 与我已知的关系：`CASCADE` / `SET NULL` 与 T-SQL 同名同义，**但 MySQL 默认是 RESTRICT，且不支持 SET DEFAULT**

==一：意义与概念==

父表的行被删/改时，子表怎么办？这就是"删除更新行为"，五种取值：

| 行为 | 含义 | T-SQL 对应 |
|---|---|---|
| `RESTRICT` | 父行被子行引用时，**拒绝**删除/修改（默认）| 有 |
| `NO ACTION` | 同 RESTRICT（MySQL 里两者等效，立即检查）| 有 |
| `CASCADE` | 级联：父行删，子行跟着删；父键改，子键跟着改 | 有 |
| `SET NULL` | 子表外键列置为 NULL（要求该列可空）| 有 |
| `SET DEFAULT` | 置为默认值 | T-SQL 有，**MySQL 的 InnoDB 不支持**，写了会被拒绝 |

三个必须理解的边界：

1. **默认是 `RESTRICT`**，不是 `CASCADE`。不写就代表"父行有人引用时不许删"。这跟直觉相反——很多人以为不写就是"随便删"。
2. **`SET NULL` 要求子列允许 NULL**，否则建约束时直接报错。
3. **`CASCADE` 会连锁传播**：A 删 → B 删 → C 删，一次 `DELETE` 可能删掉几十万行，且**这个删除动作不写 binlog 明细（ROW 格式下会记）**，排查数据丢失很痛苦。生产上慎用级联删除。

与你 EF Core 经验的对应：`DeleteBehavior.Cascade` 生成的就是 `ON DELETE CASCADE`，`DeleteBehavior.Restrict` 对应 `RESTRICT`，`DeleteBehavior.SetNull` 对应 `SET NULL`。**EF Core 默认对必需关系用 Cascade、可选关系用 ClientSetNull**，这跟数据库的 `RESTRICT` 默认值不是一回事——两边默认值不一样，是踩坑高发区。

==二：使用格式==

```sql
CONSTRAINT fk_名 FOREIGN KEY (子列) REFERENCES 父表(父列)
  [ON DELETE {RESTRICT | CASCADE | SET NULL | NO ACTION}]
  [ON UPDATE {RESTRICT | CASCADE | SET NULL | NO ACTION}]
```

两个子句独立，可以一个用 `CASCADE`、一个用 `RESTRICT`。

==三：代码实践==

```sql
-- 部门删了，员工跟着删（危险，仅演示）
ALTER TABLE emp ADD CONSTRAINT fk_emp_dept
  FOREIGN KEY (dept_id) REFERENCES dept(id)
  ON DELETE CASCADE ON UPDATE CASCADE;

DELETE FROM dept WHERE id = 1;   -- emp 里 dept_id=1 的行一起消失

-- 部门删了，员工保留但部门清空（要求 dept_id 可空）
ALTER TABLE emp DROP FOREIGN KEY fk_emp_dept;
ALTER TABLE emp ADD CONSTRAINT fk_emp_dept
  FOREIGN KEY (dept_id) REFERENCES dept(id)
  ON DELETE SET NULL;
```

==四：总结归纳==

- 三条：默认 `RESTRICT`；`SET NULL` 要求子列可空；`SET DEFAULT` 在 InnoDB 不支持。
- 记忆锚：不写就是不让你删——外键默认是个保守的门卫，不是无脑追随者。

# 外键约束

> 来源：P34《34. 基础-约束-外键约束》 · 档位 B 部分重叠
> 与我已知的关系：`FOREIGN KEY ... REFERENCES` 语法一致，**但 MySQL 要求引擎必须是 InnoDB，且业界普遍不建物理外键**

==一：意义与概念==

外键保证"子表的这个值，在父表里一定存在"。语法你在 T-SQL 里写过，MySQL 有三处前置条件：

1. **引擎必须是 InnoDB**。MyISAM 表上写外键**不报错但直接忽略**——这是最阴的一条，约束静默失效。
2. **父列必须有索引**（主键或唯一键自然满足）。子表列上 MySQL 会**自动建索引**，T-SQL 不会。
3. **父子表必须在同一个库**。MySQL 不支持跨库外键。

还有一个必须讲清的行业现实：**互联网公司普遍不建物理外键**。

理由不是"外键没用"，而是它带来的运维代价：分库分表后父子表可能不在同一个库（MySQL 不支持跨库外键，直接失效）；大批量导入/删除时外键检查拖慢速度；`DELETE` 父行会被子行卡住，线上排障困难。所以常见做法是**逻辑外键**——子表只存 `dept_id`，不加 `FOREIGN KEY` 约束，由应用层（或 EF Core 的导航属性）保证一致性。

这与你的 EF Core 经验直接对应：EF Core 默认会**生成**外键约束，但你可以用 `.HasNoForeignKey()` 或干脆不配导航关系来避免。阿里 Java 开发手册明确写了"不得使用外键与级联，一切外键概念必须在应用层解决"，这条在 .NET 圈同样流行。

**判断标准**：教学/单体项目/数据一致性要求高 → 用物理外键；要分库分表、要高吞吐写入 → 用逻辑外键。

==二：使用格式==

```sql
-- 建表时
CONSTRAINT fk_子表_父表 FOREIGN KEY (子表列) REFERENCES 父表(父表列);

-- 已有表追加
ALTER TABLE 子表 ADD CONSTRAINT fk_名字
  FOREIGN KEY (子表列) REFERENCES 父表(父表列);

-- 删除外键（注意：删约束用 DROP FOREIGN KEY，不是 DROP CONSTRAINT）
ALTER TABLE 子表 DROP FOREIGN KEY fk_名字;
```

最后一条是 MySQL 特有的坑：T-SQL 用 `DROP CONSTRAINT`，MySQL 删外键必须用 `DROP FOREIGN KEY`。

==三：代码实践==

```sql
CREATE TABLE dept (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(20) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE emp (
  id      INT AUTO_INCREMENT PRIMARY KEY,
  name    VARCHAR(20) NOT NULL,
  dept_id INT,
  CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) REFERENCES dept(id)
) ENGINE=InnoDB;

INSERT INTO emp (name, dept_id) VALUES ('张三', 999);
-- ERROR 1452: Cannot add or update a child row: a foreign key constraint fails
```

反例：

```sql
CREATE TABLE emp (...) ENGINE=MyISAM;   -- 外键语句能执行成功，但约束不存在
```

==四：总结归纳==

- 三条：外键要求 InnoDB + 父列有索引 + 同库；MyISAM 上外键静默失效；删外键用 `DROP FOREIGN KEY`。
- 记忆锚：物理外键是"数据库帮你守门"，逻辑外键是"你自己在应用层守门"——分库分表的世界里只能选后者。

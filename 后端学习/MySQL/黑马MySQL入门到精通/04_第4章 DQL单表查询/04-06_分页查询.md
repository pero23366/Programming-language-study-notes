# DQL 分页查询

> 来源：P20《20. 基础-SQL-DQL-分页查询》 · 档位 B 部分重叠
> 与我已知的关系：**分页语法换了关键字**——T-SQL 的 `OFFSET ... FETCH` 在 MySQL 是 `LIMIT 偏移, 条数`

==一：意义与概念==

分页解决"一次返回太多行"的问题：前端一次要 10 条，数据库不该把 10 万条都吐出来。

两边的写法完全不同：

| | T-SQL | MySQL |
|---|---|---|
| 关键字 | `OFFSET n ROWS FETCH NEXT m ROWS ONLY` | `LIMIT n, m` |
| 偏移量计算 | 自己算 `(页码-1)*每页` | 同 |
| 是否必须 `ORDER BY` | **必须**，否则报错 | **不必须**，但顺序不保证 |
| 省略偏移 | `OFFSET 0` 也得写 | `LIMIT m` 直接表示前 m 条 |

`LIMIT n, m` 的第一个参数是**偏移量**（跳过多少行），不是页码。这个顺序与直觉相反，写反了会得到"跳 2 条取 10 条"而不是"第 2 页"。等价写法 `LIMIT m OFFSET n` 更不容易错，推荐用它。

三个必须知道的行为：

1. **没有 `ORDER BY` 的 `LIMIT` 结果是不确定的**。InnoDB 返回顺序取决于索引和执行计划，同一句 SQL 两次执行可能不一样。分页必须配 `ORDER BY`。
2. **深分页会越来越慢**：`LIMIT 1000000, 10` 要扫描并丢弃前 100 万行。这是第 12 章"limit 优化"的主题（解法是延迟关联或游标分页）。
3. **总数要单独查**：`SELECT COUNT(*)` 一次，`LIMIT` 一次。MySQL 没有 T-SQL 的窗口函数 `COUNT(*) OVER()` 顺手方案（8.0 有窗口函数，但一次查询算总数仍不划算）。

==二：使用格式==

```sql
SELECT 列 FROM 表名 [WHERE ...] ORDER BY 排序列 LIMIT 偏移量, 条数;
SELECT 列 FROM 表名 [WHERE ...] ORDER BY 排序列 LIMIT 条数 OFFSET 偏移量;  -- 推荐
```

| 参数 | 含义 | 建议 |
|---|---|---|
| 偏移量 | 跳过几行 = `(页码-1) × 每页条数` | 用 `OFFSET` 写法避免顺序搞反 |
| 条数 | 本页取几行 | 固定值，走参数化 |

==三：代码实践==

```sql
-- 第 3 页，每页 10 条：跳过 20 条，取 10 条
SELECT id, name, salary FROM emp ORDER BY id LIMIT 10 OFFSET 20;
```

反例：

```sql
SELECT * FROM emp LIMIT 10, 20;   -- 你以为"第 10 页取 20 条"，实际是"跳过 10 条取 20 条"
SELECT * FROM emp LIMIT 0, 10;    -- 没有 ORDER BY，两页之间可能重复或漏行
```

==四：总结归纳==

- 三条：`LIMIT 偏移, 条数`，偏移不是页码；`LIMIT 条数 OFFSET 偏移` 更好读；分页必配 `ORDER BY`。
- 记忆锚：T-SQL 的分页是"先排好再跳过"，MySQL 的是"跳过前几个再拿几个"，语义顺序更贴近实现。

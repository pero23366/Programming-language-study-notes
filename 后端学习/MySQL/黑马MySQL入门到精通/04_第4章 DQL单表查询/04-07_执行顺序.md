# DQL 语句执行顺序

> 来源：P22《22. 基础-SQL-DQL-执行顺序》 · 档位 B 部分重叠
> 与我已知的关系：**和你写 T-SQL 的心智完全一致**，这一段值得读，因为它解释了"为什么别名有的地方能用、有的地方不能用"

==一：意义与概念==

SQL 是**声明式**语言：你写的是"我要什么"，不是"怎么算"。所以书写顺序和执行顺序不是一回事。

真实执行顺序（编号是执行顺序，不是书写顺序）：

```
① FROM / JOIN    —— 先确定从哪些表取数据，生成笛卡尔积
② ON             —— 连接条件，过滤掉不匹配的组合
③ WHERE          —— 对行做过滤
④ GROUP BY       —— 分组
⑤ HAVING         —— 对组做过滤
⑥ SELECT         —— 投影出要的列、算聚合、算别名
⑦ DISTINCT       —— 去重
⑧ ORDER BY       —— 排序
⑨ LIMIT          —— 截取
```

这个顺序能解释三个常见困惑：

1. **为什么 `WHERE` 不能用 `SELECT` 起的别名？** 因为 ③ 在 ⑥ 之前，别名还不存在。
2. **为什么 `ORDER BY` 能用别名？** 因为 ⑧ 在 ⑥ 之后。
3. **为什么 `WHERE` 里不能写聚合函数？** 因为聚合发生在 ④，`WHERE` 在 ③，那时还没分组。

与 T-SQL 的区别只有一处：**`LIMIT` 在 MySQL 是第 ⑨ 步、永远最后**；T-SQL 的 `TOP` 写在 `SELECT` 里，逻辑上属于第 ⑥ 步之后的一层包装。这就是为什么 MySQL 的 `LIMIT` 一定在 `ORDER BY` 后面，而 `TOP` 写在前面。

==二：使用格式==

书写顺序（人写的时候）：

```sql
SELECT ... FROM ... JOIN ... ON ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...
```

记忆用"执行顺序九步"，写代码时**不用改书写顺序**，只要理解每一步能看到什么。

| 步骤 | 能看到前面步骤的产物吗 | 典型陷阱 |
|---|---|---|
| `WHERE` | 表原始列，看不到别名、聚合 | 写 `WHERE 别名 = 1` 报 1054 |
| `SELECT` | 前面所有过滤后的行 | 在这里算别名 |
| `ORDER BY` | 能看到别名、能看到聚合 | 可以用 `ORDER BY COUNT(*)` |
| `LIMIT` | 排好序的结果 | 不写 `ORDER BY` 顺序随机 |

==三：代码实践==

```sql
-- 反例：WHERE 用别名 → ERROR 1054 Unknown column '年薪' in 'where clause'
SELECT salary * 12 AS 年薪 FROM emp WHERE 年薪 > 100000;

-- 正确：条件里把表达式写全，或者交给 HAVING
SELECT salary * 12 AS 年薪 FROM emp WHERE salary * 12 > 100000;

-- ORDER BY 用别名 → 合法，因为排序在投影之后
SELECT salary * 12 AS 年薪 FROM emp ORDER BY 年薪 DESC;
```

==四：总结归纳==

- 三条：执行顺序是 FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT；别名只能被后面的步骤看见；`LIMIT` 是 MySQL 的最后一步。
- 记忆锚：SQL 像流水线，`SELECT` 在中间不在开头——先筛数据，最后才挑列。
- 自测：① 为什么 `HAVING` 里能用聚合而 `WHERE` 不能？② `LIMIT` 和 T-SQL 的 `TOP` 位置不同，本质原因是什么？

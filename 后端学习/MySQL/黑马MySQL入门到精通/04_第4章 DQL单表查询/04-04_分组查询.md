# DQL 分组查询

> 来源：P18《18. 基础-SQL-DQL-分组查询》 · 档位 B 部分重叠
> 与我已知的关系：`GROUP BY` / `HAVING` 概念一样，**但 MySQL 8.0 默认开了 `ONLY_FULL_GROUP_BY`，规则比 SQL Server 更凶**

==一：意义与概念==

按某列的值把行切成几堆，每堆算一个聚合值。`WHERE` 在分组**前**筛行，`HAVING` 在分组**后**筛组——这个顺序两边一样。

真正要理解的是 MySQL 8.0 默认开启的 `sql_mode = ONLY_FULL_GROUP_BY`：

> **`SELECT` 里出现的非聚合列，必须出现在 `GROUP BY` 里。**

违反它会直接报错：

```
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause
and contains nonaggregated column 'demo.emp.name' which is not functionally dependent on columns in GROUP BY clause
```

这个限制在 MySQL 5.7 之前**不存在**——老代码 `SELECT name, gender, COUNT(*) FROM emp GROUP BY gender` 能跑，`name` 会随机取组内某一行。这是最典型的"网上抄来的 SQL 在 8.0 报错"。

为什么该有这个限制：`GROUP BY gender` 之后，一个性别对应多行，`name` 该显示哪一个？没有正确答案。老 MySQL 给的是"碰巧第一行"，这种结果不可复现，是 bug 不是特性。

SQL Server 也有同样的要求（非聚合列必须在 `GROUP BY` 或聚合函数里），所以对你来说**这条规则不是新增负担**，反而是回归正常。差别在于 SQL Server 报错信息更直白，MySQL 的"functionally dependent"提示会让人以为跟主键依赖有关。

==二：使用格式==

```sql
SELECT 分组列, 聚合函数(列)
FROM 表名
[WHERE 分组前的行条件]
GROUP BY 分组列
[HAVING 分组后的组条件]
[ORDER BY ...];
```

| 子句 | 时机 | 能写什么 | 典型用途 |
|---|---|---|---|
| `WHERE` | 分组前，作用于行 | 原始列、不能写聚合函数 | 先过滤掉不参与统计的行 |
| `HAVING` | 分组后，作用于组 | 聚合函数、分组列 | 筛掉样本太少的组 |

==三：代码实践==

```sql
-- 按性别统计人数与平均薪资，只要平均薪资 > 8000 的组
SELECT gender, COUNT(*) AS 人数, AVG(salary) AS 平均薪资
FROM emp
WHERE age >= 20              -- 分组前：剔掉 20 岁以下的
GROUP BY gender
HAVING AVG(salary) > 8000    -- 分组后：剔掉平均薪资低的组
ORDER BY 平均薪资 DESC;
```

反例（8.0 直接报 1055）：

```sql
SELECT name, gender, COUNT(*) FROM emp GROUP BY gender;
-- name 不分组也不聚合，一个性别多个人，显示谁？
```

正确改法二选一：把 `name` 加进 `GROUP BY`，或者用聚合把它收掉 `MAX(name)`（语义上要想清楚为什么取 MAX）。

想临时关掉（不推荐，只是让你能读懂老代码）：

```sql
SELECT @@sql_mode;   -- 看当前模式，含 ONLY_FULL_GROUP_BY
SET SESSION sql_mode = 'STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION';
```

==四：总结归纳==

- 三条：`WHERE` 筛行在分组前、`HAVING` 筛组在分组后；8.0 默认 `ONLY_FULL_GROUP_BY`，非聚合列必须进 `GROUP BY`；老代码报 1055 不是你的错。
- 记忆锚：分组之后每一行代表一堆，能显示的只有"这堆的共同标签"和"这堆算出来的数"。
- 自测：① `HAVING COUNT(*) > 5` 能不能改写成 `WHERE`？② 为什么 `SELECT name, COUNT(*) FROM emp GROUP BY gender` 在语义上无解？

# 磁盘结构与后台线程

> 来源：P136–P137《79–80. 进阶-InnoDB引擎-架构-磁盘结构 / 后台线程》 · 档位 C 全新
> 与我已知的关系：这一篇是"数据库的文件都长什么样"，也是备份/恢复/崩溃排查的地图

==一：意义与概念==

### 磁盘上的六类文件

| 文件 | 存放内容 | 能不能删 |
|---|---|---|
| **系统表空间** `ibdata1` | 数据字典、undo log、change buffer 的持久化 | ❌ 删了库就废 |
| **独立表空间** `表名.ibd` | 一张表的数据 + 索引 | ❌ |
| **redo log** `ib_logfile*` | 事务的"物理日志"，用于崩溃恢复 | ❌（但可以重建）|
| **undo log** | 事务的"反向操作"，用于回滚和 MVCC | ❌ |
| **binlog** `binlog.000001` | 服务层的"逻辑日志"，用于主从复制和归档 | ⚠️ 可归档，但不能随便删 |
| 双写缓冲 `#ib_16384_0.dblwr` | 防止页写入不完整的"半写" | ❌ |

**redo log 和 binlog 是最容易搞混的一对**，这张表必须记住：

| | redo log | binlog |
|---|---|---|
| 谁产生 | **InnoDB 引擎** | **MySQL 服务层** |
| 内容 | 物理日志："页 X 的偏移 Y 改成了 Z" | 逻辑日志："执行了 `UPDATE ...`" |
| 用途 | **崩溃恢复**（前滚）| **主从复制、数据归档** |
| 写入时机 | 事务进行中持续写 | **事务提交时**写 |
| 循环/追加 | 循环写（固定大小，覆盖）| 追加写（文件递增）|
| 跨引擎 | 只有 InnoDB 有 | 所有引擎都有 |

**为什么两个都要**：redo 保证"已提交的不丢"（崩溃恢复），binlog 保证"能复制给别人、能回滚到某个时间点"。两阶段提交（2PC）保证两者一致——这是 17-04 的重点。

### 后台线程（四个）

| 线程 | 职责 |
|---|---|
| **Master Thread** | 核心调度：每秒刷脏页、合并 change buffer |
| **IO Thread** | 异步读写磁盘（读线程、写线程、日志线程分开）|
| **Purge Thread** | 回收已提交事务的 undo log（`purge` 慢会拖累性能）|
| **Page Cleaner Thread** | 专门刷脏页，减轻 Master 压力 |

`Purge Thread` 值得单独说：MVCC 依赖 undo log，但 undo log 不能永远留着。Purge 线程负责判断"哪些 undo 已经没有事务需要了"，回收掉。**如果 purge 跟不上（长事务导致 undo 无法回收），undo 表空间会暴涨**——这是"长事务"的另一个具体危害。

和 EF Core 的关系：这一层解释了三个运维现象：

1. **磁盘突然爆满**：可能是 `ibdata1` 或 undo 表空间涨了（长事务）。
2. **崩溃后启动慢**：正在做 redo 前滚恢复。
3. **主从延迟**：binlog 太大或从库回放慢。

在 .NET 侧，你能做的是**别开长事务**（别让 `DbContext` 跨 HTTP 请求存活），这直接减少 undo 堆积和 MDL 阻塞。

==二：使用格式==

```sql
SHOW VARIABLES LIKE 'innodb_log_file_size';      -- redo log 单文件大小
SHOW VARIABLES LIKE 'innodb_undo_tablespaces';
SHOW VARIABLES LIKE 'log_bin';                   -- binlog 是否开启
SHOW BINARY LOGS;                                 -- 列出 binlog 文件
PURGE BINARY LOGS BEFORE '2026-11-01';            -- 清理旧 binlog
```

==三：代码实践==

```sql
-- 查看 redo log 与 undo 使用情况
SHOW ENGINE INNODB STATUS\G
-- 关注：Log sequence number / Log flushed up to / Pages flushed up to
-- 三者差距大 = 刷盘压力大

-- 长事务检查（undo 堆积的元凶）
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS 持续秒数
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

==四：总结归纳==

- 三条：redo 是引擎级物理日志（崩溃恢复）、binlog 是服务层逻辑日志（复制归档）；redo 循环写、binlog 追加写；长事务让 undo 无法回收，purge 跟不上会撑爆磁盘。
- 记忆锚：redo 是"施工日志"（改了什么物理页），binlog 是"操作记录"（执行了什么语句）。

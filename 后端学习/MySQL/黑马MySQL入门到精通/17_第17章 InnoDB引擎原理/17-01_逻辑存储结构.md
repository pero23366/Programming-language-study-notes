# InnoDB 逻辑存储结构

> 来源：P133《76. 进阶-InnoDB引擎-逻辑存储结构》 · 档位 C 全新
> 与我已知的关系：你概念里的"表"在 InnoDB 里是五层嵌套的容器——**表空间 → 段 → 区 → 页 → 行**

==一：意义与概念==

数据库要在磁盘上组织 100GB 数据，需要一套"分块"的层级。InnoDB 是五层：

```
表空间 Tablespace（.ibd 文件）
  └─ 段 Segment（叶子段、非叶子段、回滚段）
       └─ 区 Extent（1MB = 64 个页）
            └─ 页 Page（16KB，磁盘 IO 的基本单位）
                 └─ 行 Row（实际数据）
```

### 逐层解释

| 层级 | 大小 | 作用 | 关键点 |
|---|---|---|---|
| **表空间** | 一个 `.ibd` 文件 | 存一张表的**数据 + 索引 + 表结构** | 8.0 默认每表一个文件 |
| **段** | 由多个区组成 | 按用途划分：叶子段、非叶子段、回滚段 | B+ 树的叶子/非叶子分开存 |
| **区** | **1MB = 64 页** | 分配空间的最小单位 | 一次分配 1MB，避免频繁申请 |
| **页** | **16KB** | **磁盘 IO 的最小单位** | 所有读写以页为单位 |
| **行** | 变长 | 实际记录 | 有 `COMPACT`/`DYNAMIC` 等格式 |

### 为什么"页 16KB"这件事极其重要

1. **一次 IO 读 16KB**，即使你只查一行，也是读一页。所以"一行小"意味着"一页能放更多行"，扫描更快——这是 `VARCHAR` 不要盲目定长、大字段用 `TEXT` 分离存储的原因。
2. **B+ 树的高度按页计算**：11-02 里算的"1170 个 key/页"就是以 16KB 为基准。
3. **`innodb_page_size` 可改**（4K/8K/16K/32K/64K），但建库后不能改，生产上默认 16KB 是绝大多数场景的最优。

### 段的设计意图

一个 B+ 树有两个段：**叶子段**（存数据）和**非叶子段**（存索引项）。分开的原因是它们的增长模式不同——叶子段会持续增长，非叶子段增长慢。分开管理减少碎片。

**回滚段**（rollback segment）存 undo log，是 MVCC 和事务回滚的基础（17-05 展开）。

和 EF Core 的关系：这一层的知识不直接影响写代码，但解释了三个现象：

1. **为什么"一行 1KB 的表"和"一行 10KB 的表"性能差很多** —— 每页装载行数不同，扫描的页数差 10 倍。
2. **为什么 `TEXT`/`BLOB` 大字段会拖慢查询** —— 大字段溢出到"溢出页"，读一行要多几次 IO（`DYNAMIC` 格式下只存 20 字节指针）。
3. **为什么 `OPTIMIZE TABLE` 有用** —— 它重建表空间、整理碎片。删了大量数据后表文件不缩小，就需要它。

==二：使用格式==

```sql
-- 看表空间文件
SHOW VARIABLES LIKE 'innodb_file_per_table';   -- ON = 每表一个 .ibd

-- 看页大小
SHOW VARIABLES LIKE 'innodb_page_size';

-- 看表空间使用情况（8.0）
SELECT * FROM information_schema.innodb_tablespaces WHERE name LIKE 'demo/%';
```

==三：代码实践==

```sql
-- 碎片整理（会重建表，锁表，慎用）
ALTER TABLE t ENGINE=InnoDB;      -- 等价于重建
OPTIMIZE TABLE t;                 -- 官方推荐写法

-- 查看碎片情况
SELECT table_name, data_length, data_free
FROM information_schema.tables
WHERE table_schema='demo';
-- data_free 很大 = 碎片多
```

==四：总结归纳==

- 三条：五层结构"表空间→段→区(1MB)→页(16KB)→行"；**页是 IO 最小单位**，一页装多少行决定扫描效率；大字段溢出到单独页。
- 记忆锚：InnoDB 是"一个文件柜（表空间），里面按抽屉（区）分，抽屉里放盒子（页），盒子里装东西（行）"。

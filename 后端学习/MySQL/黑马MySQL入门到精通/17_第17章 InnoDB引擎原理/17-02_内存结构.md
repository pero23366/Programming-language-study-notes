# InnoDB 内存结构

> 来源：P134–P135《77–78. 进阶-InnoDB引擎-架构-内存结构1 / 2》 · 档位 C 全新
> 与我已知的关系：C# 有 GC 管理内存，InnoDB 的 Buffer Pool 是"自己手写的缓存层"——**数据库快不快，一半看它**

==一：意义与概念==

InnoDB 的内存分四块，最重要的是第一块：

```
┌──────────────────────────────────────────┐
│ Buffer Pool（缓冲池）  ← 绝对主力，占 70~80% │
├──────────────────────────────────────────┤
│ Change Buffer（写缓冲）                    │
├──────────────────────────────────────────┤
│ Adaptive Hash Index（自适应哈希）           │
├──────────────────────────────────────────┤
│ Log Buffer（日志缓冲）                     │
└──────────────────────────────────────────┘
```

### 1. Buffer Pool：把"磁盘上的页"缓存到内存

**核心机制**：InnoDB 以**页**为单位把数据从磁盘读到 Buffer Pool，之后所有读写都在内存里做，改完的页叫"脏页"，后台线程异步刷回磁盘。

- 读：先查 Buffer Pool，命中就直接返回（内存速度）；不命中才读磁盘（慢 10 万倍）。
- 写：改 Buffer Pool 里的页 + 写 redo log，**不立即刷盘**（这就是"WAL"）。

**为什么它是性能命门**：`innodb_buffer_pool_size` 决定能缓存多少数据。如果库有 10GB 数据、Buffer Pool 只有 1GB，那 90% 的查询都要读磁盘。**这是 MySQL 最重要的一个参数**，生产上通常设为物理内存的 50%~70%。

内部结构（了解）：

| 组件 | 作用 |
|---|---|
| **页链表（LRU 变体）** | 管理哪些页留在内存。InnoDB 把 LRU 分成 young（热）和 old（冷）两段，防止全表扫描把热数据挤出去 |
| **Free List** | 空闲页 |
| **Flush List** | 脏页（等待刷盘）|

**LRU 的分段设计**很聪明：新读入的页先放 old 区尾部，只有在 old 区待够 `innodb_old_blocks_time`（默认 1 秒）后再次被访问，才升到 young 区。这样"一次性全表扫描"不会污染热数据。

### 2. Change Buffer：延迟"非唯一二级索引"的写入

场景：`INSERT` 一行，要更新 3 个二级索引。如果这些索引页不在内存里，就得先读磁盘 → 改 → 再写。Change Buffer 把这些"索引页不在内存"的修改**先记在内存**，等该页被读入时再合并（merge）。

**限制**：只对**非唯一二级索引**有效。唯一索引必须立即读页校验唯一性，没法延迟。

这条限制有个实践推论：**唯一索引比普通索引写入更慢**。所以"为了性能，能不建唯一索引就不建"是个真实取舍（当然正确性优先）。

### 3. Adaptive Hash Index（AHI）

InnoDB 观察哪些索引被**频繁等值查询**，自动在内存里给它们建 hash 索引，加速查找。全自动，你管不了，只能开/关（`innodb_adaptive_hash_index`）。

### 4. Log Buffer：redo log 的内存缓冲

写 redo log 前先写到 Log Buffer，再按策略刷盘（`innodb_flush_log_at_trx_commit` 控制）。这个参数决定"提交时是否立即刷盘"，直接影响**持久性 vs 性能**：

| 值 | 行为 | 风险 |
|---|---|---|
| `1`（默认）| 每次 `COMMIT` 都刷盘 | 最安全，最慢 |
| `0` | 每秒刷一次 | 宕机丢 1 秒数据 |
| `2` | 写到 OS 缓存，每秒刷 | 宕机（非断电）不丢 |

和 EF Core 的关系：`innodb_buffer_pool_size` 是运维参数，但你会在一个地方间接感受到它——**第一次查询慢、后续查询快**（因为第一次没命中缓存）。这就是"缓存预热"问题。如果你的服务重启后第一波请求特别慢，不是 EF Core 的锅，是 Buffer Pool 冷的。

==二：使用格式==

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';       -- 缓冲池大小（字节）
SHOW VARIABLES LIKE 'innodb_change_buffer_max_size'; -- Change Buffer 占比
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';

SHOW ENGINE INNODB STATUS\G    -- 看 Buffer Pool 命中率等
```

==三：代码实践==

```sql
-- 命中率估算（每小时重置一次统计）
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';  -- 逻辑读次数
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';          -- 物理读次数
-- 命中率 = 1 - reads / read_requests，正常应 > 99%
```

==四：总结归纳==

- 三条：Buffer Pool 缓存页、决定命中率，是最重要的参数；Change Buffer 只对非唯一二级索引有效；Log Buffer 的刷盘策略决定持久性与性能的取舍。
- 记忆锚：Buffer Pool 是"数据库的桌面"，常用资料放手边，不常用的回档案柜找。

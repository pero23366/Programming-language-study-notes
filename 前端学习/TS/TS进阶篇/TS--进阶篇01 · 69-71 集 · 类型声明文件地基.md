==一：概念==

## 1. 69 集：要解决的病 —— TS 只认识 TS（7'10"）

先把病说清楚，否则 `.d.ts` 像个凭空冒出来的东西。

### 1.1 一个你每天都在用、却从没想过的事实

```ts
document.getElementById('app')      // ← document 是哪来的？你没声明过
localStorage.setItem('k', 'v')      // ← localStorage 呢？
arr.filter(x => x > 1)              // ← filter 的方法签名呢？
```

TS 是**从零开始**的一门语言，它凭什么认识浏览器？凭什么认识 `Array.prototype.filter`？

答案：**这些类型全是别人提前写好的 `.d.ts`，编译器启动时自动加载。**

### 1.2 反过来：JS 库进了 TS 项目会怎样

```js
// utils.js —— 一个你三年前写的工具文件，纯 JS
export function formatDate(d) { return d.toISOString().slice(0, 10) }
```

```ts
// main.ts
import { formatDate } from './utils'
formatDate(123)        // ← TS 会报错吗？
```

**答案：不会报错，而且 `d` 的类型是 `any`。** 因为 TS 读得懂 `.js` 的**语法**，但读不到任何**类型信息** —— JS 文件里根本没有类型。

> ⭐ 这就是本章要解决的病：
> **TS 的语言能力只覆盖 `.ts`；一旦跨进 JS 的地盘，所有类型检查瞬间归零，退回 `any`。**

### 1.3 C# 里为什么没这个问题

| | C# | TS |
|---|---|---|
| 编译产物 | `.dll` | `.js` |
| 类型信息在哪 | **`.dll` 的元数据里**（PE metadata） | **编译后全部删除** |
| 引用一个库 | `AddReference` 读元数据 | ❌ `.js` 里没有元数据可读 |
| 类型从哪来 | `public` 修饰符自动导出 | **得另找一个文件单独写** |

⭐ **这一格是整章的根**：

> **C# 的 `.dll` 自带类型信息，所以「引用」就够了。**
> **JS 的 `.js` 被剥得只剩逻辑，所以类型必须另外找个地方住 —— 那个地方就是 `.d.ts`。**

### 1.4 `.d.ts` 到底是什么

**它是一份"承诺书"**：我（人类）向你（编译器）保证，运行时真的存在这个函数、这个类、这个全局变量，它们的形状是这样的。你（编译器）不用管实现，只管按我说的检查。

```ts
// utils.d.ts —— 只有形状，没有一行实现
export function formatDate(d: Date): string
```

⚠️ 注意最后**没有 `{}`**。这不是省略，是**语法规定**：`.d.ts` 是「环境声明（ambient）」，**不允许有实现体**。

> **一句话**：`.d.ts` = 给一段真实存在的 JS 代码，配一张**类型名片**。

## 2. 70 集：TS 的两种文件类型（6'30"）🔥🔥

这一集只有 6 分半，但它是**全章最值钱的一集**，因为它决定你以后「怎么把类型给别人」。

### 2.1 逐项对比

| | `.ts`（实现文件） | `.d.ts`（类型声明文件） |
|---|---|---|
| 能写逻辑吗 | ✅ 能 | ❌ **不能**（只有签名） |
| 编译产出 | `xxx.js` | **什么都不产出** |
| 运行时会加载吗 | ✅ 会 | ❌ **永远不会**（它只给编译器看） |
| 里面要写 `declare` 吗 | ❌ 写了报错 | **不用写**（整个文件默认就是 declare 环境） |
| 典型内容 | 函数体、`console.log`、`if` | `interface` / `type` / `declare` |
| 能不能被 `import` | ✅ | ✅（只能拿到类型） |
| 谁写它 | 业务开发者 | 库作者 / 老项目迁移者 |

### 2.2 ⭐ 最关键的一行：编译产物对比

```
src/
├── main.ts        →  main.js         ✅ 有产物
├── types.d.ts     →  （没有产物）      ❌ 消失
└── utils.ts       →  utils.js        ✅ 有产物
```

**这就是 `.d.ts` 存在的全部意义**：它能在**不增加任何运行时体积**的前提下，携带类型信息。

> **C# 对照**：`.d.ts` ≈ **引用程序集（reference assembly）**。
> .NET 里 `ref/*.dll` 也只有签名没有 IL 实现，只用于编译期。**思路完全一致**，区别在于 C# 的 `ref dll` 是编译器自动剥出来的，TS 的 `.d.ts` 得**手写**（或者用 `tsc --declaration` 自动生成）。

### 2.3 `--declaration`：让 `.ts` 自动产出 `.d.ts`

既然手写累，TS 提供了自动生成：

```bash
tsc utils.ts --declaration
# 产出 utils.js（给人跑）+ utils.d.ts（给 TS 看）
```

```ts
// utils.ts（你写的）
export function formatDate(d: Date): string {
  return d.toISOString().slice(0, 10)
}
```

```ts
// utils.d.ts（自动生成的）—— 函数体被剥掉了
export declare function formatDate(d: Date): string;
```

⭐ **注意两个细节**：
1. 自动生成时，`declare` 是**写出来的**（因为这个文件是由实现推导的，得声明一下）。手写时不用写。
2. 参数名 `d` 保留了，但**没有任何意义** —— 类型才重要。

> **这条命令是你以后写 npm 包的第一课**：`"declaration": true` 一开，发布时 `.js` + `.d.ts` 一起给，用户就有类型提示了 —— **这就是「库有没有类型」的真相**。

### 2.4 ⚠️ 坑：`.ts` 和同名 `.d.ts` 不能并存

```
utils.ts
utils.d.ts      ← 同一个目录下同名
```

`import './utils'` 会**优先解析 `.ts`**，`.d.ts` 被静默忽略。你以为改的是声明，其实编译器根本没读它。

> **实测**：我建了 `a.ts` + `a.d.ts`，`import './a'` 报
> `TS2724: '"./a"' has no exported member named 'A'. Did you mean 'a'?`
> —— 它读的是 `a.ts`，那里没有 `A`。

**工程规矩**：一个模块要么 `.ts`，要么 `.js + .d.ts`，**不要三个都放**。

## 3. 71 集：内置类型声明文件（5'27"）

### 3.1 它们住在哪

**TS 5.x（课程年代的版本）**：

```
node_modules/typescript/lib/
├── lib.es5.d.ts            ← ES5 全部内置对象（Array / String / Object…）
├── lib.es2015.d.ts         ← Promise / Map / Set / Symbol…
├── lib.es2020.d.ts         ← BigInt / globalThis…
├── lib.dom.d.ts            ← ⭐ DOM（document / window / HTMLElement / Event…）
├── lib.dom.iterable.d.ts   ← DOM 集合的可迭代类型
├── lib.scripthost.d.ts     ← WSH 宿主环境
└── ...（几十个文件）
```

⭐ **`lib.dom.d.ts` 是全世界最长的类型文件之一**（3 万行以上）。你在 VS Code 里对 `document.` 按 `Ctrl+Space` 弹出的每一条提示，都来自它。

⚠️ **你的机器上和这个不一样**：你装的是 **TypeScript 7.0.2（Go 重写版）**，内置声明**打包进可执行文件**了，`node_modules/typescript/lib/` 下只有 5 个文件，没有 `lib.dom.d.ts`。

**但不影响行为** —— 我在你的环境实测过，`--lib es5` 一样能触发同一条报错。**文件看不见，机制没变。**

### 3.2 `lib` 选项：决定「你认为世界有什么」

`tsconfig.json` 里的 `lib` 字段，就是**选择加载哪几个内置声明文件**。

| 场景              | `lib` 该写什么                          | 不写的后果                                    |
| --------------- | ----------------------------------- | ---------------------------------------- |
| 浏览器项目（CRA/Vite） | `["dom", "dom.iterable", "esnext"]` | 可能缺 `Promise` / 缺 `document`             |
| Node 后端项目       | `["esnext"]`                        | 有了 `document` 类型 → **写了浏览器代码不会报错，跑起来才炸** |
| Web Worker      | `["webworker", "esnext"]`           | `window` 存在但运行时没有                        |
| 库作者（跨端）         | **不写**（让它跟随 `target`）               | 会把宿主环境写死                                 |

⭐ **`lib` 的默认值取决于 `target`**（这个默认规则很反直觉）：

| `target` | 默认 `lib` |
|---|---|
| `ES5` | `["DOM", "ES5", "ScriptHost"]` |
| `ES2015` | `["DOM", "ES2015", "ScriptHost"]` |
| `ESNext` | `["DOM", "ESNext", "ScriptHost"]` |

⚠️ **注意 `DOM` 是默认带上的**。这就是为什么你**什么都没配**，`document` 也能用。

### 3.3 ⭐ 反直觉实验：把 `DOM` 摘掉

```ts
// dom.ts
document.title = "hi"
```

```bash
$ tsc --noEmit --lib es5 dom.ts
```

```
dom.ts(1,1): error TS2584: Cannot find name 'document'.
Do you need to change your target library?
Try changing the 'lib' compiler option to include 'dom'.
```

⭐ **报错信息自己把答案说出来了**（`include 'dom'`）。TS 的报错文案质量在编译器里算顶尖的，**学会读报错 = 学会半个 TS**。

> **这个实验的价值**：你终于亲眼看见「`document` 有类型」不是魔法，是**一个可以关掉的开关**。

### 3.4 三斜线指令：单个文件级别的「引入声明」

除了 tsconfig 的 `lib`，还能在文件顶部单独引：

```ts
/// <reference types="node" />        // ← 引入 @types/node 的全局声明
/// <reference lib="dom" />           // ← 引入内置 DOM 声明
```

⚠️ **只在「类型层面」生效，不改编译目标**。这类 `///` 指令在 78 集的 `react-app-env.d.ts` 里会再出现一次 —— 那时候你就知道它是干嘛的了。

## 4. ⭐ 一个必须先立住的判断：`.d.ts` 是「全局」还是「模块」

这是 73 集的核心坑，但 71 集就该埋下伏笔。

**规则只有一条**：

> **`.d.ts` 顶层只要出现 `import` 或 `export`，整个文件就变成「模块」；否则它是「全局脚本」。**

| 写法 | 身份 | 里面的 `interface Foo` 谁能用 |
|---|---|---|
| `interface Foo { … }` | **全局** | 整个项目**任何文件**不用 import |
| `export interface Foo { … }` | **模块** | **必须** `import { Foo } from './xxx'` |

⚠️ **最坑的地方**：这两者的**语法长得几乎一样**，只差一个 `export`，行为天差地别。而且搞错了**不会报"你写错了"**，只会报「找不到名字」，让你去别处找原因。

```ts
// global.d.ts —— 没有 export
interface G { id: number }
```

```ts
// use.ts
const x: G = { id: 1 }       // ✅ 直接能用
```

**加一个 `export` 之后**：

```ts
// global.d.ts
export interface G { id: number }
```

```ts
// use.ts
const x: G = { id: 1 }       // ❌ error TS2304: Cannot find name 'G'.
```

**实测报错原文**：`use.ts(1,10): error TS2304: Cannot find name 'G'.`

> ⭐ **记住这个因果**：
> **你为了「导出类型」加的 `export`，恰恰把它从全局踢出去了。**
> 想两全 → 用 `declare global { }`（73 集讲）。

==二：格式==

## 1. `.ts` vs `.d.ts` 速查表

| 维度 | `.ts` | `.d.ts` |
|---|---|---|
| 全称 | TypeScript 实现文件 | TypeScript Declaration File |
| 中文 | 实现文件 / 源码文件 | 类型声明文件 / 声明文件 |
| 含实现 | ✅ | ❌ |
| 编译产物 | `.js`（+ 可选 `.d.ts`） | **无** |
| 运行时加载 | ✅ | ❌ |
| 内部是否 ambient | ❌ | ✅（默认 `declare`） |
| 典型文件名 | `main.ts` / `App.tsx` | `types.d.ts` / `global.d.ts` / `xxx.d.ts` |
| 谁写 | 业务代码 | 库作者 / 迁移老项目 |

## 2. `.d.ts` 里能写 / 不能写

| ✅ 能写 | ❌ 不能写 |
|---|---|
| `interface` / `type` | 函数体 `{ return x }` |
| `declare function f(a: T): R` | `if` / `for` / `while` |
| `declare const x: T` | `console.log()` |
| `declare class C { … }` | 赋值 `x = 1`（`declare const x = 1` 也不行） |
| `declare module 'xxx' { }` | `export default function() { … }` |
| `declare global { }` | 任何有副作用的语句 |
| `export type` / `export interface` | — |

⚠️ **写了实现会报**：`TS1183: An implementation cannot be declared in ambient contexts.`（实测原文）

## 3. `lib` 常用组合速查

| 项目类型 | `lib` | 备注 |
|---|---|---|
| CRA / Vite（浏览器） | `["dom", "dom.iterable", "esnext"]` | 课程用这个 |
| Next.js | `["dom", "dom.iterable", "esnext"]` | 同浏览器 |
| Node 服务端 | `["esnext"]` | **故意不给 dom** |
| 同构库 | 不写 | 跟随 `target` |
| Web Worker | `["webworker", "esnext"]` | 没有 `window` |

## 4. 命令对照

| 目的 | 命令 |
|---|---|
| 只查类型不产出 | `tsc --noEmit` |
| 生成 `.d.ts` | `tsc xxx.ts --declaration` |
| **只**生成 `.d.ts`（不产 JS） | `tsc xxx.ts --declaration --emitDeclarationOnly` |
| 指定 lib 验证 | `tsc --noEmit --lib es5 xxx.ts` |
| 看当前生效的配置 | `tsc --showConfig` |
| 看这个文件被谁引进来 | `tsc --explainFiles` |

⚠️ **你的环境实测**：`TS 7.0.2` 在**没有 tsconfig.json** 的目录里跑 `tsc --noEmit` 会**打印帮助并退出 1**，不像 TS 5.x 那样编译当前目录。所以验证时必须**显式列文件名**：`tsc --noEmit a.ts b.d.ts`。

## 3. 实验三：`export` 如何让全局声明失效（经典坑）

```ts
// global.d.ts（版本 A）
interface G { id: number }
```

```ts
// use.ts
const x: G = { id: 1 }
console.log(x)
```

```bash
tsc --noEmit use.ts global.d.ts     # 注意必须显式列出两个文件
```

**✅ 通过（exit 0）** —— 全局生效。

现在把 `global.d.ts` 改成：

```ts
// global.d.ts（版本 B）
export interface G { id: number }
```

```bash
tsc --noEmit use.ts global.d.ts
```

**实测输出**：

```
use.ts(1,10): error TS2304: Cannot find name 'G'.
```

⭐ **只加了一个 `export`，全局就没了。** 这不是 bug，是 ES 模块规范：**文件一旦是模块，作用域就封闭了。**

> **C# 对照**：这就像你在一个 `internal` 类里加了个 `public` —— 听着更开放了，实际上被命名空间关住了。**"导出"和"全局"是两件不同的事**，TS 里它们**互斥**。

## 5. 实验五（选做）：让 `tsc` 自己生成 `.d.ts`

```ts

export function formatDate(d: Date): string {
```

```bash
tsc utils.ts --declaration
```

==四：总结==

## 1. 一句话记住三个

| 集 | 一句话 |
|---|---|
| 69 | **JS 没有元数据，所以类型得写在 `.d.ts` 里。** |
| 70 | **`.d.ts` 编译后什么都不产出 —— 这就是它存在的理由。** |
| 71 | **`document` 有类型，是因为 `lib.dom.d.ts` 被加载了，而这只是一个可以关掉的开关。** |

## 2. ⭐⭐ 本篇要背的（4 条）

1. **两种文件类型**：`.ts` 有实现有产物；`.d.ts` 只有签名、**零产物**、运行时不存在。
2. **`.d.ts` ≈ C# 的引用程序集**。区别：C# 自动剥，TS 要手写或用 `--declaration` 生成。
3. **`.d.ts` 的身份由 `export` 决定**：无 `export` = 全局；有 `export` = 模块。**二者互斥**。
4. **`lib` 控制"你认为世界有什么"**，默认值跟 `target` 走，且**默认包含 `DOM`**。

## 3. ⭐ 收敛时刻：这一篇把前面哪几条线接到了同一个点

**回到 49-68 集 §7.3**：你当时「拆开 `Partial` 看内脏」，看到的是：

**那行代码住在哪？** 住在 `lib.es5.d.ts` 里 —— **一个 `.d.ts` 文件**。

> ⭐ **一句话收口**：
> **你以为 49-68 集学的是"怎么写类型"；其实你学的每一条，都是从某个 `.d.ts` 里读出来的"别人的类型"。**
> **这一篇告诉你那些文件在哪 —— 从此 `F12` 能跳到定义了。**

**再往回收一层**（接 TS--01 的类型擦除）：

| 因为 | 所以 |
|---|---|
| 类型运行时消失 | 不能靠运行时反射拿类型 |
| 不能靠反射 | 必须有一个**独立于 `.js` 的载体**存类型 |
| 需要独立载体 | 于是有了 `.d.ts` |

⭐ **`.d.ts` 不是"额外加的一个功能"，是"类型擦除"这个决定的必然产物。**

## 4. 静默失败清单（本篇 4 条）

| # | 陷阱 | 表现 | 怎么防 |
|---|---|---|---|
| 1 | `.ts` 与同名 `.d.ts` 并存 | `.d.ts` 被**静默忽略**，你改了半天没生效 | 一个模块只留一种 |
| 2 | `.d.ts` 里加了 `export` | 全局声明**静默失效**，报 `TS2304` 让你去别处找 | 想全局就**一个 `export` 都不要**，或用 `declare global` |
| 3 | `.d.ts` 没被任何文件引用 | 编译器**根本不读它**，全局声明形同虚设 | 放进 `include` 范围，或写 `/// <reference path="…" />` |
| 4 | `lib` 里带了 `dom` | 在 Node 项目里写 `document` **编译通过，运行时炸** | Node 项目 `lib: ["esnext"]` |

> ⚠️ **这一篇的 4 条全都是"不报错型"失败** —— 编译器不会说"你配错了"，只会说"找不到名字"。
> **这正是 JS 世界的老毛病**：从 JS 200 集一路带过来的「**静默失败**」暗线，在 TS 里换了个形式继续存在。

## 5. C# 类比可用度（本篇新增）

| 概念                | C# 对应                                      | 可用度 | 说明                                              |
| ----------------- | ------------------------------------------ | --- | ----------------------------------------------- |
| `.d.ts` 整体        | 引用程序集（`ref/*.dll`）                         | ⭐⭐⭐ | **思路完全一致**：只有签名、无实现、只给编译器看                      |
| `--declaration`   | `dotnet build /p:ProduceReferenceAssembly` | ⭐⭐  | 都是自动剥离实现，但 C# 是默认行为                             |
| `lib` 选项          | `TargetFramework` + 引用的 BCL 程序集            | ⭐⭐  | 都是"你认为平台提供什么"                                   |
| `declare`         | `DllImport` / `extern` 声明                  | ⭐⭐  | 都是"我保证运行时存在，别问实现"                               |
| 全局 `.d.ts`        | 全局 `using static` / 无命名空间的 `public class`  | ⭐   | 概念像，但 TS 的全局是"污染式"的                             |
| 内置 `lib.dom.d.ts` | .NET 的 `System.*.dll` 元数据                  | ⭐⭐  | 都是平台自带、自动加载                                     |
| 模块 vs 全局          | 命名空间 vs 全局命名空间                             | ⭐   | **TS 只要有 `export` 就"自动关进模块"，C# 得自己包 namespace** |

⭐ **统计：7 项里 1 项 ⭐⭐⭐、4 项 ⭐⭐、2 项 ⭐。**
**这是整章类比可用度最高的一篇** —— 因为 `.d.ts` 和引用程序集在**设计意图上就是同一件事**。往后走（React 篇）会迅速掉到 ⭐ 甚至 ❌。

## 1. 87 集：类组件的状态与事件（8'56"）

### 1.1 `state` 的三条铁律

```tsx
type State = { count: number }

class Counter extends React.Component<{}, State> {
  state: State = { count: 0 }
}
```

| 铁律 | 原因 |
|---|---|
| **① `state` 不能直接改** | `this.state.count++` 不触发渲染（React 不知道变了） |
| **② 只能用 `setState`** | 它才会通知 React "数据变了，重渲染" |
| **③ `setState` 是"合并"不是"替换"** | 你只传 `{count: 0}`，其他字段**不会丢** |

⚠️ **铁律 ③ 最容易记错**（因为 `useState` 的行为**相反**）：

```tsx
// 类组件 setState：浅合并
this.setState({ count: 1 })
// state = { count: 1, name: 'x' }   ← name 还在！

// 函数组件 useState：整体替换
setState({ count: 1 })
// state = { count: 1 }              ← name 没了！
```

⭐ **这是两套 API 最容易混的一点**。**类组件合并，hooks 替换。**

### 1.2 ⭐ `setState` 的两种写法（差别很大）

```tsx
// 写法 A：对象
this.setState({ count: this.state.count + 1 })

// 写法 B：函数
this.setState(prev => ({ count: prev.count + 1 }))
```

**在"连续调用"时，两者结果完全不同**：

```tsx
// A 连点两次
this.setState({ count: this.state.count + 1 })   // 读到的都是旧值 0
this.setState({ count: this.state.count + 1 })   // → 最终 count = 1 ❌

// B 连点两次
this.setState(prev => ({ count: prev.count + 1 }))   // prev = 0 → 1
this.setState(prev => ({ count: prev.count + 1 }))   // prev = 1 → 2 ✅
```

⭐ **原因**：`setState` 是**异步批处理**的。两次调用之间 `this.state` 还没更新，所以 A 读到两次 `0`。

> **C# 对照**：像 `Interlocked.Increment` vs `count = count + 1`。
> `count = count + 1` 在并发下会丢更新，`Interlocked` 是"基于当前值原子地加" —— **`setState(prev => ...)` 就是那个 `Interlocked` 版本**（严格说是"串行化"而不是"原子"）。

### 1.3 ⚠️ `this` 为什么会丢（类组件最大的坑）

```tsx
class Counter extends React.Component<{}, State> {
  state: State = { count: 0 }

  handleClick() {
    this.setState({ count: this.state.count + 1 })   // ← this 是 undefined！
  }

  render() {
    return <button onClick={this.handleClick}>+1</button>
  }
}
```

**运行时报**：`Cannot read properties of undefined (reading 'setState')`

⭐ **原因回扣 JS 192-194 集**：

| JS 阶段你学的 | 这里发生的事 |
|---|---|
| `this` 由**调用方式**决定 | `onClick={this.handleClick}` 把函数**脱开对象**传出去 |
| 没有"点"就是 `window` | React 调用时是 `fn(e)`，**没有点** → 严格模式下 `this = undefined` |

**三种修法**：

```tsx
// ① 构造器里 bind（老写法）
constructor(props: {}) {
  super(props)
  this.handleClick = this.handleClick.bind(this)
}

// ② 类字段箭头函数（✅ 推荐）
handleClick = () => { this.setState(...) }

// ③ 内联箭头（每次都新建函数，不推荐）
<button onClick={() => this.handleClick()}>
```

⭐ **② 为什么能解决**：**箭头函数没有自己的 `this`**，它捕获定义处的 `this`（也就是实例）。**回扣 JS 192 集那条"箭头函数不参与 `this` 绑定"。**

### 1.4 事件处理函数的类型

```tsx
handleClick = (e: React.MouseEvent<HTMLButtonElement>) => {
  console.log(e.currentTarget.disabled)
}

handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  this.setState({ text: e.target.value })
}
```

⚠️ **和函数组件唯一的区别**：**必须手写类型**。因为类字段不经过 JSX 的上下文推断。

```tsx
// 函数组件：内联能自动推断
<button onClick={(e) => {}} />      // e 自动有类型

// 类组件：写成字段就推断不了
handleClick = (e) => {}              // ❌ TS7006
```

### 2.1 需求

| 功能 | 交互 |
|---|---|
| 展示任务列表 | 列表渲染，完成的加删除线 |
| 添加任务 | 输入框 + 按钮 / 回车 |
| 切换完成状态 | 点复选框 |
| 显示未完成数量 | 派生数据 |

### 2.2 ⭐ 数据设计（先想清楚再写代码）

```ts
type Task = {
  id: number
  name: string
  done: boolean
}
```

**为什么这三个字段？**

| 字段 | 为什么必须有 |
|---|---|
| `id` | **列表渲染的 `key`**（89 集讲为什么） |
| `name` | 任务内容 |
| `done` | 完成状态 |

⚠️ **不要存的字段**：

| 诱惑 | 为什么不能存 |
|---|---|
| `unfinishedCount` | **能算出来的不要存**（回扣 JS 173-175 集铁律） |
| `index` | 下标会变（删除后就错位了） |
| `isEditing` | 如果不是所有任务都需要，会浪费；确实需要再存 |

> ⭐ **回扣 JS 173-175 集**：你当时学的两条铁律 —— **「能算出来的不要存」「改完数据必须重新渲染」** —— 在 React 里变成了**框架强制的**：
> - 前者：`const unfinished = tasks.filter(t => !t.done).length` 每次渲染现算
> - 后者：`setTasks(...)` 自动重渲染

### 2.3 组件拆分

```
App
├── 状态：tasks: Task[]
├── <新增输入区>
│   └── 受控 input + 添加按钮
└── <列表区>
    └── TaskItem × N（props: task, onToggle）
```

**拆分的判据（很重要）**：

| 判据 | 说明 |
|---|---|
| **有独立状态** → 拆 | 没有就不拆 |
| **会被复用** → 拆 | 列表项一定要拆 |
| **能让父组件变短** → 拆 | 但别为了拆而拆 |

⭐ **课程里拆了两个组件**：`App`（容器 + 状态）和 `TaskItem`（展示 + 回调）。**这是"容器 / 展示"分离的最小版本。**

## 3. 89 集：展示任务列表（15'17"）🔥

### 3.1 第一步：把数据变成状态

```tsx
function App() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, name: '学 TS 声明文件', done: true },
    { id: 2, name: '学 React 类型', done: false },
  ])
  …
}
```

⭐ **`useState<Task[]>` 的泛型**：

| 写法 | 结果 |
|---|---|
| `useState<Task[]>([])` | `tasks: Task[]`，**空数组也有类型** ✅ |
| `useState([])` | `tasks: never[]` ❌ **什么都不能放** |
| `useState<Task[]>()` | `tasks: Task[] \| undefined` ⚠️ 要处理 undefined |

⚠️ **`useState([])` 是最经典的坑**：

```tsx
const [tasks, setTasks] = useState([])     // 推断成 never[]
setTasks([{ id: 1, name: 'a', done: false }])   // ❌ 报错
```

**因为空数组没有任何元素可供推断**，TS 只能取"最窄"的 `never[]`。

> ⭐ **这条和 49-68 集的泛型推断是同一个机制**：**泛型参数推断不出来时，TS 会取"最窄"而不是"最宽"。**

### 3.2 第二步：`map` 渲染（和 JS 174 集一模一样）

```tsx
return (
  <ul>
    {tasks.map(task => (
      <TaskItem key={task.id} task={task} onToggle={handleToggle} />
    ))}
  </ul>
)
```

⭐ **和你在 JS 阶段写的 `map` 渲染几乎一样**，只多了一个 `key`。

### 3.3 ⭐ `key` 到底是什么（必须搞懂）

**`key` 不是 props，是 React 内部用来"认人"的标记。**

```tsx
// 渲染前
[<TaskItem task={a} />, <TaskItem task={b} />]

// 数据变了
[<TaskItem task={a} />, <TaskItem task={newB} />, <TaskItem task={c} />]
```

**React 靠 `key` 判断"哪个是原来那个"**，从而决定「复用 DOM 还是新建 DOM」。

| 写法 | 后果 |
|---|---|
| `key={task.id}` | ✅ 正确：稳定唯一 |
| `key={index}` | ⚠️ **有风险**：删除/排序后会错位，导致输入框内容、动画跑到错误的行 |
| 不写 `key` | ❌ 控制台警告，且性能差 |
| `key={Math.random()}` | ❌ **每次都重建**，性能灾难 |

⚠️ **`key={index}` 什么时候能凑合**：列表**只增不改不排**时勉强可以。**一旦有删除/插入，必炸。**

⭐ **`key` 的坑和 TS 无关**，但**它是最常见的 React 事故来源之一**。课程只说了"要用 id"，没说为什么 —— 这里补上。

### 3.4 第三步：条件渲染（三种写法）

```tsx
// ① 三元：二选一
{task.done ? <s>{task.name}</s> : task.name}

// ② &&：有就显示，没有就不显示
{tasks.length > 0 && <ul>…</ul>}

// ③ 提前 return：整个组件不渲染
if (tasks.length === 0) return <p>暂无任务</p>
```

⚠️ **`&&` 的经典坑**：

```tsx
{tasks.length && <ul>…</ul>}
// 当 length 为 0 时，会渲染出字符串 "0"！
```

⭐ **原因**：`0` 是 falsy，但 **React 会把它当"可渲染内容"渲染出来**（因为 `0` 是合法的 `ReactNode`）。
**修法**：`tasks.length > 0 && …`。

> ⭐ **这条正好是进阶篇05 §1.2 那句的实战**：**`ReactNode` 包含 `number`** —— 所以数字 `0` 会被渲染，而 `null` / `false` 不会。

### 3.5 状态提升：`onToggle` 为什么写在 `App` 里

```tsx
// App（有状态）
function handleToggle(id: number) {
  setTasks(prev =>
    prev.map(t => (t.id === id ? { ...t, done: !t.done } : t))
  )
}

// TaskItem（无状态，只接收回调）
function TaskItem({ task, onToggle }: { task: Task; onToggle: (id: number) => void }) {
  return (
    <li>
      <input type="checkbox" checked={task.done} onChange={() => onToggle(task.id)} />
      {task.name}
    </li>
  )
}
```

⭐ **为什么不能把 `setTasks` 直接传给子组件？**

| 方案 | 问题 |
|---|---|
| 传 `setTasks` | 子组件能**任意改**状态，失控 |
| 传 `onToggle(id)` | 子组件**只能请求**"切换这个"，干什么由父决定 ✅ |

> **这就是"状态提升（lifting state up）"** —— **状态往上提，能力往下传**。
> **C# 类比**：子组件拿到的是**方法调用**（`onToggle(id)`），不是**字段引用**（`setTasks`）。前者是封装，后者是暴露。

==二：格式==

## 1. `useState` 泛型速查

| 写法 | 推断类型 | 何时用 |
|---|---|---|
| `useState(0)` | `number` | 初始值能推断 |
| `useState<string>('')` | `string` | 初始值能推断，但想明确 |
| `useState<Task[]>([])` | `Task[]` | ⭐ **空数组必写** |
| `useState<Task \| null>(null)` | `Task \| null` | 可能没有值 |
| `useState<Task>()` | `Task \| undefined` | ⚠️ 少用 |

## 2. `setState`（类）vs `setX`（hooks）对照

| | 类组件 `setState` | hooks `setX` |
|---|---|---|
| 对象合并 | ✅ **浅合并** | ❌ **整体替换** |
| 函数式更新 | `setState(prev => ({...}))` | `setX(prev => ...)` |
| 异步 | ✅ 批处理 | ✅ 批处理 |
| 读旧值 | `this.state`（可能是旧的） | 闭包里的变量（也可能是旧的） |

## 3. 列表渲染三要素

| 要素 | 写法 | 不写的后果 |
|---|---|---|
| `map` | `tasks.map(...)` | — |
| `key` | `key={task.id}` | ⚠️ 警告 + 性能差 + 状态错位 |
| 返回元素 | `<TaskItem … />` | — |

## 4. 条件渲染对照

| 场景 | 写法 | 坑 |
|---|---|---|
| 二选一 | `cond ? A : B` | — |
| 有才显示 | `cond && A` | ⚠️ `0` 会被渲染 |
| 没数据时 | `if (!len) return <Empty />` | — |
| 两个都可能不显示 | `cond ? A : null` | — |

## 5. 类组件 `this` 三种修法

| 写法 | 推荐度 | 说明 |
|---|---|---|
| `this.fn = this.fn.bind(this)` | ⭐ | 老写法，构造函数里 |
| `fn = () => {}`（类字段） | ⭐⭐⭐ | **推荐** |
| `onClick={() => this.fn()}` | ⭐⭐ | 每次新建函数 |

## 1. 实验一：`setState` 连续调用的差别（类组件）

```tsx
// A 写法
handleAddA = () => {
  this.setState({ count: this.state.count + 1 })
  this.setState({ count: this.state.count + 1 })
}

// B 写法
handleAddB = () => {
  this.setState(prev => ({ count: prev.count + 1 }))
  this.setState(prev => ({ count: prev.count + 1 }))
}
```

**现象**：A 点一次只加 1，B 点一次加 2。

⭐ **一次实验，永久记住"要基于 `prev` 更新"。**

## 3. 实验三：完整任务列表（89 集的最小可运行版）

```tsx
// src/types.ts
export type Task = {
  id: number
  name: string
  done: boolean
}
```

```tsx
// src/TaskItem.tsx
import type { Task } from './types'

type Props = {
  task: Task
  onToggle: (id: number) => void
}

export function TaskItem({ task, onToggle }: Props) {
  return (
    <li style={{ listStyle: 'none', margin: '6px 0' }}>
      <label>
        <input
          type="checkbox"
          checked={task.done}
          onChange={() => onToggle(task.id)}
        />
        <span style={{ textDecoration: task.done ? 'line-through' : 'none' }}>
          {task.name}
        </span>
      </label>
    </li>
  )
}
```

```tsx
// src/App.tsx
import { useState } from 'react'
import { TaskItem } from './TaskItem'
import type { Task } from './types'

export default function App() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, name: '学 TS 声明文件', done: true },
    { id: 2, name: '学 React 类型', done: false },
    { id: 3, name: '写任务列表案例', done: false },
  ])

  function handleToggle(id: number) {
    setTasks(prev =>
      prev.map(t => (t.id === id ? { ...t, done: !t.done } : t))
    )
  }

  const unfinished = tasks.filter(t => !t.done).length

  return (
    <div style={{ padding: 20 }}>
      <h2>任务列表（未完成 {unfinished}）</h2>
      {tasks.length > 0 ? (
        <ul style={{ padding: 0 }}>
          {tasks.map(task => (
            <TaskItem key={task.id} task={task} onToggle={handleToggle} />
          ))}
        </ul>
      ) : (
        <p>暂无任务</p>
      )}
    </div>
  )
}
```

⭐ **这段代码里有 7 个知识点**：

| # | 知识点 | 对应集 |
|---|---|---|
| 1 | `Task` 类型单独放 `types.ts` | 73 / 90 |
| 2 | `useState<Task[]>` 泛型 | 89 |
| 3 | `map` + `key={task.id}` | 89 |
| 4 | `{ ...t, done: !t.done }` **不可变更新** | 89 / 91 |
| 5 | `unfinished` **现算不存** | 88 |
| 6 | `onToggle(id)` **状态提升** | 89 |
| 7 | `tasks.length > 0 &&` 防 `0` 渲染 | 89 |

## 4. 实验四：`key={index}` 的事故现场

```tsx
// ❌ 用 index
{tasks.map((t, i) => <TaskItem key={i} task={t} />)}
```

**怎么复现问题**：

1. 列表渲染 3 个任务，每个 `TaskItem` 里放一个 `<input>`（非受控）
2. 在第一个输入框里打几个字
3. 删除第一个任务
4. **输入框里的字跑到了"原来的第二个"上**

⭐ **原因**：`key` 从 `0,1,2` 变成 `0,1` —— React 认为 `key=0` 的还是同一个组件，**只是 props 换了**，于是**复用了 DOM 和内部状态**。

## 5. 实验五：`0` 被渲染出来

```tsx
const [list, setList] = useState<string[]>([])

return <div>{list.length && <p>有数据</p>}</div>
```

**页面会显示一个 `0`。**

**修法**：

```tsx
return <div>{list.length > 0 && <p>有数据</p>}</div>
```

⭐ **原因在进阶篇05 §1.2**：`ReactNode` 包含 `number`，所以 `0` 是"合法的渲染内容"，而 `false` / `null` / `undefined` 不是。

==四：总结==

## 1. 一句话记住三集

| 集 | 一句话 |
|---|---|
| 87 | **`setState` 异步且合并；连续更新必须用 `prev =>`；类方法里的 `this` 用箭头函数属性救。** |
| 88 | **先设计数据再写代码：`id` 必须有，能算的不要存。** |
| 89 | **`useState<T[]>([])` 泛型不能省，`map` 必须配稳定的 `key`。** |

## 2. ⭐⭐ 本篇要背的（6 条）

1. **`setState` 是浅合并，`setX` 是整体替换** —— 两套 API 最容易混的一点。
2. **连续更新用 `setState(prev => …)` / `setX(prev => …)`**，不要读闭包里的旧值。
3. **类方法里的 `this` 会丢**，用 `handle = () => {}` 类字段解决。
4. **`useState([])` → `never[]`**，空数组必须写泛型。
5. **`key` 必须是稳定的唯一标识**，`index` 在有删除/排序时会错位。
6. **`0 && <X/>` 会渲染出 `0`**，要写 `length > 0 &&`。

## 4. 静默失败清单（本篇 5 条）

| # | 陷阱 | 表现 | 怎么防 |
|---|---|---|---|
| 1 | 直接改 `this.state.count++` | **界面不更新**，值其实变了 | 只用 `setState` |
| 2 | 连续 `setState({count: this.state.count+1})` | 只加 1，**不报错** | 用 `prev =>` |
| 3 | `key={index}` | 删除后**内容错位**，没有报错 | 用 `id` |
| 4 | `{len && <X/>}` | 页面多个 `0` | `len > 0 &&` |
| 5 | `useState([])` | `never[]`，**后续 `setX` 全报错** | 写泛型 |

> ⚠️ **第 1、2、3、4 条全都"不报错"** —— 前两条是"值不对"，后两条是"界面不对"。
> **React 不会告诉你"你写错了"，它只会照着你的意图执行。** 这比 JS 更危险 —— 因为 JS 至少还会 `undefined` 崩一下。

## 5. C# 类比可用度（本篇新增）

| 概念                      | C# 对应                            | 可用度 | 说明                                      |
| ----------------------- | -------------------------------- | --- | --------------------------------------- |
| `state`                 | 字段                               | ⭐⭐⭐ | 一样                                      |
| `setState`              | 字段 setter + `OnPropertyChanged`  | ⭐⭐⭐ | **WPF 的 `INotifyPropertyChanged` 就是这套** |
| `state` 不可变更新           | `record with { }`                | ⭐⭐⭐ | **C# 9 的 `with` 表达式一模一样**               |
| `useState<T>`           | 泛型字段                             | ⭐⭐⭐ | 形似                                      |
| `key`                   | WPF 的 `x:Name` / 元素标识            | ⭐⭐  | 都是"认人"                                  |
| 状态提升                    | 事件回调 `Action<T>`                 | ⭐⭐⭐ | **Blazor 的 `EventCallback<T>` 就是这个**    |
| `{...t, done: !t.done}` | `record with { Done = !t.Done }` | ⭐⭐⭐ | **几乎逐字对应**                              |

⭐ **统计：7 项里 5 项 ⭐⭐⭐、1 项 ⭐⭐。**
⭐ **这一篇是整章类比可用度最高的一篇** —— 因为"状态 + 不可变更新"在 C# 里有 `record with` 和 `INotifyPropertyChanged` **两个直接对应物**。

> **如果你写过 WPF/MVVM：`useState` = 属性 + `PropertyChanged`，`setTasks([...prev, x])` = `record with`。**

==一：概念==

## 1. TS 是什么（01）🔥

### 1.1 官方定义：三个必须同时成立的事实

官方原话：**TypeScript is JavaScript with syntax for types.**（带类型语法的 JavaScript）

三件事必须同时成立，缺一件后面的推论就全歪：

| | 是什么 | C# 对照 |
|---|---|---|
| ① | TS 是 JS 的**超集** —— 合法 JS 几乎都是合法 TS | ❌ 无对应 |
| ② | TS 只加**语法** —— 加的是写代码时的类型标注，不是运行时能力 | C# 加的是 CLR 能力 |
| ③ | TS **没有运行时** —— 没有 TS 虚拟机、没有 TS 运行时库、没有 TS 字节码 | C# 有 IL + CLR + BCL |

**第 ③ 行是这一轮的全部重点。** 把它记成一句对照：

> **C# 的类型活在 CLR 里；TS 的类型活在编辑器里。**

⭐ **这句话为什么值得背一整天**：后面你会遇到至少 20 次「TS 为什么不能 X」。你不需要记 20 条结论 —— 只需要问一句「**这件事需要运行时知道类型吗**」，然后回头看这句话。

### 1.2 ⭐⭐ 本轮唯一的产出：类型的生死四问

这张表是 M1 唯一必须记住的东西。四个问题，四个答案：

| 问题 | C# | TS |
|---|---|---|
| 类型**谁定义** | 源码 | 源码 |
| 类型**谁检查** | 编译器（csc） | 编译器（tsc） |
| 类型**谁执行** | **CLR —— 运行时真的在管** | **没人** |
| 编译后还在吗 | ✅ 完整留在 metadata，`typeof(T)` 随时可拿 | ❌ **一个字都没有** |

**前三行看起来一样，第四行把它们劈成两个世界。**

⭐ **一个 C# 人最容易漏掉的点**：C# 的编译器**同时**是「检查者」和「生产类型信息的人」。TS 的编译器**只是检查者** —— 它检查完就把类型全删了，**不生产任何能用的东西**。

### 1.3 🔵 撞名警报：「编译」在两边不是一个意思

这是本课的**第一个撞名**，必须当场切开：

| | C# 的「编译」 | TS 的「编译」 |
|---|---|---|
| 输入 | `.cs` | `.ts` |
| 干什么 | ① 检查类型 ② **把类型信息编进 metadata** ③ 生成 IL | ① 检查类型 ② **把类型全删掉** ③ 降级语法，生成 JS |
| 产物 | `.dll`（含完整类型信息） | `.js`（**零类型信息**） |
| 能不能反编译出类型 | ✅ 能，`ildasm` 一看就明白 | ❌ 不能，类型在编译那一刻就死了 |

**C# 的编译是「翻译 + 存档」；TS 的编译是「检查 + 销毁」。**

> ⚠️ 这个撞名会一直骗你到后面好几轮。凡是看到「编译后」「编译产物」两个词，都要先问一句：**是 C# 那种编译，还是 TS 这种编译。**

## 2. 为什么需要它（02）🔥🔥 —— 回到你 200 集那条暗线

### 2.1 三个你亲自踩过的场景

你的 JS 笔记里，那条从第 1 集贯穿到第 200 集的主线叫 **「静默失败」**。当时我们总结过一句：

> **别问「会不会报错」，要问「行为是不是我想要的」。**

TS 存在的唯一理由，就是把这条主线切断。三个你亲手踩过的场景：

```js
// ═══ ① 属性名拼错 —— 不报错，只是永远拿不到 ═══
const user = { name: 'pero' };
console.log(user.nmae);        // undefined ← 控制台干净得像没事，页面一片空白

// ═══ ② 参数传错 —— 不报错，只是算错了 ═══
function add(a, b) { return a + b; }
add('1', 2);                   // "12" ← 字符串拼接，安静地错

// ═══ ③ 该有值的没有 —— 不报错，直到你访问它的属性 ═══
const list = null;
list.forEach(x => x);          // 到这里才炸，而且离出错的地方已经很远
```

**共同结构**：写完不说、启动不说、**跑到那一步才说，甚至永远不说**（第 ① 种）。

⭐ 第 ① 种最毒 —— 它连「延迟报错」都不是，它是**永远不报**。你只会觉得「这数据怎么是空的」。

### 2.2 C# 为什么不会这样

因为 C# 有一道**编译**：类型不对，`dotnet build` 直接红，代码根本跑不起来。

```csharp
var user = new { name = "pero" };
Console.WriteLine(user.nmae);   // ❌ 编译不过：匿名类型没有 nmae 成员
```

**你在 C# 里从来没遇到「拼错属性名还能跑」这种事** —— 不是因为你小心，是编译器不让。

### 2.3 一句话概括 TS 的全部生意

> **TS 不让你不犯错。TS 让你早犯错。**

它把错误的**发生时刻**从「运行时」挪到「写代码时」。仅此一件事，没有别的。

⭐ **所以别指望 TS 让代码变「安全」** —— 它只让错误**变早**，不让错误**变少**。这个区别在第 4 节会变得非常具体。

## 3. 三个实惠（03）

### 3.1 排序：最值钱的不是「报错」

课程讲这部分时说得最轻，但实际价值排序是这样的：

| # | 实惠 | 什么时候兑现 | 价值 |
|---|---|---|---|
| 1 | 早期报错 | 只有出错那天 | 🟡 中 |
| 2 | **补全与类型提示** | **每敲一次键盘** | 🟢 **最高** |
| 3 | **安全重构** | 每次改字段名 | 🟢 **高** |

**第 2、3 项才是天天能感觉到的东西**，而课程只是一句带过。

### 3.2 为什么「补全」比「报错」值钱

**没有 TS 的世界**（你过去 200 集）：想看 `user` 上有哪些字段，得往回翻定义、翻接口文档、或者 `console.log(user)` 打出来瞄一眼。**每次都要离开当前代码。**

**有 TS 的世界**：`user.` 一敲，`name` / `age` / `email` 全列出来，还带注释。

⭐ **这不是「少打几个字」，是「不用离开心流」。** 一天省下来的不是按键，是**上下文切换**。

同理第 3 项：把字段从 `username` 改成 `name`，JS 里只能全局搜字符串然后祈祷没漏；TS 里 F2 一按，全部引用一起改，**改错立刻红**。

## 4. ⭐⭐ 核心：类型擦除（Type Erasure）

### 4.1 定义

> **TS 的类型只存在于源码里。编译成 JS 时，所有类型语法被整段删掉，产物里一个字都不剩。**

**这不是「优化掉了」，是设计前提** —— 浏览器和 Node 只认 JS，TS 若在产物里留下任何类型痕迹，它就不再是 JS 的超集了（回扣 §1.1 第 ① 条）。

### 4.2 真实产物（在你机器上编译的，不是示意）

源码 `demo.ts`：

```ts
interface User { name: string; age: number }

function greet(u: User): string {
  return 'hello ' + u.name;
}

let count: number = 0;
const u: User = { name: 'pero', age: 20 };
console.log(greet(u), count);
```

执行 `tsc --target es2020 demo.ts` 之后的产物 `demo.js` —— **原文，一个字没改**：

```js
"use strict";
function greet(u) {
    return 'hello ' + u.name;
}
let count = 0;
const u = { name: 'pero', age: 20 };
console.log(greet(u), count);
```

### 4.3 逐行对照

| 源码 | 产物 | 发生了什么 |
|---|---|---|
| `interface User { ... }` | **整条消失** | 声明被删 |
| `function greet(u: User): string` | `function greet(u)` | 参数类型、返回值类型都删 |
| `let count: number = 0` | `let count = 0` | 注解删掉，值保留 |
| `const u: User = {...}` | `const u = {...}` | 同上 |

**类型不是「运行时开销很小」，是「运行时根本不存在」。**

⭐ **注意第一行**：`interface` 是**整条语句**被删的，不是「删掉 interface 这个词」。所以产物里连空行都不留 —— **它压根没编译出过任何东西**。

### 4.4 由此得出的 6 条硬约束（挂账表）

这 6 条**现在只需要认识**，不用会用。每一轮遇到我会点名回扣。

| 推论 | C# 里为什么可以 | 挂在哪轮 |
|---|---|---|
| 不能 `new T()` | 泛型具化，靠 `new()` 约束 / `Activator` | **M7** 泛型 |
| 不能 `default(T)` | 运行时知道 T 是值类型还是引用类型 | **M7** 泛型 |
| 不能 `typeof(T)` 拿类型 | `typeof(T)` 返回 `Type` 对象，元数据里有 | **M7** 泛型 |
| `as` 不做任何运行时检查 | `(T)x` 会 `castclass`，不匹配抛 `InvalidCastException` | **M3** 断言 |
| `private` 运行时读得到 | CLR 执行访问控制 | **M5** 修饰符 |
| 不能按类型重载 | CLR 按签名分派 | **M2** 函数类型 |

⭐ **这张表就是「为什么要先学擦除」的答案** —— 不先讲擦除，后面这 6 个坑每一个都会显得莫名其妙。

### 4.5 为什么必须擦除：三角取舍

三个语言能力，只能选两个：

```
        ① 有类型检查
         /        \
        /          \
  ② 零运行时开销 —— ③ 与 JS 完全兼容
```

| 语言 | 选了什么 | 放弃了什么 | 代价 |
|---|---|---|---|
| **C#** | ① + 有运行时类型 | 与 JS 兼容 | 必须跑在 CLR 上，产物是 IL |
| **TS** | ① + ③ | **运行时类型** | **编译器一过，类型就死** |
| **JS** | ② + ③ | ① | 你过去 200 集的世界 |

### 4.6 这不是 bug，是代价

⭐ **收口句**：

> **TS 的每一个「做不到」，都能追到「因为它必须是 JS」。**

记住这一句，比记 §4.4 那 6 条管用 —— 因为它是**生成规则**，那 6 条只是它生出来的结果。

⚠️ 按老规矩补一句「工程上怎么防」：**擦除不是缺陷，但它意味着你必须自己承担两件事** ——
① 运行时数据的真实性（TS 管不到后端返回什么）；
② 边界处的校验（接口返回、`localStorage` 读出来的、用户输入）。这两处 TS 一律给不了保证，见 §四 静默失败清单第 4 条。

## 5. import / export（前置补丁，你的 JS 空白）

### 5.1 为什么必须现在补

你的 JS 200 集**完全没讲模块化**（当时列在「课程外，仍锁着」那一栏）。但 TS 从「项目内共享类型」一直到最后的 `.d.ts`，**全部**建立在 `import` / `export` 上。

**不补这个，M10 会整轮卡死。** 而且本轮你马上要靠它做擦除实验（§5.3）。

### 5.2 五个要点

```ts
// ═══ math.ts —— 一个文件就是一个模块 ═══
export const PI = 3.14;                                   // 导出值
export function add(a: number, b: number): number {       // 导出函数
  return a + b;
}
export interface Point { x: number; y: number }           // 导出类型
```

```ts
// ═══ main.ts ═══
import { add, PI } from './math.ts';        // 导值
import type { Point } from './math.ts';     // ⭐ 导类型，必须写 type

const p: Point = { x: 1, y: 2 };
console.log(add(1, 2), PI, p);
```

| # | 要点 | 说明 | C# 对照 |
|---|---|---|---|
| ① | 一个文件 = 一个模块 | 不是 namespace 层级，是**文件级** | ❌ 无对应 |
| ② | `export` 标记「谁能被外部看到」 | 没 export 就是文件私有 | ≈ `public` / `internal` |
| ③ | `import` 按名字取 | 顺序无关，名字必须对上 | ≈ `using`，但 `using` 不挑名字 |
| ④ | **`import type` 必须显式写** | 因为类型**运行时不存在**（回扣 §4） | ❌ 无对应 |
| ⑤ | 相对路径要写扩展名 `.ts` | Node 原生 ESM 的硬要求 | ❌ 无对应 |

⭐ **③ 的差别值得停一下**：C# 的 `using` 只是「让名字可见」，两个同名类会歧义。TS 的 `import` 是**明确点名**要哪几个 —— `import { add }` 就只拿 `add`。**更接近 C# 的 `using static X;`，或者干脆写全名。**

### 5.3 ⭐⭐ ④ 为什么不是「风格问题」—— 这是本轮最好的证据

**实测**（文件在 `_自测/04-module/`）：

```ts
import { add, PI, Point } from './math.ts';   // ❌ 普通 import 混进了 interface
```

```
SyntaxError: The requested module './math.ts' does not provide an export named 'Point'
```

**`Point` 在运行时不存在的。** 你让 JS 去取一个只活在编辑器里的东西，它当然找不到。

改成 `import type { Point }` 就正常了 —— 因为 **`import type` 整句都会被擦掉**（回扣 §4）。

> ⭐ **这是「类型擦除」最锋利的一次现形**：它不是个理论，是你能亲手撞上的 `SyntaxError`。
> 也是本轮唯一的「你会主动想跑一遍」的实验。

### 5.4 环境注意

Node 直接跑 `.ts` 的 ESM，需要在目录放一个 `package.json`：

```json
{ "type": "module" }
```

而且 `tsc` 检查时要加 `--allowImportingTsExtensions`（Node 要求写 `.ts`，tsc 默认不许写，见 §二：格式 表 2）。

**M10 建 tsconfig 时把这两条一次性配好**，现在知道有这回事就行 —— 别在这里被工具链卡住。

==二：格式==

## 1. 类型注解速查（本轮范围）

本轮只需要认三种形状，细节在 M2 展开。

| 场景 | 写法 | C# 对照 | 位置差异 |
|---|---|---|---|
| 变量 | `let n: number = 0;` | `int n = 0;` | 类型**写在名字后面** |
| 函数参数 | `function add(a: number, b: number)` | `int Add(int a, int b)` | 每个参数各标一处 |
| 函数返回值 | `function add(...): number` | 写在方法名前 | 冒号 + 类型，在括号后 |
| 对象形状 | `interface User { name: string; age: number }` | `interface` / `class` | 成员用 `;` 或换行分隔 |
| 类型导入 | `import type { Point } from './x.ts'` | ❌ 无对应 | 必须写 `type` |

⭐ **记忆技巧**：C# 是「**类型 名字**」，TS 是「**名字: 类型**」—— 像填表时「姓名：张三」。

## 2. 「跑」和「查」命令对照

**这一格是你环境和课程差别最大的地方，必须背下来。**

| 目的 | 命令 | 会不会查错 | 会不会读 tsconfig | 会不会产出文件 |
|---|---|---|---|---|
| **跑** | `node x.ts` | ❌ **不查** | ❌ 不读 | ❌ 不产出 |
| **查** | `tsc --noEmit x.ts` | ✅ 查 | ✅ 读 | ❌ 不产出 |
| 编译 | `tsc x.ts` | ✅ 查 | ✅ 读 | ✅ 产出 `x.js` |

⚠️ **`node x.ts` 不查错，这是本轮最容易被忽略的一条。** 它跑得通 ≠ 你写对了。

## 3. 环境对账（替代 04-06 集）

课程用 `npm i -g typescript` + `tsc` + `ts-node`。你机器上已经装好并验证过：

| 项 | 你的版本 | 课程假设 | 差异怎么处理 |
|---|---|---|---|
| Node | v24.22（`C:\Users\14871\nodejs`） | 未提 | 能直接跑 `.ts` |
| npm | 11.19 | 有 | — |
| tsc | **7.0.2**（Go 重写版） | 5.x | 个别旧选项行为有变，遇到再对 |
| ts-node | **不需要** | 需要 | 被 `node x.ts` 替代 |
| tsconfig | 暂无 | 有 | M10 才建 |
| PowerShell 执行策略 | 已设 `RemoteSigned` | 未提 | 否则 `tsc.ps1` 报「禁止运行脚本」 |

⭐ **所以你跳过 04-06 集不是「偷懒」，是把 3 集安装视频换成这张表 + 一次实测。**

## 4. 三个必须记住的判断

| 遇到这个情况 | 用哪个 |
|---|---|
| 想验证「代码能不能跑」 | `node x.ts` |
| 想验证「类型对不对」 | `tsc --noEmit x.ts` |
| 想知道「最终产物长什么样」 | `tsc x.ts`，然后看 `.js` |

⚠️ **日常最容易犯的错**：只跑 `node`，看到有输出就以为写对了。**本轮起养成习惯：改完先 `tsc --noEmit`。**

==三：代码==

## 1. 擦除实验：亲眼看着 `interface` 消失（01-03）

```ts
// ═══ demo.ts ═══
interface User { name: string; age: number }

function greet(u: User): string {
  return 'hello ' + u.name;
}

let count: number = 0;
const u: User = { name: 'pero', age: 20 };
console.log(greet(u), count);
```

```bash
tsc --target es2020 demo.ts      # 产出 demo.js
cat demo.js                      # 看产物
```

**产物**（原文）：

```js
"use strict";
function greet(u) {
    return 'hello ' + u.name;
}
let count = 0;
const u = { name: 'pero', age: 20 };
console.log(greet(u), count);
```

**三个观察点**：

| 看这里 | 说明 |
|---|---|
| 第 1 行本该是 `interface User` | **整条没了**，连空行都不留 |
| `function greet(u)` | `: User` 和 `: string` 都删了 |
| `let count = 0` | 注解删了，值留着 |

⭐ **做完这一步你该有一个感觉**：`tsc` 不是在「翻译类型」，是在**「看懂类型 → 检查 → 扔掉」**。

## 2. 跑 ≠ 查 实验

```ts
// ═══ 05-类型写错照样跑.ts ═══
const n: number = 'hello';
console.log('[实验1] node 输出 →', n);
```

```bash
node 05-类型写错照样跑.ts
# [实验1] node 输出 → hello        ← 没报错，甚至还输出了

tsc --noEmit 05-类型写错照样跑.ts
# 05-类型写错照样跑.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.
```

⭐ **这是整轮最反直觉的一条**：Node 的 `.ts` 支持本质是「**类型剥离**」（type stripping）—— 它把类型当注释撕掉就执行，**从头到尾没打算理解类型**。

**所以它连「检查作用」都要靠另一个工具来提供** —— 这本身就是擦除的实物证明。

## 3. 把类型当值 import（前置补丁验证）

```ts
// ═══ bad.ts ═══
import { add, PI, Point } from './math.ts';   // ❌ Point 是个 interface
const p: Point = { x: 1, y: 2 };
console.log(add(1, 2), PI, p);
```

```bash
node bad.ts
# SyntaxError: The requested module './math.ts' does not provide an export named 'Point'
```

改成 `import type { Point }` → 正常输出 `3 3.14 { x: 1, y: 2 }`。

⭐ **这个 `SyntaxError` 值得你多看一眼**：它证明的不是「TS 的规则」，是「**类型从来就没被编译出来过**」。你在问 JS 要一个不存在的导出，它诚实地告诉你没有。

## 动手小练习（不留超纲作业）

1. **写 `person.ts`**：导出一个 `interface Person { name: string; age: number }`，和一个 `function describe(p: Person): string`，返回 `'pero 今年 20 岁'` 这样的字符串。
2. **写 `run.ts`**：导入并打印。⚠️ 导入 `Person` **必须用 `import type`**。
3. **三条命令都要过**：`node run.ts`、`tsc --noEmit run.ts`、把 `import type` 改成 `import` 后**亲眼看到那个 `SyntaxError`**。

**做完这三步，M1 就真的落地了 —— 因为你自己制造过一次「类型不存在」的事故。**

==四：总结==

## 1. 一句话记住三个

| 集 | 一句话 |
|---|---|
| 01 | **TS = JS + 类型层。没有运行时，类型编译后一个字不剩。** |
| 02 | **TS 不让你不犯错，它让你早犯错** —— 把错误从运行时挪到写代码时 |
| 03 | **最值钱的不是报错，是补全和重构**（前两项天天兑现，报错只在出事那天） |

## 2. ⭐⭐ 本轮要背的

> **C# 的类型活在 CLR 里；TS 的类型活在编辑器里。**
>
> 遇到「TS 为什么不能 X」，先问：**这件事需要运行时知道类型吗？**
> 需要 → TS 做不到，绕。不需要 → TS 能。

**四问表**（§1.2）也要能默写：谁定义 / 谁检查 / **谁执行** / 编译后还在吗。

## 3. ⭐ 收敛时刻：这一轮把 JS 的哪几条线接到了同一个点

| 前面哪一条 | 当时的话 | M1 给的解释 |
|---|---|---|
| **JS 基础篇 §七 动态类型** | "JS 变量没有类型，类型跟值走" | **TS 把类型搬回源码，但只搬到编译期** —— 运行时依旧"类型跟值走" |
| **JSDoc 速查表** | "JSDoc + `// @ts-check` ≈ 一个不用改后缀名的 TS" | **同一个类型系统**，M10 的 `.d.ts` 是它的正式版 |
| **进阶篇 16 收官** | "课程最大收获 = 「静默失败」暗线" | **TS 就是给这条暗线修的护栏** —— 但护栏只管开发期，见本表第 4 条 |
| **JS 模块化（空白）** | "`import`/`export` 还没学" | **`import type` 让你第一次亲眼看见「类型不存在」** |
| **你对 JS 的长期抵触** | "JS 不严谨，维护性差" | **TS 是同一批人给的答案**（Anders Hejlsberg，C# 之父） |

⭐ **五条线接在一点上**：你过去 200 集积累的所有「JS 太松」的不适感，根都在「没有编译期」。TS 补的正是这一块 —— **但它只补一半，因为它必须能跑在浏览器里**。

## 4. 静默失败清单（TS 版，本轮 4 条）

> 按老规矩：**这不是 TS 的 bug，是它的边界。**

| 你写的 | 实际发生 | 谁会拦 |
|---|---|---|
| 只跑 `node x.ts`，不跑 `tsc` | 类型错了照样输出结果 | ❌ **没人** —— 这是你最容易犯的 |
| `const u = null as unknown as User; u.name` | 运行时 `TypeError` | ❌ 没人，`tsc` 认为完全合法（M3 详讲） |
| `import { Point }`（interface） | 运行时 `SyntaxError` | ⚠️ 会炸，但**炸在运行时**，不是编译期 |
| 类型标对了，但数据来自接口 / `localStorage` | TS 认为一定有值，运行时 `undefined` | ❌ **没人** —— TS 只管形状，不管来源 |

⭐ **第 4 条是本轮最该记的工程结论**：

> **TS 的类型是「你对数据的声明」，不是「对数据的保证」。**
> 后端返回 `null`、用户改了 `localStorage`、接口字段被删 —— TS 全不知道。**边界处的校验永远要自己写。**

## 5. C# 类比可用度（本轮新增）

| TS 的做法 | C# 对应 | 档 | 说明 |
|---|---|---|---|
| 「给代码加类型检查」这个概念 | 有 | ⭐⭐⭐⭐⭐ | 完全同源，**同一作者**（Anders Hejlsberg） |
| 注解语法 `n: number` | `int n` | ⭐⭐⭐⭐ | 只差位置：类型在后 |
| 类型检查的**执行者** | 编译器 | ⭐ | ⚠️ **反向迁移必须掐断**：C# 后面还有 CLR 在执行，TS 后面什么都没有 |
| **「编译」这个词** | 编译 | ⭐⭐ | 🔵 **撞名**：C# 是「翻译 + 存档」，TS 是「检查 + 销毁」 |
| 编译产物 | `.dll` + metadata | ⭐ | C# 能反编译出类型，TS 产物是纯 JS |
| 报错体验 | 红波浪线 + 构建失败 | ⭐⭐⭐⭐ | 几乎一致，可以直接迁移 |
| 「类型是约束」这个直觉 | 强类型 | ⭐⭐⭐ | ⚠️ C# 的约束**运行时也成立**，TS 的约束**只在编辑器里成立** |
| `import` / `export` | `using` | ⭐⭐ | 文件即模块，不是 namespace 层级；`import` 是点名式 |

⭐ **本轮最大的可用度陷阱**：你以为「C# 的类型系统 = TS 的类型系统，只是语法不同」。
**不是。** 它们是**同一套类型理论的两种落地**：C# 落到了运行时，TS 落在了编辑器里。**同一个设计者，两个完全不同的妥协。**

==一：概念==

## 1. 静态结构：一个页面塞了三块（179）

### 1.1 页面分区

```
┌────────────────────────────────────────────┐
│ ① 搜索栏：分类下拉 + 状态下拉 + 搜索 + 重置   │
├────────────────────────────────────────────┤
│ ② 表格：标题 / 分类 / 状态 / 发布时间 / 操作  │
├────────────────────────────────────────────┤
│ ③ 分页：总数 + 每页条数 + 页码 + 跳转        │
└────────────────────────────────────────────┘
```

**三块各自是独立的职责**：

| 区块 | 谁的状态 | 谁来触发数据变化 |
|---|---|---|
| 搜索栏 | `cateId` / `state` | 点「搜索」→ 带参数重新请求 |
| 表格 | `list` | 请求完就有 |
| 分页 | `page` / `pageSize` / `total` | 翻页 → 带新页码重新请求 |

**读懂这张表，就理解了本轮的骨架**：**三个区块各有一份状态，但只有「一个」请求函数** —— 因为请求参数是「分类 + 状态 + 页码 + 每页条数」拼起来的。

**这就是为什么第 182-183 集会出现一堆 bug**：三份状态都能影响同一次请求，**任何一个没同步好，就会看到错的数据**。

### 1.2 用 `PageContainer` 包起来（篇 2 的成果）

```html
<PageContainer title="文章管理">
  <template #extra>
    <el-button type="primary" @click="openDrawer">发布文章</el-button>
  </template>
  <!-- 搜索栏 + 表格 + 分页 -->
</PageContainer>
```

**篇 2 花 764 秒封装的组件，这里一行就用上了。** 这就是「先封装再复用」的回收时刻。

## 2. 中文国际化 + 分类组件封装（180）🔥

**这一集干了两件不相关的事，但都是「让页面像人做的」。**

### 2.1 为什么 Element Plus 默认是英文

**Element Plus 是国际项目**，默认 locale 是 `en`。所以：

| 组件 | 默认显示 |
|---|---|
| `el-pagination` | `Total 100`、`Go to`、`items/page` |
| `el-date-picker` | 星期是 `Mon Tue Wed`，月份是 `January` |
| `el-upload` | `Drop file here or click to upload` |
| `ElMessageBox` 的按钮 | `OK` / `Cancel` |

**只有这几类会露馅**（`el-button` 的文字是你自己写的，所以没事）。

### 2.2 两种设置方式，按引入方式选

**方式 A：全量引入时（`app.use(ElementPlus)`）**

```js
import ElementPlus from 'element-plus'
import zhCn from 'element-plus/es/locale/lang/zh-cn'

app.use(ElementPlus, { locale: zhCn })
```

**方式 B：按需引入时（本项目）→ 用 `ElConfigProvider`**

```html
<!-- App.vue -->
<script setup>
import zhCn from 'element-plus/es/locale/lang/zh-cn'
</script>

<template>
  <el-config-provider :locale="zhCn">
    <router-view />
  </el-config-provider>
</template>
```

⚠️ **本项目必须用方式 B** —— 因为按需引入时 `app.use(ElementPlus)` 等于把「按需」作废了（你又全量引入了）。**`ElConfigProvider` 是「组件级配置」，不需要全量注册。**

### 2.3 `ElConfigProvider` 是什么机制

**它用 `provide/inject` 往下传配置** —— 就是你在 Vue3--05 学的那套。

```
ElConfigProvider（provide 'locale'）
   ↓ 整棵子树
el-pagination / el-date-picker（inject 'locale'）
```

**所以它必须「包住」要用到的组件**。放在 `App.vue` 最外层最保险。

⚠️ **一个常见的失效**：你把 `el-config-provider` 放在了某个页面里，但**弹层（`el-dialog`）默认会 teleport 到 `<body>`** —— **它跑出了 provider 的子树，于是又变回英文**。

**这就是 `provide/inject` 的「子树」限制在实战里的第一次翻车**（Vue3--05 的 1.2 节：只能沿树往下）。**解法：provider 放在最外层（`App.vue`），让整个 body 都在它的子树里 —— 严格说 teleport 出去的内容仍然在组件树的「逻辑位置」上，所以能取到。**

**记住这个结论**：**`ElConfigProvider` 放 `App.vue` 最外层，永远不会有问题。**

### 2.4 `ChannelSelect`：把下拉框封成一个组件

**重复在哪**：文章列表要用「分类」做筛选，发布文章的表单也要填「分类」。**两个地方都要下拉框 + 都要请求分类列表。**

**做法：组件自己请求数据，只对外暴露「选中的值」**：

```html
<!-- components/ChannelSelect.vue -->
<script setup>
import { ref, onMounted } from 'vue'
import { getCategoryAPI } from '@/api/article'

const model = defineModel()                 // ← v-model 绑选中的 cate_id
const list = ref([])

onMounted(async () => {
  list.value = await getCategoryAPI()
})
</script>

<template>
  <el-select v-model="model" placeholder="请选择分类">
    <el-option v-for="item in list" :key="item.id"
               :label="item.cate_name" :value="item.id" />
  </el-select>
</template>
```

```html
<!-- 用起来 -->
<ChannelSelect v-model="cateId" />
```

### 2.5 「组件自己请求」是个取舍，要说清

| | 组件自己请求 | 父组件传进来 |
|---|---|---|
| 调用方成本 | **零**（一个标签搞定） | 要自己请求 + 传 prop |
| 请求次数 | 用两次 → **请求两次** | 父组件请求一次，传两份 |
| 数据新鲜度 | **每次挂载都是最新** | 取决于父组件什么时候请求 |

**课程选「自己请求」**，因为**调用方零成本**最重要 —— 这个组件只用在 2 个地方，多一次请求无所谓。

**什么时候该改成「父组件传」+ 缓存？**

**当组件被用在 5 个以上地方，或者列表请求很重的时候。** 那时候引入一个 Pinia store 存分类列表（一次请求，全局共享）是最优解 —— **这正是「Pinia 该存什么」的判断标准：跨多个页面共用 + 不常变**（篇 1 的 8.1 说过）。

**现在别做这个优化**。2 个地方、几十条数据，**过早优化只会让你多一层要维护的东西**。

### 2.6 `defineModel` 在这里为什么刚刚好

`ChannelSelect` 的本质是「一个能双向绑定的输入控件」——**和 `el-select` 一样**。

**判断标准**：**如果一个组件「输入一个值、输出同一个值」，就该用 `v-model`**（而不是 emit 一个 `change` 事件让父组件自己赋值）。

**这比 Vue2 的 `value` + `input` 那套省了将近 10 行代码** —— 你在 Vue3--05 学过 `defineModel` 省掉的就是这些。

## 3. 列表 API + 渲染（181）

### 3.1 查询参数是「四合一」

```js
// api/article.js
export const getArticleListAPI = ({ pagenum, pagesize, cate_id, state }) =>
  request.get('/api/article', { params: { pagenum, pagesize, cate_id, state } })
```

**注意 `params` 和 body 的区别**（这个必须分清）：

| | 放哪 | 对应 HTTP | 什么时候用 |
|---|---|---|---|
| `params` | **URL 上** `?pagenum=1&pagesize=2` | GET 查询参数 | **查询、筛选、分页** |
| 第二个参数（body） | 请求体里 | POST/PUT | **提交数据** |

```js
request.get('/api/article', { params: {...} })     // ✅ GET 用 params
request.post('/api/article', { title: 'x' })       // ✅ POST 用 body
request.get('/api/article', { title: 'x' })        // ❌ 会被当成 config，请求发不出去
```

⚠️ **第三行是高频错误**：把 data 位置写错了，**axios 不会报错**，只是把它当成「配置对象」忽略掉了 —— 你看到的现象是「后端收不到参数」。

### 3.2 响应结构：`items` + `total`

```js
const res = await getArticleListAPI({ pagenum: page.value, pagesize: pageSize.value, ... })
list.value = res.items
total.value = res.total
```

**为什么不是 `res.data`？** 因为**拦截器已经拆过一层**（篇 1 的 9.3）。`res` 就是后端 body 里的 `data`，而 `data` 里面是 `{ items, total }`。

**这里要养成一个习惯**：**看接口文档时，把「最外层的 code/message/data」当空气，直接从 `data` 里面开始读。** 因为你永远拿到的都是 `data`。

### 3.3 请求参数为什么要「每次都从 ref 里现取」

```js
// ✅ 正确
const getList = async () => {
  const res = await getArticleListAPI({
    pagenum: page.value, pagesize: pageSize.value,
    cate_id: cateId.value, state: state.value,
  })
}

// ❌ 错误：组件初始化时算好参数存起来
const params = { pagenum: 1, pagesize: 2 }
const getList = async () => await getArticleListAPI(params)
```

**第二行的问题**：翻页改了 `page.value`，但 `params.pagenum` 还是 1 → **点下一页，数据不变**。

**规则**：**请求函数必须是「无参」的，参数在函数体内从 ref 现取。** 这样任何地方调 `getList()` 都是「用当前状态请求」—— 翻页、搜索、重置、增删改后刷新，全都调同一个函数。

**这条能消灭一整类 bug。** 如果你让 `getList(params)` 接受参数，就会出现「这里传了、那里忘了传」的碎片化调用。

## 4. 分页渲染（182）

### 4.1 `el-pagination` 的五个绑定

```html
<el-pagination
  v-model:current-page="page"
  v-model:page-size="pageSize"
  :page-sizes="[2, 5, 10, 20]"
  :total="total"
  layout="total, sizes, prev, pager, next, jumper"
  @current-change="getList"
  @size-change="onSizeChange"
/>
```

| 绑定 | 含义 | 谁改它 |
|---|---|---|
| `v-model:current-page` | **当前第几页**（从 1 开始） | 用户点页码 / 你代码改 |
| `v-model:page-size` | 每页几条 | 用户选 `page-sizes` 时 |
| `:page-sizes` | 可选每页条数 | 你定 |
| `:total` | **总条数** | 后端返回 |
| `layout` | 显示哪些部件 | 你定 |

**`v-model:xxx` 这个语法**是「具名 v-model」——`current-page` 不是 `modelValue`，所以要写 `:current-page` 的完整形式。**这就是 `defineModel('name')` 对应的父组件写法**（Vue3--05 的 1.2 节）。

### 4.2 为什么「翻页」要重新请求

**`el-pagination` 只是「页码的选择器」，它不会自己去拿数据**。它做两件事：

1. 用户点「第 2 页」→ 把 `page` 改成 2
2. 触发 `@current-change` 事件

**真正拿数据的是你绑在 `@current-change` 上的 `getList`。**

**新手最常见的误解**：以为 `:total` 和 `:data` 有某种自动关联。**没有。** 分页组件只认 `total` 这个数字，它不知道你有多少条真实数据。

### 4.3 页码从 1 开始 —— 这个 1 是有代价的

**后端接口的 `pagenum` 从 1 开始**（符合人类直觉），但**数据库的 `OFFSET` 从 0 开始**。

```
第 1 页，每页 2 条 → 跳过 0 条，取 2 条     OFFSET = (1-1) * 2 = 0
第 2 页，每页 2 条 → 跳过 2 条，取 2 条     OFFSET = (2-1) * 2 = 2
```

**公式**：`OFFSET = (pagenum - 1) * pagesize`

**这个换算是后端的活**（你以后写 ASP.NET Core 时会用到）。**前端只要保证传的 `pagenum` 从 1 开始**，别传 0 —— 传 0 后端可能返回 `OFFSET = -2`（报错）或者干脆返回第一页（静默正确，但换后端就炸）。

### 4.4 `size-change` 必须把页码归 1

```js
const onSizeChange = () => {
  page.value = 1        // ← 关键
  getList()
}
```

**不归 1 会怎样**：原来每页 2 条、第 5 页（第 9-10 条）。改成每页 10 条 → **总共只有 10 条，只有 1 页** → 但 `page` 还是 5 → 请求第 5 页 → **后端返回空数组**。

**用户看到「空白列表」，以为数据没了。**

**这条和篇 2 的 10.3（删除末页最后一条要翻页）是同一个病的两种症状**：**页码状态和实际数据量脱节。**

**统一的防法**：**任何改变「每页条数」或「筛选条件」的操作，都必须把 `page` 归 1。** 只有「翻页」本身不归。

## 5. loading 与搜索重置（183）

### 5.1 `v-loading` 是「指令」，不是「组件」

```html
<el-table v-loading="loading" :data="list">...</el-table>
```

**`v-loading` 和 `<el-button>` 不是一类东西** —— 它是**自定义指令**，作用是在元素上盖一层遮罩 + 转圈。

**为什么用指令而不是组件？** 因为遮罩必须**跟着目标元素的大小和位置**。组件做不到（组件是独立的 DOM 节点），指令可以直接操作宿主元素的样式。

### 5.2 🔥 按需引入时 `v-loading` 会失效 —— 这是个真坑

**`unplugin-vue-components` 的 `ElementPlusResolver` 只能自动导入「组件」**，**导不了「指令」**。

**表现**：

```
[Vue warn]: Failed to resolve directive: loading
```

**而表格照常显示**（只是没有遮罩）—— **又一个静默失败**。

**解法（在 `main.js` 手动注册）**：

```js
import { ElLoading } from 'element-plus'
app.use(ElLoading)          // ← 会注册 v-loading 指令 + $loading 服务
```

或者在用到的那一个组件里：

```js
import { ElLoadingDirective } from 'element-plus'
const vLoading = ElLoadingDirective       // ← 局部指令，名字必须是 vLoading
```

⚠️ **局部注册的命名规则**：`vLoading` 对应模板里的 `v-loading`。**写成 `loading` 就无效** —— 这是 Vue 的指令命名约定（`vXxx` → `v-xxx`）。

**同类问题还有几个**：`v-infinite-scroll`、`v-click-outside`、`v-repeat-click` 都是指令，**按需引入都要手动注册**。**记住这条规律：`v-` 开头的 Element Plus 功能，自动导入管不到。**

### 5.3 搜索与重置

```js
// 搜索
const onSearch = () => {
  page.value = 1            // ← 换条件必须回第 1 页
  getList()
}

// 重置
const onReset = () => {
  cateId.value = ''
  state.value = ''
  page.value = 1            // ← 别忘了这个
  getList()
}
```

**重置的三个坑**：

| # | 坑 | 后果 |
|:--:|---|---|
| 1 | 忘了把 `page` 归 1 | 在第 3 页点重置 → 请求第 3 页但结果只有 1 页 → **空白** |
| 2 | 只清了筛选条件，**没重新请求** | 下拉框变空了，但表格还是旧数据 |
| 3 | 用 `Object.assign` 重置整个对象 | 如果筛选条件是 `reactive({})` 且被别处引用，会改到别人 |

**第 2 条很常见**：重置函数只负责「把变量清空」，忘了调 `getList()` —— 因为变量清空**本身不会触发请求**（你不是在 watch 它）。

⚠️ **这里有个设计选择**：可以让筛选条件「一变就自动请求」（用 `watch`），这样就不用手动调 `getList`：

```js
watch([cateId, state], () => { page.value = 1; getList() })
```

**但课程没这么做，为什么？**

| 自动请求（watch） | 手动请求（点按钮） |
|---|---|
| 少写代码，不会忘 | 每次输入都请求 → **后端压力大** |
| 输入框打字时**每次都请求** | 用户想好了一次性搜 |
| 适合下拉、单选 | **适合文本输入** |

**在后台管理系统里，「搜索按钮」是标准做法**，因为筛选条件往往有好几个，用户要填完一起搜。**自动请求只适合「单个开关型筛选」**（比如 tab 切换）。

### 5.4 `loading` 什么时候开什么时候关

```js
const loading = ref(false)

const getList = async () => {
  loading.value = true
  try {
    const res = await getArticleListAPI({...})
    list.value = res.items
    total.value = res.total
  } finally {
    loading.value = false        // ← 必须 finally
  }
}
```

⚠️ **为什么用 `finally` 而不是在 `await` 后面直接关？**

因为**请求失败会抛异常**，`await` 后面那行**根本不会执行** → `loading` 永远是 `true` → **遮罩永远转圈，页面卡死**。

**这是「loading 状态」的通用规则**：**开启在 try 之前，关闭在 finally 里。** 你以后写任何 `loading` 都要这么写。

**这也解释了一个常见现象**：用户说「页面一直在转圈，刷新才好」—— 十次有八次是请求失败而 `loading` 没关。

## 6. 抽屉组件封装（184）

### 6.1 `el-drawer` 和 `el-dialog` 的差别

**只有一个：从哪边滑出来。**

```html
<el-drawer v-model="visible" title="发布文章" direction="rtl" size="50%">
  表单内容
</el-drawer>
```

| 属性 | 值 | 含义 |
|---|---|---|
| `direction` | `rtl` / `ltr` / `ttb` / `btt` | 从右/左/上/下滑出 |
| `size` | `'50%'` / `'600px'` | 宽（或高）度 |

**为什么「发布文章」用抽屉而不是弹层？**

**因为内容多。** 文章表单有：标题、分类、封面图、富文本编辑器、状态 —— **一个 500px 的居中弹层塞不下**。抽屉能占半屏，高度撑满，**表单长了还能滚动**。

**判断口诀**：**内容少、要「打断」用户 → 弹层；内容多、要「并排参考」→ 抽屉。**

### 6.2 封装成 `ArticleEdit` 组件

```html
<!-- views/article/components/ArticleEdit.vue -->
<script setup>
const visible = defineModel()
</script>

<template>
  <el-drawer v-model="visible" title="文章编辑" direction="rtl" size="50%">
    <slot></slot>
  </el-drawer>
</template>
```

**封装的理由和篇 2 的 `DialogEdit` 完全一样** —— 但这里有一个新问题。

### 6.3 新问题：抽屉里的东西「要不要跟着一起封装」

**你在封装什么？** 只有 `el-drawer` 这层壳？还是整个表单？

| 封装程度 | 好处 | 代价 |
|---|---|---|
| **只封壳**（`slot` 放表单） | 组件通用，任何内容都能塞 | 调用方要写全部表单 |
| **连表单一起封** | 调用方一行 `<ArticleEdit v-model="show" />` | 组件变「胖」，只能干这一件事 |

**课程的取舍：先只封壳（184 集），再在壳里填表单（185 集）。**

**这个顺序很重要**，它体现了封装的一条原则：**先封「结构」，再封「内容」**。因为结构是稳定的（抽屉总是那三层：标题/内容/底部按钮），内容是多变的（表单字段会改）。

⚠️ **如果反过来**（先写完整表单再抽壳），你会发现「抽出来的壳跟表单长在一起了」—— 想复用到别的地方就得拆一遍。

## 7. 完善抽屉表单结构（185）

### 7.1 文章表单和分类表单的差别

| 分类表单 | 文章表单 |
|---|---|
| 2 个字段（名称、别名） | **5 个字段**（标题、分类、封面、内容、状态） |
| 全是 `el-input` | **4 种控件**：`el-input` / `ChannelSelect` / `el-upload` / 富文本 |

**控件一多，「布局」就成了问题。** 课程用了 `el-form` 的 `label-width` 对齐 + 几个 `el-row` / `el-col` 做左右分栏。

**这里不需要学新东西** —— `el-row` / `el-col` 就是栅格（24 格制，`span` 表示占几格），和 CSS 的 flex 是一回事。

### 7.2 `label-width` 要统一

```html
<el-form label-width="80px">
```

**不设的话**：每个 `el-form-item` 的标签宽度跟着文字长度走 → 「标题」和「文章分类」的输入框**左边不对齐**，看着很业余。

**规则**：**同一个表单里所有 `el-form-item` 的 label 用同一个宽度**，`el-form` 上设一次就行。

## 8. 上传文件（186）🔥 本轮最容易翻车的一集

### 8.1 `el-upload` 的基本形态

```html
<el-upload
  action="http://big-event-vue-api-t.itheima.net/api/upload"
  :headers="{ Authorization: userStore.token }"
  :show-file-list="false"
  :on-success="onUploadSuccess"
  :before-upload="beforeUpload"
>
  <img v-if="form.cover_img" :src="form.cover_img" class="cover" />
  <el-icon v-else><Plus /></el-icon>
</el-upload>
```

**五个属性，各自在管一件麻烦事**：

| 属性 | 作用 | 不写会怎样 |
|---|---|---|
| `action` | **上传地址**（完整 URL） | 必须写，没有默认值 |
| `:headers` | **请求头**（放 token） | **后端返回 401** |
| `:show-file-list` | 是否显示已上传文件列表 | 会出现一排文件条目，很丑 |
| `:on-success` | 上传成功回调 | 拿不到图片地址 |
| `:before-upload` | 上传前校验 | 用户能传 50MB 的视频 |

### 8.2 ⚠️ 为什么必须手动传 token —— 这是全篇最重要的一条

**你封装的 `request.js` 里，拦截器会自动加 `Authorization`。但 `el-upload` 不走它。**

```
你的代码
  ├── 业务请求 → axios（request.js）→ 拦截器加 token ✅
  └── el-upload → 组件内部自己发 XHR → 拦截器管不到 ❌
```

**原因**：`el-upload` 是**组件自己**用原生 `XMLHttpRequest`（或 `fetch`）发的请求，**完全没有经过 axios**。你封装的实例对它来说不存在。

**所以后端收到的请求没有 `Authorization` 头 → 返回 401 → 上传失败。**

**这就是「封装漏了一个入口」的经典案例。**

**它给你的教训（比这个坑本身重要）**：

> **封装只对「走这条路的代码」生效。** 任何「自带请求能力」的第三方组件（上传、富文本的图片插入、地图 SDK），都要单独检查「它怎么带凭证」。

**同类会踩的地方**：

| 组件/库 | 要不要单独处理 token |
|---|---|
| `el-upload` | **要**（`:headers`） |
| `@vueup/vue-quill` 的图片上传 | **要**（自定义 handler 里用 axios） |
| 第三方地图 / 统计 SDK | 一般要单独的 key，不是 token |
| `<img src>` 请求 | 不用（走 cookie，或者后端公开） |

### 8.3 `on-success` 的参数

```js
const onUploadSuccess = (response) => {
  // response 是后端返回的「完整 body」：{ code: 0, message: '...', data: 'http://...' }
  if (response.code === 0) {
    form.cover_img = response.data       // ← 图片 URL
  } else {
    ElMessage.error(response.message)
  }
}
```

⚠️ **注意这里 `response` 是什么** —— **是原始 body，不是拆过包的 `data`**。

**因为拆包是拦截器干的，而上传没走拦截器。** 所以：

| 场景 | 拿到的对象 |
|---|---|
| `await getArticleListAPI()` | 后端 body 的 **`data`** |
| `el-upload` 的 `on-success(response)` | **完整 body**（`code` / `message` / `data` 都在） |

**这是本篇第二个「层级认知」考点**（第一个是篇 2 的 `res.data.token`）。**判断依据还是那一条：这段代码走没走 `request.js`。**

### 8.4 `before-upload` 做文件校验

```js
const beforeUpload = (file) => {
  const isImage = file.type.startsWith('image/')
  const isLt2M = file.size / 1024 / 1024 < 2
  if (!isImage) { ElMessage.error('只能上传图片'); return false }
  if (!isLt2M) { ElMessage.error('图片不能超过 2MB'); return false }
  return true                    // ← 返回 false 会中断上传
}
```

**返回 `false` 就中断上传** —— 这是 `before-upload` 的约定。

⚠️ **返回 `undefined` 会怎样？** **继续上传**（只有明确 `return false` 才中断）。所以「忘了写 return」= 校验白做了。

**`file` 是什么**：原生 `File` 对象，常用的三个属性 `name` / `size`（**字节**）/ `type`（MIME，如 `image/png`）。

### 8.5 图片回显：封面图的两态

```html
<img v-if="form.cover_img" :src="form.cover_img" />
<el-icon v-else><Plus /></el-icon>
```

**上传成功后，`form.cover_img` 变成了 URL → 图片显示。** 上传前显示一个「+」图标。

**这就是「受控回显」的模式**：**UI 由数据决定，不靠手动操作 DOM。** 你之前手改 `class` 的教训（Vue--实战01）在这里不用重演。

## 9. 富文本编辑器 `vue-quill`（187）

### 9.1 为什么要富文本

**普通 `el-input` 存的是纯文本**，文章内容要有加粗、标题、列表、图片 → 需要存 **HTML 字符串**。

**富文本编辑器干的事**：给你一个「所见即所得」的区域，编辑完吐出一段 HTML。

```bash
pnpm i @vueup/vue-quill
```

### 9.2 基本用法（三个必写项）

```html
<script setup>
import { QuillEditor } from '@vueup/vue-quill'
import '@vueup/vue-quill/dist/vue-quill.snow.css'    // ← 忘了这行就没有工具栏
</script>

<template>
  <QuillEditor
    v-model:content="form.content"
    content-type="html"
    theme="snow"
    :toolbar="toolbarOptions"
  />
</template>
```

| 写法 | 为什么 |
|---|---|
| **`v-model:content`**（不是 `v-model`） | 它的 v-model 是**具名**的，绑的是 `content` |
| **`content-type="html"`** | 默认是 `delta`（Quill 自己的 JSON 格式）→ 后端不认 |
| `theme="snow"` | 带工具栏的经典主题（另一个是 `bubble`，气泡式） |

### 9.3 ⚠️ `v-model:content` 这个坑要认真看

**如果你写成 `v-model="form.content"`**：

```html
<QuillEditor v-model="form.content" />       <!-- ❌ 不生效 -->
```

**现象**：编辑器能打字，但 `form.content` **永远是空字符串** → 提交时内容是空的 → **后端报「内容不能为空」，而你明明写了三大段**。

**为什么？** 因为 `v-model` 展开是 `:modelValue` + `@update:modelValue`。**这个组件不认 `modelValue`，它认 `content`。**

**展开写法**（等价的，帮你理解）：

```html
<QuillEditor :content="form.content" @update:content="form.content = $event" />
```

**所以「具名 v-model」的本质就是「换个 prop 名」** —— 和你在 Vue3--05 学的 `defineModel('name')` 是一对。**这次你站在「使用者」这一侧，撞上了它的代价。**

### 9.4 `content-type` 必须显式指定

| `content-type` | `form.content` 里是什么 |
|---|---|
| 不写（默认 `delta`） | `{ ops: [{ insert: "你好\n" }, ...] }` —— **一个 JSON 对象** |
| `'html'` | `'<p>你好</p>'` —— **HTML 字符串** |
| `'text'` | 纯文本（格式全丢） |

**后端存的是 `TEXT` 字段**，它要的是 HTML 字符串。**不写 `content-type` → 后端收到一个对象 → 存进去变成 `[object Object]`。**

**这是最阴的一种失败**：编辑器里看起来完全正常，**只有打开文章详情时才看到 `[object Object]`。** 那时候提交已经过去很久了。

### 9.5 toolbar 配置

```js
const toolbarOptions = [
  ['bold', 'italic', 'underline', 'strike'],     // 行内格式
  [{ header: 1 }, { header: 2 }],                 // 标题
  [{ list: 'ordered' }, { list: 'bullet' }],      // 列表
  [{ align: [] }],                                // 对齐
  ['image', 'link'],                              // 图片、链接
  ['clean'],                                      // 清除格式
]
```

**每一项是一个「按钮组」**，数组嵌套的层级决定**分组之间有一条竖线**。

⚠️ **`'image'` 这个按钮默认是「上传到 base64 内嵌」** —— 一张图就能让文章变成几 MB。**真要用于生产，需要自定义 `image` handler 走你自己的上传接口**（课程没做，你知道有这个坑就行）。

## 10. 新增文章完成（188）

### 10.1 提交的七个字段

```js
await addArticleAPI({
  title: form.title,
  cate_id: form.cate_id,
  cover_img: form.cover_img,
  content: form.content,
  state: form.state,          // '草稿' / '已发布'
})
```

**注意 `state` 是中文** —— 这个项目的后端用的是中文字符串枚举，**不是 `0/1`**。**接口文档怎么写你就怎么传，别自己「规范化」。**

### 10.2 提交前的最后一关：富文本的「空」怎么判断

```js
// ❌ 无效：Quill 空内容是一段空标签，不是 ''
if (!form.content) { ... }

// ✅ 正确：留 required 规则，或者判断去掉标签后是否为空
if (!form.content.replace(/<[^>]+>/g, '').trim()) { ... }
```

**Quill 的空内容是 `<p><br></p>`** —— **一个真值**。所以 `!form.content` 永远是 `false`。

**这是富文本的通用坑**：**「空」不等于「没有字符」**。后端如果做「内容不能为空」的校验，你前端也要用同样的标准（去标签后为空）。

### 10.3 提交成功的六步（和篇 2 一样）

```js
const submit = async () => {
  await formRef.value.validate()               // ①
  await addArticleAPI(form)                    // ②
  ElMessage.success('发布成功')                 // ③
  visible.value = false                        // ④
  resetForm()                                  // ⑤
  page.value = 1                               // ⑥ ← 新文章在第一页
  await getList()                              // ⑦
}
```

⚠️ **第 ⑥ 步是新增文章独有的**：新文章按「发布时间倒序」排，**一定在第 1 页**。如果用户当时在第 3 页，不归 1 就**看不到自己刚发的文章**，会以为发布失败了。

**这又是「页码状态」的第三次出现**（篇 2 的删除、本轮的 size-change、这里的新增）。**三种症状，同一个病根：操作改变了数据的「范围」，但页码没跟着变。**

## 11. 编辑文章（189）

### 11.1 「新增」和「编辑」共用一个抽屉

**判断依据：有没有 `id`。**

```js
const form = reactive({
  id: null,            // ← 有 id = 编辑，没有 = 新增
  title: '',
  cate_id: '',
  cover_img: '',
  content: '',
  state: '',
})

const openEdit = async (row) => {
  visible.value = true
  Object.assign(form, row)          // ← 回填（下面重点说）
  form.content = await getContent(row.id)   // 富文本可能不在列表里
}
```

### 11.2 ⚠️ `Object.assign(form, row)` 有个必须知道的副作用

**`Object.assign` 是「逐字段赋值」，它保留 `form` 的引用。** 这本身是好事（`reactive` 的对象不能被整体替换，否则丢响应式）。

**但副作用是：`row` 里没有的字段，`form` 里的旧值会留着。**

**具体场景**：

```
① 编辑文章 A（有封面）→ form.cover_img = 'http://a.png'
② 关闭抽屉
③ 编辑文章 B（没封面）→ Object.assign(form, B)
   → B 里没有 cover_img 字段 → form.cover_img 还是 'http://a.png'
   → 【文章 B 的抽屉里显示着文章 A 的封面】
```

**如果此时点保存** → **文章 B 被加上了文章 A 的封面**。**这是真会发生的 bug，而且很难发现。**

**三种修法**：

```js
// ① 先重置再赋值（推荐，最不容易忘）
const resetForm = () => {
  Object.keys(form).forEach(k => { form[k] = '' })
  form.id = null
}
resetForm()
Object.assign(form, row)

// ② 从接口拿完整详情（最稳，但多一次请求）
const detail = await getArticleDetailAPI(row.id)
Object.assign(form, detail)

// ③ 显式赋每个字段（最啰嗦，最清楚）
form.id = row.id
form.title = row.title
// ...
```

**课程用的是 ① 或 ② 的混合** —— **但你要知道「不重置」的后果**。

**关键认知**：**`Object.assign` 是浅拷贝里的「按 key 覆盖」，它不删 key。** 你以后在 C# 里用 AutoMapper 的 `mapper.Map(src, dest)` 也会遇到同样的问题（`dest` 里已有的值不会被清空，除非配置）。

### 11.3 富文本回填的特殊问题

**列表接口一般不返回 `content`**（文章内容可能几万字，列表带上是灾难）。所以要单独请求详情：

```js
const detail = await getArticleDetailAPI(row.id)
form.content = detail.content
```

⚠️ **「什么时候赋值给 QuillEditor」的坑**：

如果抽屉还没渲染完就赋值，**Quill 可能拿不到内容**。安全做法是「先打开抽屉，`await nextTick()` 后再赋值」：

```js
visible.value = true
await nextTick()                    // ← 等 DOM 渲染完
form.content = detail.content
```

**`nextTick()` 是什么**：等 Vue 把「数据变化」引起的 DOM 更新**全部刷完**后的回调。你在 Vue--05 学过它的语义 —— 这里第一次有实际用途。

**但大多数情况不用它**：`v-if` 控制的抽屉第一次打开时，绑定的是 `reactive` 对象，`form.content` 变了组件会自己响应。**只有在「组件已经实例化、但内部有初始化逻辑只跑一次」时才会出问题**（Quill 就是这种）。

### 11.4 编辑提交是 `PUT` 还是 `POST`

```js
// api
export const updateArticleAPI = (data) => request.put('/api/article', data)
```

**判断依据还是 `id`**：

```js
const submit = async () => {
  await formRef.value.validate()
  if (form.id) {
    await updateArticleAPI(form)
  } else {
    await addArticleAPI(form)
  }
  ElMessage.success(form.id ? '修改成功' : '发布成功')
  visible.value = false
  resetForm()
  await getList()
}
```

⚠️ **编辑时不要 `page.value = 1`** —— **用户在第 3 页编辑完，应该还在第 3 页。** 只有「新增」要回第 1 页。

**这个区别很小但很重要**：**改现有数据不改变它的「位置范围」，加新数据才会。**

```html
<QuillEditor v-model="form.content" />      <!-- 故意写错 -->
```

```js
console.log(JSON.stringify(form.content))    // ""
```

```js
console.log(JSON.stringify(form.content))    // "<p>你打的字</p>"
```

```js
console.log(typeof form.content)      // "object"
```

**看到 `ops` 就说明是 delta 格式** —— 后端存这个就是灾难。**这三个实验 5 分钟能做完，能省掉你以后半小时的排查。**

## 2. 验证 `Object.assign` 不删 key

```js
const form = { id: 1, title: 'A', cover_img: 'http://a.png' }

console.log(form)     // { id: 2, title: 'B', cover_img: 'http://a.png' }  ← 封面还在
```

==四：总结==

## 1. 一句话记住三个

1. **`el-upload` 不走 axios，所以拦截器加的 token 它拿不到** —— 必须手动 `:headers`；`on-success` 拿到的也是**原始 body**。
2. **富文本必须 `v-model:content` + `content-type="html"`** —— 少一个就静默存进一堆没人能读的东西。
3. **任何改变「数据范围」的操作都要把 `page` 归 1** —— 改条数、搜索、重置、新增；只有编辑不用。

## 2. ⭐⭐ 本轮要背的

| 内容 | 答案 |
|---|---|
| `el-pagination` 五个绑定 | `v-model:current-page` / `v-model:page-size` / `:page-sizes` / `:total` / `layout` |
| 翻页靠什么触发请求 | `@current-change` → 你自己调 `getList`（组件不拿数据） |
| `pagenum` 从几开始 | **1**（`OFFSET = (pagenum-1) * pagesize` 是后端的活） |
| `size-change` 必做 | `page.value = 1` |
| 重置的函数里必须有 | 清条件 + **`page = 1`** + **`getList()`** |
| `GET` 的参数放哪 | **`{ params: {...} }`**，不是第二个参数直接写 |
| `getList` 要不要参数 | **不要**，参数在函数体内从 ref 现取 |
| `loading` 在哪关 | **`finally`** —— 请求失败时 `await` 后面不执行 |
| `v-loading` 按需引入要不要注册 | **要**，`app.use(ElLoading)` 或局部 `vLoading` |
| `ElConfigProvider` 放哪 | **App.vue 最外层**（它靠 `provide/inject` 往下传） |
| `el-upload` 为什么要 `:headers` | **它不走 axios**，拦截器管不到 |
| `on-success` 的 `response` 是什么 | **完整 body**（`code` / `data` 都在） |
| `before-upload` 怎么中断 | **`return false`**（返回 undefined 会继续传） |
| `QuillEditor` 的 v-model | **`v-model:content`**（具名） |
| `content-type` 不写会怎样 | 存成 **delta JSON**（`{ ops: [...] }`），后端不认 |
| Quill 的「空」是什么 | `'<p><br></p>'` —— **真值**，所以 `!content` 判断无效 |
| `Object.assign(form, row)` 的坑 | **不删 key** → 上一条数据的字段残留 |
| 新增成功后要不要翻页 | **`page = 1`**（新文章在第一页） |
| 编辑成功后要不要翻页 | **不要**（位置没变） |
| 编辑提交用哪个方法 | **`PUT`**（有 id）/ `POST`（无 id） |

## 3. ⭐ 收敛时刻

**① 「页码」这件事，在这一轮出现了四次，而且是同一个病根。**

| 位置 | 症状 |
|---|---|
| 改每页条数不归 1 | 空白列表 |
| 搜索不归 1 | 空白列表（或结果不全） |
| 重置不归 1 | 空白列表 |
| 新增不归 1 | **看不到自己刚发的东西**（以为发布失败） |

**四次症状不同，病根完全相同**：**「当前页」是一个「依赖于数据量」的派生状态，但它是手动维护的。**

**这就是「冗余状态」的代价**：`page` 和 `total` / `pageSize` 之间有一个隐含的约束（`page ≤ ceil(total/pageSize)`），**但这个约束没有任何东西在帮你维护**。

**Vue 的响应式只负责「数据变了 → UI 变」，不负责「数据之间的一致性」。** 这是你要自己保证的。

**工程上怎么办？** 两种思路：

| 思路 | 做法 | 代价 |
|---|---|---|
| **收口** | 所有「改 range」的操作都走一个 `resetAndFetch()` 函数 | 要用的人记得调 |
| **派生** | 用 `computed` 算出「有效页码」= `Math.min(page, maxPage)` | 请求参数要跟着变，链路更绕 |

**课程用第一种（手写 `page.value = 1`），因为看得见。** 第二种更「正确」但少有人这么写 —— **因为前端项目里「显式」比「优雅」更容易维护**。

**② `el-upload` 那个坑，暴露了「封装」的边界在哪。**

你花了整整一集（篇 1 的 166）封装 `request.js`，以为「所有请求都过这道闸」。**结果 `el-upload` 从旁边绕过去了。**

**这不是封装写得不好，是封装的本质决定的**：

> **封装只能管「愿意走这个入口的代码」。**

**你以后会反复遇到这个边界**：

| 场景 | 绕过去的方式 |
|---|---|
| `el-upload` | 组件内部自己发 XHR |
| 富文本里插入图片 | 编辑器自己的上传 handler |
| `<img src="...">` | 浏览器直接请求 |
| 第三方 SDK（地图、统计） | 自己的网络层 |
| WebSocket | 完全另一套协议 |

**每一次你都要问同一个问题：它带不带我的凭证？带的话怎么带？**

**这个思维模型比记住 `:headers` 这个属性值有用得多。**

**③ 三篇连起来看，你其实在学「一件事的三种写法」。**

| 篇 | 「一个功能」的不同层次 |
|---|---|
| 篇 1 | **基础设施**：让「发请求」这件事有统一入口 |
| 篇 2 | **模式**：表单（校验→提交→刷新）+ 弹层 |
| 篇 3 | **极限**：同一个模式加上「分页 / 搜索 / 上传 / 富文本」四个复杂度 |

**篇 3 没有引入任何新的「模式」** —— 它用的还是篇 2 的「校验→请求→提示→关闭→刷新」。

**新增的四个东西，全都是「模式之外的干扰项」**：

| 复杂度 | 干扰在哪 | 你在哪学的对策 |
|---|---|---|
| 分页 | 「范围」状态要维护 | 本篇的归 1 规则 |
| 搜索 | 「条件」状态要维护 | `getList` 无参、参数现取 |
| 上传 | 不走统一请求层 | 手动 `:headers` + 认原始 body |
| 富文本 | 数据形状不是字符串 | `content-type="html"` |

**这就是「业务复杂度」的真面目**：**核心逻辑永远很简单，难的是外围状态越来越多，而它们之间互相牵连。**

**这也解释了你为什么会觉得「项目写到后面越来越乱」** —— 不是你的代码变差了，是**状态的数量在指数增长**，而你还没有「收口」的习惯。

**收口的三个动作**（本系列反复出现的，这次是最后一次点名）：

1. **把重复的值收进变量**（`baseURL`、`whiteList`）
2. **把重复的流程收进函数**（`getList`、`confirmBox`）
3. **把重复的结构收进组件**（`PageContainer`、`ChannelSelect`）

**三个动作，一个目的：让「会变的东西」只有一个地方要改。**

## 4. 静默失败清单

| # | 写法 | 现象 | 真相 |
|:--:|---|---|---|
| 1 | `v-loading` 没注册指令 | 表格正常显示，**没有遮罩**，控制台一条 warn | `ElementPlusResolver` 不管指令 |
| 2 | 局部注册写 `const loading = ElLoadingDirective` | 无效 | 必须叫 **`vLoading`** |
| 3 | `loading` 不在 `finally` 里关 | 请求失败后**遮罩一直转** | `await` 抛异常，后面不执行 |
| 4 | `el-upload` 没写 `:headers` | **401**，上传失败 | 不走 axios，拦截器管不到 |
| 5 | `on-success` 里写 `form.cover_img = response` | 图片地址变成 `[object Object]`，图裂 | 这里 `response` 是**完整 body**，要取 `response.data`（⚠️ 与组件里恰好相反） |
| 6 | `before-upload` 忘 `return false` | 校验「没生效」，什么都能传 | 只有明确的 `false` 才中断 |
| 7 | `QuillEditor` 用 `v-model` | 编辑器能打字，`form.content` **永远是 `''`** | 它认的是 `content` 这个 prop |
| 8 | 不写 `content-type="html"` | 后端存成 `{ops:[...]}`，详情页显示异常 | 默认 delta 格式 |
| 9 | 忘 import `vue-quill.snow.css` | 没有工具栏，就是个白框 | 样式文件要单独引 |
| 10 | 富文本「空」用 `!form.content` 判断 | 判不出来 | Quill 的空是 `<p><br></p>` |
| 11 | `Object.assign(form, row)` 前不重置 | **上一条数据的封面/内容残留** | assign 不删 key |
| 12 | 搜索/重置/改条数不把 `page` 归 1 | **空白列表** | 页码超出总页数 |
| 13 | 新增后不归 1 | 看不到刚发的文章 | 新数据在第 1 页 |
| 14 | `getList(params)` 接受参数 | 某处忘了传 → 用了默认值 | 参数应在函数体内现取 |
| 15 | `GET` 把数据写成第二个参数 | 后端收不到，**axios 不报错** | 要写 `{ params: {...} }` |
| 16 | `el-config-provider` 只包了页面 | 弹层里的分页/日期**还是英文** | teleport 出去了，provider 要在最外层 |
| 17 | `Object.keys(form).forEach(k => form[k] = '')` 漏了 `id` | 新增时带着上次的 id → **变成修改** | `id` 要单独置 `null` |

**重灾区：5、6、11、17。**

**第 5 条特别绕**，值得单独说 —— **它是本篇唯一「两套规则打架」的地方**：

```js
// 组件里（走 request.js）
const res = await getArticleListAPI()      // res = data
list.value = res.items

// 上传回调（不走 request.js）
const onSuccess = (response) => {
  form.cover_img = response.data           // response = 完整 body
}
```

**两处都叫「拿数据」，但层级差一层。** 判断依据永远只有一条：**这段代码走没走 `request.js`。**

**工程上怎么防**：**在这两处各写一行注释**，把「我在哪一层」标出来。这比任何文档都有效：

```js
// ⚠️ 此处 res 是后端 body 的 data（拦截器已拆包）
const res = await getArticleListAPI()
```

```js
// ⚠️ 此处 response 是完整 body（上传不走 axios）
const onSuccess = (response) => { ... }
```

## 5. C# 类比可用度

| C# / .NET 侧 | 前端侧 | 可用度 | 注意 |
|---|---|:--:|---|
| `List<T>` 分页 + `Skip((page-1)*size).Take(size)` | `el-pagination` 的 `pagenum` | ⭐⭐⭐ | **`(page-1)` 那个 1 在两边都存在** |
| `HttpClient` 单独 new 一个不走 DI 的实例 | `el-upload` 绕过 axios | ⭐⭐⭐ | 「绕过统一入口」的两世界版本 |
| `MultipartFormDataContent` 上传 | `el-upload` 的 `action` | ⭐⭐ | 前端这个更省事（表单自己拼） |
| `IFormFile` 的 `ContentType` / `Length` | `before-upload` 的 `file.type` / `file.size` | ⭐⭐⭐ | 同一个「先校验再收」的思路 |
| AutoMapper 的 `Map(src, dest)` | `Object.assign(form, row)` | ⭐⭐⭐ | **都是「按 key 覆盖，不删多余 key」** |
| `CultureInfo.CurrentCulture` | `ElConfigProvider` 的 `locale` | ⭐⭐⭐ | 都是「一处的配置影响一片 UI」 |
| 局部 `CultureInfo` 覆盖 | provider 子树限制 | ⭐⭐ | 前端的「子树」比 C# 的线程文化更物理 |
| WPF 的 `RichTextBox` / RTF | `QuillEditor` | ⭐⭐ | 都是「格式化的内容」，但序列化格式完全不同 |
| Blazor 的 `@bind-Value` | `v-model:content`（具名） | ⭐⭐⭐ | 具名绑定的概念完全一致 |
| `finally` 里释放资源 / `using` | `finally` 里关 `loading` | ⭐⭐⭐ | **同一条纪律：清理必须无条件执行** |

**最值得记的一条**：**AutoMapper 的 `Map(src, dest)` 和 `Object.assign` 是同一个陷阱。**

```csharp
var existing = db.Articles.Find(id);      // 有 cover_img
mapper.Map(dto, existing);                // dto 里没有 cover_img
// → existing.cover_img 还是旧值
```

**你以后写 ASP.NET Core 的更新接口时，这个坑会再等你一次。** 那时候你会想起来「前端也踩过」。
